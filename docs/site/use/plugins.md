## Purpose

Select, activate, observe, drain, disable, replace, or retire a plugin without
allowing project content to expand trust or permissions. This page is the only
canonical plugin-lifecycle procedure.

The generated [plugin catalogue](../extend/plugin-catalogue/README.md) is the
published, dynamic package list. Counts and package names are not copied here
because they change with the source tree.

## Complete Operator Views

The generated rows below assign every discovered package to an operator task,
host, role, surface, and declared dependency. They also assign every discovered
registration to its external-service evidence. Publication fails when discovery
and these rows drift. Use the [recursive plugin configuration
reference](../reference/plugin-configuration.md) to interpret nested fields and
conditional schema branches.

`source-backed unknown` is a stop condition when it affects authority, secrets,
data ownership, or a required live dependency. It is not evidence that no
dependency exists.

## Canonical Plugin Lifecycle Procedure
<!-- operator-task: plugin-lifecycle -->

### Supported start state, version, location, and authority

Start with a clean checkout at the exact source commit, an existing
`pipeline-platform.v2` file, an operator-supplied project or graph that uses the
plugin, and writable durable storage. Run commands from `<repository-root>` on
an administration machine with Node.js 24. The platform configuration owner,
not project content, controls installation roots, built-in trust, external
digests or attestations, providers, grants, adapters, observers, and storage.

The registry supports discovery and activation of packages already present in
approved installation roots. Internal APIs can copy or remove a local external
package, but the repository exposes no general operator CLI for those actions.
Do not turn an internal API or a filesystem copy into an undocumented operator
command.

### Preconditions

- Record the source commit and SHA-256 digest of `<platform.json>`.
- Identify exact package ID, registration ID, contract version, content digest,
  capability grants, dependencies, secret names, and every active run that pins
  the package.
- Complete the per-plugin external dependency matrix above and assign an owner to
  every required reachability check and failure response.
- Keep plugin code and schemas available for every nonterminal pinned run.
- Keep secret values only in the configured secret authority. Platform and
  project JSON may name secrets but must not contain their values.
- Prepare a controlled project or graph whose external effects are safe and
  whose success proves the selected registration.

Stop when a package identity is ambiguous, its digest or attestation is absent,
a dependency has no owner, a requested grant is wider than intended, or a
procedure would place a secret in evidence.

### 1. Discover and select

First complete the canonical
[Locked Dependency Installation](quickstart.md#locked-dependency-installation)
in the disposable checkout. Its retained evidence is part of this procedure's
evidence.

```bash
git status --short
git rev-parse HEAD
npm run plugin-system:inventory:check
npm run verify:plugin-packages
sha256sum "<platform.json>"
```

Expected observation: the worktree has no unexpected change, inventory and
package verification exit zero, and the recorded platform digest matches the
file to be used. Inspect the dynamic catalogue and select by exact IDs and
contract version, never by discovery order.

Check these platform fields together:

| Field | Operator decision |
| --- | --- |
| `installationRoots` | Canonical roots allowed for discovery |
| `trustedBuiltinRoots` | Which discovered roots are trusted built-ins |
| `externalTrust` | Exact source digest or verified-attestation binding |
| `providers` | One registration selected for each required capability |
| `grants` | The least capability scope for each registration |
| `adapters` and `activeAdapters` | Configuration and which adapters start |
| `observers` | Configuration for enabled observers |
| `storageRoot` | Persistent private run storage |

Relative roots resolve from the platform file, not the shell directory.

### 2. Validate a candidate configuration without starting work

Have the platform owner create `<candidate-platform.json>`. Then compile a
controlled project to a new output path:

```bash
test ! -e "<compiled-pipeline.json>"
npm run pipeline -- \
  --platform "<candidate-platform.json>" \
  --project "<controlled-project.json>" \
  --compile "<compiled-pipeline.json>"
sha256sum "<candidate-platform.json>" "<compiled-pipeline.json>"
```

Expected output is a JSON object with `status` equal to `compiled`, a run ID,
stage count, and definition digest. Compilation validates discovery, trust,
registrations, selected providers, schemas, configuration, and grants. It does
not prove an external endpoint, account, credential, or live dependency.

Distinguish failures before changing anything:

| Observation | Cause class | Action |
| --- | --- | --- |
| Manifest/schema/digest error | Package or trust input | Reject the candidate package |
| Duplicate ID or provider ambiguity | Registry selection | Select one exact registration; do not depend on order |
| Missing grant or denied resource | Authority policy | Confirm intended need; do not widen the grant merely to pass |
| Missing secret name | Secret configuration | Provision through its owner, then retry validation |
| Adapter readiness/startup error | Dependency or adapter configuration | Repair the named dependency; activation is transactional |
| Project requests uninstalled stage | Project/package mismatch | Correct the project or select an approved package |

### 3. Activate and prove health

Activation occurs while Nova prepares the runtime for a compile or run. It is
fail-closed: a failed registration or adapter startup must not be treated as a
partially healthy registry. After the non-mutating compile, start the controlled
project only during its approved window:

```bash
npm run pipeline -- \
  --platform "<candidate-platform.json>" \
  --project "<controlled-project.json>"
npm run pipeline -- \
  --platform "<candidate-platform.json>" \
  --audit "<run-id>"
```

Take `<run-id>` from the first command. Expected observation: the selected
registration appears in the resolved graph and attempt evidence, its functional
result succeeds, and audit state agrees with the terminal command output.
Registry activation alone is not health; the controlled functional result is
the health proof.

For endpoint, account, or data failures, use the
[canonical symptom diagnosis procedure](diagnose.md#canonical-symptom-diagnosis-procedure).
Do not retry an accepted external effect until its request and receipt are
reconciled.

### 4. Drain and disable

Stop admission of new projects that select the registration. Audit every active
run and let safe work reach a terminal state:

```bash
npm run pipeline -- --platform "<active-platform.json>" --audit "<run-id>"
```

There is no supported operator cancel command. If a run remains active or
waiting, keep the plugin package, schema, configuration, secrets, and dependency
available. Urgent process containment does not make the durable run cancelled.

After every pinned run is terminal, have the platform owner create a candidate
that removes the registration from provider selection, active adapters,
observers, and grants. Repeat the compile procedure. Expected observation: the
replacement controlled project compiles without the disabled registration and
unrelated registrations retain the same identities.

### 5. Replace or remove

For replacement, add and validate the new exact package before disabling the old
one. Prove the new functional path, drain old pinned runs, then remove old
selection and grants. Do not delete the old package while a run snapshot or
validator can still reference it.

For external package removal, stop after drain unless an approved operator tool
calls the owned removal API with authorization and a direct child of the
installation root. The repository currently supplies no such general command.
Manual filesystem deletion is unsupported. Built-in packages remain part of the
selected source tree; remove their activation from platform configuration, not
their files from a live checkout.

### Recovery, cleanup, and evidence

Before activation, recovery is to discard the candidate configuration. After a
new run begins, restore the previous compatible platform configuration only for
new admission; existing runs remain bound to their original graph and package
snapshot. Reconcile uncertain effects before another run.

Remove unused temporary compiled files and candidate files only after retaining
their hashes and final decision. Revoke a plugin secret only after all consumers
are drained and the old identity is proved unused. Retain source commit,
catalogue identity, package and platform digests, grants, dependency owners,
secret names, compile output, functional result, audit, drain inventory,
replacement proof, cleanup result, and exact blocked step.
