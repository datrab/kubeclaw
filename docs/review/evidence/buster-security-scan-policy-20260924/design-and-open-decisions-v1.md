# security.scan host policy — source inventory and design proposal

Status: private source-derived design only. No production/test code change, runtime, build, lint, deployment or configuration activation. Source identities and copies are in `source-identities-v1.json` and `sources/`. This is the next bounded CONFIG proposal, not closure of security.scan, CONFIG, original findings or live gates.

## Current execution path and actual authors

Production runtime JSON is decoded by `production-capability-sources.ts` into `securityScanSource`, made mandatory when `allowedCapabilities` contains `security.scan`. `production.ts` calls `securityScanOptions`, which reads executable, full registry prefixes, execution/output limits and cache path from that object. It optionally decodes database policy and scanner-specific registry metadata. The real capability factory constructs `SecurityScanCapabilityInvoker` in the job workspace; provider IPC can request dependency, image or Kubernetes-policy scans.

The entrypoint independently authors five obvious values and three database values in runtime JSON. TrivyDatabase's exported DEFAULT_TRIVY_DATABASE_POLICY and default parameter provide the same three values a second way. Direct constructor policy is optional. The command wrapper separately authors a three-directory PATH. Database inspection separately authors a 16384-byte metadata admission quota. Finding projection separately truncates titles to 2048 and policy message/resolution to 4096 code units. The proposed 13-field inventory names each actual consumer and initial checked-in value; these additional five authors must not be overlooked by moving just the old runtime object.

Constructor performs workspace/executable realpath/access before full policy validation. Decoder coerces missing executable/cache values through String before resolving paths. Direct registryAccess is stored by reference while registry prefix arrays and database scalar policy are copied. Missing/invalid policy must reject before these effects, and nested registry-access changes must not alter a previously validated consumer.

Dependency/image scans verify both actual database files and metadata before and after execution, reject changed identity, check source UpdatedAt age (not DownloadedAt/mtime), and include DB identities in result digest. Each DB gets the configured individual byte cap, not a combined quota. Metadata is separately admitted and retained for JSON parsing. Config scans bypass DB inspection and require manifest digest matching. The whole deadline includes DB work; each actual command gets only remaining time. Payload timeout can reduce the configured maximum but supplies no independent numeric maximum when omitted. Trivy CLI timeout rounds milliseconds upward to seconds while the host deadline remains millisecond-bound.

## Proposed sole component owner

Use required `settings.securityScan` in the existing complete `buster-engine.config.json`, rather than putting a non-cluster scanner under `clusterInvokers`. Both maintained complete Buster profiles must author the entire object. Update the closed Buster settings type/schema and both-chart shared validation from five to six declared sections; preserve exact whole-selected-file packaging, ConfigMap, checksum and physical-generation capture. Relative executable/cache paths resolve from that captured generation, never old runtime JSON or later alias resolution.

All 13 proposed fields are required even with the route disabled. Active permission remains independent of config presence. Remove the entrypoint policy object, optional database-policy decoding, default constant/default parameter and every replaced runtime policy reader. Reject the old `securityScan` runtime key by presence including null/empty/equal input before registry/store effects. A transport binding may remain as a distinct single-author delivery object only after the registry decision below. Direct constructors and `databasePolicy` require explicit validated policy; original direct callers load or state the original effective values explicitly instead of inheriting code defaults.

Preserve existing meaningful numeric domains: execution 1..2147483647 ms, output >=1024 safe integer; DB ages 1..2592000000 ms and DB bytes 1..34359738368. Metadata/text quota domains need review; use positive safe integers unless an actual contract dictates a narrower bound. Do not copy unrelated namespace/prefix maxima or invent array ceilings. Registry string semantics must preserve exact-or-slash-child matching. PATH entries must explicitly name absolute directories without delimiter/NUL, with no fallback to host PATH.

## Registry authority: decision needed before implementation

The existing single operator registry contract is rendered by `registry-client-config.mjs` from KUBECLAW_REGISTRY_CONFIG. The entrypoint currently duplicates that generated runtime descriptor into both `containerBuild` and `securityScan.registry`. The scanner decoder separately validates origin/reference consistency and credential ENV names. Missing scanner registry permits an anonymous direct/legacy scanner; an explicitly supplied HTTPS registry requires credentials, and HTTP lab must fail image scans rather than disable TLS verification. Direct constructors can scan public registries without registryAccess.

Do not introduce another editable endpoint, transport, username/password value, CA file policy or independent registry ENV fallback. Normal production can derive scanner repository prefixes from the same registry origin already used by containerBuild, while the scanner owns only repository-admission prefixes. Reuse the descriptor/credential resolver and preserve TLS, scoped credentials and HTTP-lab denial. Secrets remain external; temporary Docker auth files are generated delivery and never component values or evidence payloads.

**Open compatibility/design gate:** simply requiring containerBuildSource for every enabled security.scan route would reject previously valid dependency/config-only runtimes and anonymous-public-image direct profiles. Likewise converting all formerly full allowedRegistryPrefixes to prefixes relative to one host could silently remove legitimate multi-registry scope. That restriction is not authorized by this inventory. Prefer making the existing generated registry-client descriptor one shared runtime binding consumed by both BuildKit and scanner, with no duplicated endpoint fields; explicitly map how public/anonymous prefixes reference their existing external registry authorities. The precise public registry reference model and absent-binding behavior must be agreed before code. Do not invent an imageEnabled switch or a second endpoint author merely to make tests pass. Direct API credential ownership/immutability remains testable independently of this normal-runtime projection decision.

The image build places locked DB artifacts at `/home/builder/.cache/trivy`. That installation path is an image layout contract, not an alternate runtime cache fallback. An operator-selected different cache path must receive the genuine corresponding DB artifacts via explicit packaging/mounting; do not redirect silently or create fake empty DBs. `versions.json` / the maintained generated DB lock / pinned scanner release retain software/artifact authority, not a new duplicate component version field. Database installer transport limits (for example curl600s and default manifest1MiB) remain a separate installer-owner CONFIG inventory, not silently closed here.

## Literals distinguished from operator budgets

The proposed scan-owned budgets include PATH, metadata byte admission and lossy finding text ceilings because they materially select behavior. Other inspected literals are request/format/security contracts: supported operations, Trivy JSON SchemaVersion2, DB schemas2/1 and fixed DB filenames, SHA-256/image grammar, path containment, result digest, exact findings mapping, no telemetry/update flags, UTF-8/no-color output, credential directory0700/file0600 and registry-specific credential scoping. These cannot become options that bypass security. Generic request text lengths (operation32/path4096/image2048/digest71, vulnerability ID256/package512, timestamp64) are currently fixed interface bounds; any later decision to make them operator policy must preserve downstream contracts rather than copy arbitrary ranges.

UNKNOWN/info/unknown and absent optional installed/fixed values are scanner-result normalization, not operator config defaults. This classification does not excuse actual configurable resource authors. Provider-layer request defaults remain independently open: dependency/image300000ms with1000..900000 bounds, Kubernetes-policy120000ms with1000..300000 bounds; common provider finding truncations and strict policy are separate provider-owned migration work. Host settings must not pretend to eliminate those authors.

## Concrete outstanding defects and resource boundaries

- execute aborts before recording OUTPUT_LIMIT; synchronous abort can replace the real cause with TIMEOUT, as previously observed in RuntimeSecurity. A proposed fix needs its own exact old-order control; it is a behavior correction, not pure config movement.
- Child wrapper can settle before actual close and has no detached-group ownership. Finally may remove Docker credential files while scanner work has not been confirmed stopped. Test-owned cleanup cannot prove production ownership; these remain required overall work.
- Kubernetes-policy manifest uses unbounded readFileSync before execution; output quota does not cover it. No manifest budget value is authorized by this inventory.
- Raw output quota does not establish parsed JSON/finding-count/retained-result memory bounds. DB streaming bounds file bytes but does not prove native CPU/RAM/task isolation; library stream buffer defaults are also not component-owned memory policy.
- Credential-directory creation/write can fail before its path is returned to #scan, leaving cleanup ownership incomplete. Constructor aliases registryAccess. Both need explicit defect treatment, not hidden failure suppression or a broad config pass.
- New metadata/text field configuration retains current truncation initially. Whether result truncation should instead expose counts/diagnostics is an explicit integrity decision, not an implicit migration change. No scan/source evidence may be silently dropped to satisfy resource tests.

No implementation starts until owner placement, all extra authors, registry compatibility and the above scope/remaining-work boundaries receive independent design review.
