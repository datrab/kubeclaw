## Findings

### DMC-01 — P1: six full-facade selections do not establish six installed owner instances per service

Proposal README lines 23–39 requires six tuple references for each service, supplied as actual installed/service owner instance identities, and blocks a role/service without an authentic full mapping. Current `swarm.ts:238–263` indeed validates six documents before exposing any facet, so retaining full-generation validation is justified. It does **not** establish six independently installed component instances for Studio, Control or Buster. Actual consumption is Control→control/execution; Worker→worker/control/execution; Studio→studio; Buster child→buster/worker-core. Owner documents are configuration domains, not six installed plugins/services.

The current Chart caller `charts/prism/templates/workloads.yaml` renders Control/Studio/Worker identities; role packaging selects nova/buster/prism (`packaging/runtime/roles/*`, build-runtime-role-bundle.mjs). No inspected caller provides the proposed six owner-instance mapping. The proposal names an authenticated installation mapping without naming its local representation, issuer/verification boundary or how validation-only domains acquire authentic IDs. Missing actual deployments are external, but the meaning and productive wiring of this mapping are local definition work.

**Required correction:** define the exact generated selection/mapping schema and provenance at each actual caller, distinguishing service identity, consumed-owner identity and full-facade validation selection. Either justify six explicit profile choices without asserting unrelated installed instances, or supply a real relationship contract proving those instances are needed. Do not invent equal instance IDs, standard IDs or a Nova reader. Preserve full-tree/all-profile validation and root-only profile authorship. Add exact proposed case oracles using existing case IDs for unrelated-owner mapping omission, root tuple reorder and mapping ambiguity.

### DMC-02 — P1: ConfigMap item mapping is not a physical no-follow component tree

Proposal capture steps require no-follow component reads and reject symlinked refs/ancestors; delivery table proposes ConfigMap key→relative-path volume items and read-only mounts. Existing productive delivery is `charts/prism/templates/configmap-swarm-config.yaml`→`workloads.yaml:193` ConfigMap volume; Kubeclaw uses `deployment.yaml:1643–1645`. Current loader `swarm-bundle.ts:60–66, 92–95` opens each component with O_NOFOLLOW, while only entry is realpath-resolved. ConfigMap projected files use the atomic-writer symlink layout; `items.path: components/...` preserves names but does not make the leaf or intermediate projected path ordinary physical files. Merely changing mount paths will not satisfy the proposed physical nested-tree contract.

**Required correction:** choose and specify a concrete delivery solution, e.g. trusted pre-start materialization into a verified regular-file immutable tree (including ownership/modes, receipt verification, no partial startup, directory durability and read-only handoff), or a tightly bounded captured projection resolution that preserves no-follow at physical leaves and rejects escaping refs/ancestor drift. Identify both real Chart boot callers, not just a proposed filesystem helper. Pin the chosen exception/alias rules in entry-profile and delivery contracts. Include actual Chart/package/mount/loader positive and symlink-negative future oracles. This is a proposal defect, not a newly asserted reproduction of a historical live failure.

### DMC-03 — P1: parent/child generation handoff remains an alternative, not one versioned ABI

Proposal README says to extend runtime.json's receipt association **or** use inherited boot handoff. The actual parent captures settings at `preparation-supervisor.ts:25`, uses `nativeBusterPreparationConfig` for pool/config/key verification and spawns setpriv with fixed `--config` plus fd3 (`:56–61`). Child `remote-plan-cli.ts:21–26` independently rereads SWARM_CONFIG before initializing its native channel/runtime. No existing association currently conveys the proposed generation/selection receipt.

**Required correction:** select one exact handoff representation/version, writer and transport; specify parent publication, child authentication/verification, physical generation locator and expected receipt ownership, restart/lifetime retention and mismatch-before-admission behavior. Keep fd3 NativeWorkerControlChannel protocol and runtime --config semantics explicit; do not implicitly multiplex an unversioned object or add settings ENV overrides. Define behavior if publication switches A→B after the parent captures A but before child startup. A mismatch must not silently cause the child to select B. This can be defined locally without operator credentials.

### DMC-04 — P1: C5 binding acceptance lacks an explicit live mutation-authority recheck after async preparation

Proposal `resolveOrBindModule` performs asynchronous object/reservation preparation, then FileJournal.transact synchronously rechecks only unique binding and appends. Existing `run-mutation.ts:7–24` renews a TTL lease, aborts its signal on renewal failure, but only throws renewalError after operation completes. FileJournal.transact (`journal.ts:155–177`) provides append serialization, not verification of the run-mutation lease. Thus merely being inside withRunMutationLock does not define a no-append fence following lease loss during preparation. C5-COMPLETE-LEASE-LOSS explicitly expects no binding append/view/activation/effect after loss.

**Required correction:** make the algorithm's synchronous acceptance boundary explicitly verify the current mutation authority/fence and aborted lease state after async preparation and before binding acceptance; specify authority identity/epoch and protection against stale owner acceptance. Also recheck before returning activation/projecting an attempt, including already-bound paths. Name any required run-mutation/lock API delta as C5 rather than assuming the existing journal mutex supplies it. Preserve no-await callback and no-rollback assumptions. Define orphan reservation accounting on rejected acceptance. No demand for a new budget ledger.

### DMC-05 — P2: cleanup generation rule is internally ambiguous

Actual group table gives a separate `preparation-cleanup` group its first eligible unbound selection B; crash table says **every** cleanup dependency of a started group stays A. `preparation-cleanup-binding.ts:15–22` pins original envelope/settings/effects and predecessor receipts, so dependency association is not automatically same-group membership. The target schema explicitly distinguishes kind=preparation-cleanup.

**Required correction:** state that same-group continuation/retry/repair remains A, while a separately declared, eligible unbound cleanup group may select B only for allowed M fields under pinned original effect/source/reservation/grant/budget constraints. Define exact membership/dependency edge, not natural-language “cleanup dependency.” Cross-reference all 13 preserved canonical cleanup cases with the first-bind-versus-recovery distinction and fixed-eval override.

### DMC-06 — P1: standalone Buster replay must resolve stored binding before current runtime authority checks

Proposal correctly says existing standalone records win on retry, but only gives an archive-first recovery ordering algorithm for Nova. Actual `remote-plan-service.ts:118–137` calls `#validateAuthority(job)` against `this.#options.registry.snapshotDigest` **before** locating the known stored job; `:150–151` starts the staged object after store.accept. `prepared-plan-store.ts:96–107` returns old status for matching idempotency identity, not a bound runtime/projection. Merely adding binding digest to acceptance records does not make an A job recover when the service starts with B registry/provider closure; it may reject before discovering A, or dispatch using current service options.

**Required correction:** define standalone stored-record/archive-first lookup and original bound registry/provider/settings projection at submit replay, bootstrap recovery, queue/start and cancellation/evidence/result paths. Separate immutable request conflict validation from candidate-current-authority validation for genuinely new admissions. Version the strict job-record field set (`prepared-plan-store.ts:25–32`) and define missing archived closure rejection. Preserve matching idempotency conflict and attestation checks and real grant ceilings. The original stored job, not incoming staged/current settings, must supply the launch closure.
