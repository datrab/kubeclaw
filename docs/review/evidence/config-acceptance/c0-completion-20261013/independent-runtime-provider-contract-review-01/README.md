### RPR01-03 — Pre-effect oracles falsely classify response-schema and redirect failures

Affected IDs include `RT-10f3f03208806c98` specFile and `RT-396eb59b11141a9a` operations, their original OpenAPI case families, and associated native C3 target/redirect cases. B `source-consumer-contracts.md:43` groups external/cyclic refs and unsafe patterns as failures **before request**. That is false for a supported operation containing such a selected **response body schema**.

Actual `openapi/src/provider.js:235` awaits capability invoke first. Response rule selection occurs at237 and body schema validation at247; `schemaFailures:67` then calls `assertSupportedSchema`, local-ref resolution and `safePattern`. A GET /ok with a response schema `{type:'string', pattern:'(a+)+'}` can reach transport before reporting pattern-unsafety when its response string is validated. A response-body schema `$ref` to an external document is likewise not validated in the pre-request `responseRules` collection (only top-level response objects are resolved there). Unsupported dialect is an earlier spec guard; request parameter/body schema checks are also earlier. Those gates must not be merged.

B line47 similarly places redirect denial before intended transport effect. Both actual native and Nova implementations obtain a response from fetch before rejecting redirect status; they deny **following** the redirect, not the initial request. Native exact over-limit response error name is `HTTP_REQUEST_RESPONSE_LIMIT_INVALID`, not an invented generic `HTTP_RESPONSE_LIMIT_INVALID`.

**Required definition correction:** split request preflight, response-object-ref collection and post-response body/header/schema/redirect boundaries; retain actual first-error/cleanup/uncertainty consequences and exact positive controls. Moving response validation before effect would be a separate proposed behavior change requiring explicit justification/implementation cases, not a current-source fact.
