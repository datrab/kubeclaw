### R02-02 — P1: existing lifetime.lock cannot supply the proposed parent/child lifetime authority

02 DMC-03 says supervisor writes/retains handoff while entrypoint holds existing fd9 lifetime.lock, supports child restart under the same parent and retires old handoff after parent/child quiescence. The actual `docker/buster-runtime-entrypoint.sh:12–13` acquires fd9, but its native parent spawn at `:316/:319` explicitly uses **`9>&-`**. Native parent and its setpriv child therefore do not retain that lifetime lock. Entrypoint death releases it even if old parent/child continue; native-parent crash can leave child shutdown/quiescence in flight while shell wait returns and lock is released. Regular root-owned files and a newly obtainable shell lock do not prove old-process quiescence. 02 names the desired condition but not the changed lifetime ownership or concrete quiescence check. Its DMC-03 oracle tests child restart and second writer while a parent lives, not abrupt entrypoint/native-parent loss with a surviving child.

**Correction required:** define the exact lifetime ABI delta: which processes retain or intentionally close which descriptors, when an entrant can acquire authority, and the verified old-parent/old-child/native-admission quiescence boundary before retirement/publication. One valid approach may propagate a lock-held lifetime receipt/descriptor to necessary processes with explicit close/release rules; another may use existing supervised process/ownership reconciliation, but its actual source boundary must be named and absence of prior work proven. Do not equate file ownership/bootId echo with process lifetime. Specify crash-before/after-handoff, entrypoint/native-parent SIGKILL and surviving-child behavior, safe stale handoff retirement and startup rejection until quiescence. Extend existing DMC-03 case oracle using preserved IDs; no arbitrary PID-kill fallback or new worker topology required.

The exact handoff path/version/closed fields, root:builder0440/0750, child before-channel validation, fixed A generation and versioned fd3 association are otherwise correctly defined. Channel-version delta must preserve actual framing/admission/byte-accounting semantics in preparation-channel/parent-channel; no unversioned extra frame is accepted.

### R02-03 — P1: downstream effect fence has no specified receiver for the run mutation epoch

02 DMC-04 now correctly defines a proposed metadata-mutex-held synchronous guard, events append lock order, final expiry/signal checks, already-bound views and durable-append-versus-later-expiry behavior. This addresses the original journal acceptance gap. Its final step still says to carry the same original pipeline.run lock epoch until an existing downstream effect/lease boundary accepts it, wired through existing effect invocation fences, without defining that handoff boundary.

Actual `execution/adapters.ts:54–63` builds EffectInvocation without a run mutation authority. `effects/contracts.ts:EffectInvocation` has no such field or internal guard association. `durable-invocation.ts:124–144` supplies a fence for **its per-effect resource lock**, owned by attempt.attemptId; it does not verify the distinct pipeline.run ownerLeaseId/fencingToken. `coordinator.ts:invokeConfidential` uses signal/lease checks and directly calls adapter.invoke, without that resource fence. Thus “existing downstream fence accepts the same original epoch” is not an available source fact. Checking StageExecutor before asynchronous setup is not a defined acceptance handoff across those awaits, and the confidential route must not be omitted.

**Correction required:** name the concrete proposed internal run-authority transport/guard association and receiving API changes at StageExecutor→AdapterRuntime→EffectCoordinator→durable/confidential invocation (and relevant startup effect routes). Specify the synchronous authority check/acceptance point after awaited setup/journal operations, separate run versus effect resource lock identities, lock order and what authority is retained or revalidated at adapter/provider effect entry. Include missing/stale association rejection and no queued callback based only on an earlier valid view. Preserve existing per-effect fencing and original grants/budget/deadline semantics; no requirement for a new ledger, provider grant enlargement or async-held metadata mutex. Add explicit future oracle coverage for lease loss between effect-journal acceptance and adapter entry, plus the confidential branch. APIs are definition targets, not claimed implemented now.
