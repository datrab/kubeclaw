# Kubernetes failed-prepare cleanup source audit

Source-only finding, not an observed cluster leak. Bound inputs are in source-identities.json. No runtime, live source edit or cluster operation was performed.

The preparation catch always rethrows the failed activation error. Swallowing the compensating release rejection therefore cannot itself convert that invocation to success. It does erase the fact that deletion was not confirmed: lease/namespace resources may remain. The same guarded catch starts only after successful lease apply; an ambiguous failed apply lies outside that existing guard and is a separate issue, not silently fixed by this proposal.

The actual chain is public capability invoker → preparation.prepare → waitLease/apply workload/waitPods/waitService/credential handling → failed activation → bounded releaseAfterPrepareFailure → kubectl delete. Its separate AbortController has the selected maximumExecutionMs bound. Deletion failure is currently discarded before the original activation failure reaches the caller.

The registered Kubernetes provider awaits context.invoke; a rejected prepare cannot produce its successful deployment outputs. ProviderCapabilities transports only error.message in an ok:false IPC reply, and provider-child recreates an Error. Cause/AggregateError structure alone does not cross this boundary. A corrective aggregate therefore needs an explicit stable cleanup-failure marker in its top-level message.

Runner initializes executionStarted before execute. Failed execute normally runs provider cleanup. In delete retention mode that method attempts the release again; if that second release fails, existing worker cleanup failure reaches cleanupFailed and prevents the node retry. If the second release succeeds, the earlier cleanup failure no longer establishes a remaining resource leak. In retain mode provider.cleanup returns immediately. Thus a failed prepare and failed compensating delete can leave an unresolved namespace while cleanup is reported completed; normal retry rules may continue. Namespace identity hashes attemptId, so a subsequent successful attempt can have a different namespace while an earlier one remains. This is a source-reachable risk, not proof that a particular run leaked resources.

Controller finalizers and TTL expiry provide an independent reclamation route. They do not prove immediate deletion or bound cleanup while the API/controller is unavailable. Retain policy does not exempt the controller TTL path shown in expireLease.

## Smallest correction

Inside the existing prepare catch, await the same release operation and retain the same timeout and effect order. If release succeeds, rethrow the original activation error unchanged. If release rejects, throw AggregateError([activationError, releaseError], 'KUBERNETES_FIXTURE_PREPARE_CLEANUP_FAILED', {cause: activationError}). This makes both local causes available and ensures the cleanup-failure marker survives existing message-only IPC. Do not include raw kubectl output, Secret bytes or introduce an independent retry/release loop. Do not change scope of the existing guarded region as part of this narrow correction.

This correction repairs diagnosis and error propagation. By itself it does NOT mark WorkerCore cleanup failed, prohibit retry after retain-mode failure, or guarantee reclamation. Any requirement to fence retries on unresolved failed-prepare cleanup needs a separately reviewed path through the existing cleanup authority; it must not be falsely claimed from AggregateError alone. Keeping failed-prepare state in the provider and requiring release for failed execution despite retain mode is a possible follow-up, but its process/session recovery semantics require review before implementation.

## Focused regressions

Use the original local implementation fixture's real KubernetesFixtureCapabilityInvoker and valid manifest/registry arguments with its explicitly modeled kubectl execute seam. Record the exact command order and independent cleanup signal. Make activation fail after successful lease apply, then make delete reject with a distinct Error identity. Require the new stable aggregate marker and both exact causes; no resolved result or successful deployment output. A positive control makes delete succeed and requires the original activation Error identity unchanged. A cancellation variant verifies the release uses the existing independent nonaborted cleanup signal without extending its bound.

Add a genuine registered-provider/defaultRunner local process probe of the same modeled cluster seam: activation+delete failure must remain non-passed and expose the marker after actual capability IPC. This proves serialization and consumer visibility, not real Kubernetes deletion. Keep delete versus retain behavior explicit; if retry fencing is later implemented, require actual invocation counts and both attempt-derived lease identities instead of asserting that an aggregate implicitly disables retry.

The current implementation-contract deadline case returns successful delete output; it proves readiness timeout/budget behavior, not failed compensation visibility. The provider's current live-function module tests cleanup ok:false and ok:true through an injected context, but does not cover failed prepare plus failed compensation. Preserve those original cases and deadlines. No genuine cluster-writing live script is needed or authorized for this local regression.

Session-boundary correction to the possible follow-up above: provider-loader IsolatedLoadedProvider.cleanup explicitly starts a fresh ProviderProcessSession after termination and supplies the original invocation. A provider-local success flag therefore cannot safely distinguish successful retained fixtures from failed prepare during recovery. Do not implement that shortcut. The source snapshot and exact observation are in session-boundary-addendum.json. The narrowly recommended AggregateError propagation remains valid independently; preventing unsafe retries or changing retain cleanup must use an existing host/attempt authority or a separately reviewed explicit cleanup contract, with genuine separate execute/cleanup-session regression. This audit does not invent such an authority.
