# Buster fixture cleanup authority

The host tells a provider whether cleanup concerns an incomplete attempt or a completed fixture. This is execution authority, not an operator setting or a provider-local success flag.

`TestProviderInstance.cleanup(invocation, context, disposition)` receives `incomplete` or `completed-fixture`. Loaded providers validate the value before constructing a replacement session. The cleanup command uses `schemaVersion: provider-cleanup.v1` with an explicit disposition; missing, unknown or differently versioned commands reject before the child invokes plugin cleanup. Original invocation and pinned package identity remain unchanged. The SDK adds the required argument; existing providers may ignore the argument, but host call sites must supply it. The broader plugin manifest API remains pipeline-plugin-v2.

Ordinary failed-attempt cleanup and cleanup after a worker fault use incomplete authority. A successful provider response alone is insufficient: evidence/finalization or termination can still fail. Only the final retained-fixture path may supply completed-fixture, after checking fixture kind, completed/passed host result, no cleanup failure, and matching node/attempt/invocation identities. That path runs after dependent fixture consumers finish.

The Kubernetes provider honors retain only for completed-fixture. Incomplete attempts always request lease release. A failed preparation performs its existing bounded rollback with an independent cancellation controller. If rollback succeeds, the original preparation error is rethrown unchanged. If rollback also fails, KUBERNETES_FIXTURE_PREPARE_CLEANUP_FAILED carries both original local causes. Provider capability IPC retains the top-level error marker; it does not serialize nested AggregateError causes. Provider cleanup subsequently attempts release; failure enters the existing cleanup-failed path and blocks retry, including explicitly authorized unsafe retries. Successful retained fixtures stay retained; successful delete-mode fixtures are released.

A replacement provider process receives the host disposition explicitly. It cannot infer success from its own memory because execution may have occurred in a different process. This same-host session recovery is distinct from durable crash recovery of failed cleanup: the loader still disposes its package snapshot in its existing finally boundary. No durable cleanup retry ledger is added here.

Old immutable Kubernetes provider snapshots retain their old source behavior and cannot be repaired by merely supplying an extra argument. Historical cleanup safety requires a separate compatibility/ownership contract. This change does not rewrite snapshots, change grants, authorize cluster operations or claim that historical namespaces have been retired.

`npm run verify:buster:kubernetes-cleanup` includes the original child/ownership/plugin tests and local regressions through the real invoker, registered provider and Runner. Their injected CLI/OS failure boundaries must be reported explicitly; they are not live cluster or kernel-fault acceptance. Current execution/review status belongs to the accompanying remediation evidence, not this behavioral reference.
