# Buster test-provider configuration authority inventory

Status: authored source inventory, pending independent review. All 48 repository plugin manifests were enumerated; 15 packages declare 19 `testProviders` registrations, with 116 top-level properties, 211 property occurrences including nested/reference/conditional paths, and 22 schema-default occurrences. This is a bounded F1 source inventory, not provider execution, migration, image acceptance, live availability or complete CONFIG/F1 acceptance. No production source or runtime was changed or executed. Readiness remains privately staged and is not treated as integrated.

The machine-readable [mapping](../../evidence/config-testprovider-authority-20260921/mapping.json) records the complete roster, every registration's exact raw config schema, every named property (including nested arrays, local references and conditional branches), required membership, default locations, classification, declaration resolver and consumer module/source occurrences. Conditional requirements remain in their schema context; `requiredByContainingObject` is not a claim that every branch is unconditionally required. [Code authorities](../../evidence/config-testprovider-authority-20260921/code-authorities.json) retain source expressions and line numbers for fallbacks, bounds and runtime authors. Exact source copies are bound by the [manifest](../../evidence/config-testprovider-authority-20260921/source-identities-final.json). These named sources are not a complete executable dependency closure.

## Real configuration path and separate authorities

A test/fixture declaration (possibly a suite merge and matrix variation) supplies `config`. Nova's `resolveTestPlan`/`expandNodes` calls `resolveTestProviderConfiguration`. That function uses the registration's captured schema and `resolveReferencedValue`; the schema resolver clones the input and validates with AJV `useDefaults: true`. This is materially different from the previously inventoried ordinary adapter/observer validation path, which validates without inserting defaults. The resulting `provider-configuration.v1` contains contract ID, schema digest and resolved values. The resolved plan includes that configuration and its digest; Buster builds the provider invocation using `node.configuration`, not a read of today's central plugin file. Direct provider invocation can still encounter additional code fallbacks that normal schema resolution already fills.

All fields in these 19 config schemas currently belong to test/fixture declarations, acceptance criteria or requested budgets. None is read directly from a plugin-specific operator file. A schema `default` therefore does not by itself establish that the field is operator policy. For example, HTTP method GET, expected test results, a visual comparison profile and a deployment fixture's service port are semantic/request choices; image-wide allowed origins, scanner executable paths and maximum process budgets are operator/installation choices. Requested time/byte limits remain distinguishable from independently enforced Buster ceilings.

`ResolverPolicy` is a separate API input: default/maximum timeout, default/maximum execution limits, retry/matrix/node/concurrency bounds. The resolver validates it and applies it to nodes; the current repository search finds the exported resolver and callers/tests/examples, not a newly wired central operator file for this policy. Its code additionally supplies retry count 1 (0 for unsafe providers unless explicitly requested), blocking mode and manifest evidence defaults. Moving provider fields alone would not close this planning-policy author. The explicit example policy is a caller example, not evidence of a deployed operator setting.

Buster capability grants are a different mechanism from Nova adapter capability constraints. Runner grants select declared capability names by node ID or provider registration; missing required capabilities fail. Provider `context.invoke` checks that set, and the composite invoker routes only configured capabilities. The real service also validates the plan's registry/provider identities and capability subset. Provider configuration does not authorize access by itself. The capability invoker applies its own resource policy. Do not reuse the normal Nova adapter `allowedTargets`/`allowedExecutables` grant story for this different path.

## Actual image/runtime inflows and plugin overlap

The current Buster image entrypoint still writes runtime.json sections `directCommand`, `containerBuild`, `kubernetesFixture`, `tailscaleExposure`, `networkHttp`, `browserAxe`, `browserLighthouse`, `browserVisual`, `browserPlaywright`, `securityScan`, `kubernetesRuntimeSecurity`. Production decoders pass them into the actual service/capability runtime. These are genuine additional authors beyond the test config schemas:

- Direct command: executable catalog, executable search path and runtime read roots, output 16 MiB, execution/CPU 900000 ms, 128 tasks, 4 GiB memory and termination grace. Catalog and protected environment boundaries are not permission to run arbitrary request paths.
- Build: fixed buildctl installation path, BUILDKIT_HOST, generated registry-client configuration, linux/amd64/arm64 allowlist, allowed NODE_ENV argument, 8 MiB log, 900000 ms execution and 16 MiB manifest ceilings.
- Kubernetes fixture/exposure: actual kubectl path, controller namespace, lease API identity, namespace prefix allowlist, source secret reference allowlist, resource/PVC budgets, retention ceiling, 900000 ms deadline and 1000 ms polling. Exposure adds permitted `.ts.net` suffix; API/service credentials remain external.
- Network: exact origins from environment, allowed suffixes/ports, optional WebSocket boolean, 1 MiB request, 16 MiB response and 120000 ms execution. These do not become valid merely because a provider schema accepts an URL.
- Browser runtimes: exact allowed origins, executable/module/browser paths, allowed browsers/ports, read-only roots, real run-as 1001/1000 and external cgroup path, concurrency/combination/run/worker limits, process/CPU/memory/output/result/artifact/screenshot/mask budgets. The full captured entrypoint expressions retain their exact values. Installation paths and security identities need their own classification rather than wholesale conversion into arbitrary operator overrides.
- Scanner: registry client input, Trivy executable/cache directory, allowed registry prefixes, 900000 ms / 64 MiB, database freshness 48 hours (vulnerability) and 7 days (Java), database bytes 8 GiB. Runtime Kubernetes inspection uses 300000 ms, 16 MiB output, 1000 ms polling and 10000 ms observation freshness.

The entrypoint additionally supplies service stores, network bind/auth references, source authority, allowed capabilities and dependency readiness. Readiness has a separate private migration; it remains an actual live-source author at this checkpoint. Existing central `buster-engine.config.json` owns preparation/admission; `worker-core.config.json` owns local runtime policy. Those accepted slices do not imply that provider ceilings have migrated. The Buster-generated platform discovery object has empty adapters/observers/grants/providers; it must not be mistaken for a second complete Nova orchestrator or a provider-policy file already authorizing these capabilities.

Common plugins named command-runner, network-http or runtime-dispatch are distinct implementations/registrations from these Buster capability invokers. A shared capability spelling is not proof they consume the same central config. A future coherent Buster capability-policy owner should supply these ceilings once, referenced from the Buster role's configuration; keep per-test declarations and immutable effective plans separate. Avoid duplicating every provider request field into 15 new operator files. The five security registrations can share one explicitly versioned acceptance-policy owner only if that is an intended product contract, while their execution caps stay with the actual runtime owner.

These provider JS sources do not directly spawn executables or read process.env; they invoke capabilities or perform local artifact/profile reads. Runtime implementations do launch tools and set environment. Repository-relative config files are resolved inside the invocation repository/workspace with provider-specific containment checks; artifact file URLs carry recorded size/digest checks. Generated installation/runtime-root paths resolve through production decoders. These path domains and external secret references must not be merged into one generic config-relative root.

## Migration and DOC acceptance criteria

1. Review all 48 roster entries and all 19 registration mappings against exact schemas; retain conditional defaults and nested required scopes. Distinguish the test declaration, schema default resolution, provider fallback, resolver policy, runtime ceiling and installation/credential authority for each proposed move. A captured expression is source evidence, not an endorsement to expose every numeric literal as an operator setting.
2. First migrate the real Buster runtime policy author to an explicit role-owned central file/reference and required decoder. Preserve bounds, grant/capability checks and disabled-capability behavior; reject old runtime/env authors even for equal or empty inputs. Carry actual policy values through the service to each invoker, not only a loader test. No replacement default in schema/testhelper/entrypoint.
3. Make the ResolverPolicy author explicit at its real callers separately. Preserve resolved effective provider configuration, schema/package/plan identity and original evidence semantics. Old plans with historically omitted code-level defaults need original producer semantics or an explicit versioned migration; never normalize retained plans or receipts using today's config. Removing request defaults can be a contract-version change, not merely a deployment change.
4. Require two profiles and meaningful negative/mutant consumer tests for each moved operator budget, resource allowlist, executable/secret reference and timeout. Preserve complete original provider/resolver/remote contract assertions and deadlines. Actual external BuildKit, Kubernetes, Tailscale, browser and Trivy behavior requires those environments; local stub/provider tests cannot claim live availability or isolation.
5. Update central operator tables and plugin/provider READMEs with separate request fields, effective-default provenance, ceilings/units, path bases, optional linked-input alternatives, credentials, failure behavior, rollout/restart and retained-history compatibility. Keep schema/property coverage and source bindings current. A whole F1 or CONFIG closure requires the remaining plugin, report-adapter, runner, environment and deployment author scopes; this document closes none of them by assertion.
