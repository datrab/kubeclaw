# Namespace broker and fixture boundaries

Implemented 2026-09-09 for PCR-BUSTER-NS-001/002/003, IFR-18-001 and PCR-KUBERNETES-FIXTURE-001. Independently reviewed and locally retested; live-cluster gates remain open. Historical findings remain unchanged.

The controller now reads the mounted ServiceAccount token for every HTTP request. Missing/empty input fails explicitly; no cached-token fallback is used. Namespace ownership, legacy ownership and deletion compare the same canonical lease label written by provisioning, while retaining the full Kubernetes lease UID check for current leases.

Runtime security inventory derives the allowed RoleBinding authorities from configured controller role names and the validated lease subjects. Credential reader/writer Role and RoleBinding objects share the exact builder used by provisioning. Inventory compares namespace, kind, name, roleRef, subjects and rules, rather than exempting an object by name; it verifies the namespace's lease ownership before accepting its snapshot. Referenced ClusterRole authority continues to come from the trusted installed chart. This change does not add cluster-wide RBAC authority to the controller.

The fixture parser limits parse depth to 64 and parser nodes to 100,000 through the actual js-yaml listener, before recursive parsing can exhaust the stack. Iterative traversal detects cycles, limits expanded object visits and pending work, and caps repeated shared-object visits after parsing at 1,000. List flattening is iterative and checks the configured resource count before adding each resource. Legitimate small shared aliases remain supported. Manifest bytes remain subject to the original authenticated file/digest/size boundary. The existing js-yaml declaration now describes its real options argument and iterator return type; no parser replacement or implementation shim is used.

## Admission ownership and upgrade

The broker Helm chart now renders its namespace fence and binding from the same release namespace, account fullname and allowed prefixes as the controller. Each installation gets a distinct policy name. The existing direct-Buster namespace prohibition is preserved. Kubernetes versions below 1.30 fail template rendering; clusters must serve `admissionregistration.k8s.io/v1` ValidatingAdmissionPolicy and have that admission facility enabled. Missing API support is an installation failure, not a permitted fallback. `failurePolicy: Fail` and binding action `Deny` are retained.

Infrastructure bootstrap no longer applies the hard-coded legacy `buster-namespace-fence`. The old file and explicit cleanup path remain for installed-resource migration. For an existing installation, render and install the chart policy first, then verify its admission behavior with the actual alternate controller identity before explicitly removing the legacy policy/binding. An existing legacy policy can continue denying non-`test` prefixes until removed. There is no claim that removing the old policy before validating the new one is safe. No policy, chart or deployment was applied during this work.

## Local evidence and limits

- `go test -race ./cmd/buster-namespace-controller` passes, including all original tests. New tests use the original HTTP client, expiry and provisioning paths against local HTTP endpoints: atomic token-file rotation; 63/64/253-character lease names; same-UID expiry deletion and different-UID refusal; and configured RBAC plus both credential modes. Inventory GET responses contain the objects emitted by actual provisioning POSTs. Changed subjects, roleRef and rules remain findings.
- The original fixture invoker rejects real cycle, deeply nested List, shared alias DAG and excess-resource YAML files in a separate Node process limited to a 128 MiB heap and 15 seconds. It uses the installed kubectl executable with no replacement executor; these cases fail before kubectl execution. A positive test preserves ordinary alias content.
- Helm renders for default and alternate namespaces pass identity/RBAC/prefix/binding assertions; Kubernetes 1.29 is rejected. This is rendered-manifest evidence, not API-server CEL execution or admission enforcement proof.
- Original fixture implementation, parity and provider tests pass. Their historical `mocks:0` output is not treated as live-cluster evidence: original tests contain injected command responses and source assertions.
- Plugin-runtime TypeScript check, new parser/test canonical ESLint checks, shell syntax and scoped whitespace checks pass. Linting the pre-existing fixture runtime with its owning project explicitly selected reports existing structural/environment-rule debt (complexity, function/file size, depth, parameters and environment access). No lint suppressions or policy changes were introduced; that file is not claimed lint-clean. The default ESLint project service cannot discover this engine directory's owning tsconfig.

No cluster, CNI, token issuer, live RBAC/admission, rolling-upgrade or external provider behavior was proven. No CI/deployment, substituted compiler, or successful-cluster stand-in was used. Targeted local commands encountered no kernel `/proc` or cgroup blocker.
