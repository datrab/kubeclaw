# PCR-PRISM-CONTROL-002 — atomic direction decisions and preference wire IDs

Status: source fix with real PGlite SQL regression evidence; native pooled PostgreSQL and actual control HTTP proof remain unverified. No deployment or external migration was run.

The old direction routes wrote direction state through `pool.query` before inserting an `event-…` wire ID into a UUID primary key. Both selection and rejection therefore left committed state behind when the event insert failed. Migration 011 retains the existing UUID primary key and content, adds a unique text wire ID, and keeps replay metadata in separate nullable columns. Historical content.eventId values are retained; rows without that field retain their existing UUID identity as text. Duplicate historical wire IDs make the migration fail visibly and transactionally. No actor, event, or successful decision receipt is invented for historical partial state.

New preference writes allocate internal UUIDs independently. Explicit event IDs replay only matching JSON content, subject and actual project binding; conflicting reuse fails. Direction mutations require an explicit bounded Idempotency-Key. The actor and key identify the event, while the operation, direction and submitted payload bind its request digest. The transaction reserves one existing Database connection, locks the wire identity, returns an existing matching receipt before inspecting changed state, and otherwise locks the project and direction. Selection also locks its source document while checking the current revision. State changes, event insertion and the exact response receipt commit together. A source outside the active design request cannot silently record a successful selection. Existing partial historical selections remain visible and cannot obtain invented receipts.

Studio keeps a pending key per route and exact body in the mounted component. Transport failures and rejected/invalid responses retain that key for retry; accepted validated responses clear it, allowing a later intentional identical feedback action to receive a fresh key. This in-memory retry scope does not survive browser reload. The actual production E2E selection caller now also supplies a key. No implicit body-hash fallback or compatibility path was added.

Before evidence: the original checked-in route bodies were extracted using Node's native TypeScript stripping and executed against real PGlite SQL with the original preference table columns. HTTP request/response plumbing was supplied locally; this was not an HTTP or pg.Pool test. Rejection raised `invalid input syntax for type uuid: event-…`, leaving states `[rejected, proposed, proposed]` and zero events. Selection raised the same error, leaving `[selected, rejected, rejected]` and zero events. The original route body and repository SQL were unchanged in that probe.

After evidence:

- `node --test skills/prism/tests/control-decisions.test.mts skills/prism/tests/control.test.mts skills/prism/tests/preferences.test.mts skills/prism/tests/storage.test.mts`: 11 tests pass. Five new SQL cases cover selection and rejection rollback after real trigger failures, committed-response replay, conflicting key reuse, all four feedback actions, fresh identical intent, stale source revisions, historical partial state, UUID/wire separation, preference owner/content/project conflicts, retraction references, migration preservation and visible duplicate-wire failure.
- `npm run typecheck --prefix skills/prism`: passes.
- `npm run build:studio --prefix skills/prism`: passes, with the existing bundle-size warning.
- Canonical ESLint on both new control helpers and the new test passes.

The same root-only UID namespace limitation documented in prism-corpus.md prevents native PostgreSQL initdb here despite a real PostgreSQL 17.5 and pgvector 0.8.0 build. PGlite evidence does not establish multi-connection lock scheduling, real HTTP lost-ACK behavior, or deployed migration behavior. Those remain required native integration evidence before claiming full finding closure.

Integration follow-up: the production Studio proxy's explicit request-header allowlist dropped the new mandatory `Idempotency-Key`, so browser direction mutations could not reach Control with their retry identity. `server/studio-request.ts` now forwards that header. A regression in `tests/studio-service.test.mts` spawns the actual Studio server and sends selection and feedback POST requests, including retries, to a real loopback HTTP upstream. It checks the exact key, route, method, body, cookie and CSRF token, and verifies that the proxy still replaces an untrusted client ingress secret with its configured secret. Before the fix this regression failed because the upstream key was absent; after the fix it passes. This establishes actual Studio HTTP forwarding, not a native Control/PostgreSQL or lost-ACK integration proof.

Follow-up verification: the previous four control/preference/storage test files plus `studio-service.test.mts` and `studio-proxy.test.mts` pass 19/19 tests, with no skipped tests. Prism typecheck passes. Canonical ESLint passes for the two new control helpers, control-decisions test, Studio proxy implementation and Studio service test. No worker changes were included in this follow-up.
