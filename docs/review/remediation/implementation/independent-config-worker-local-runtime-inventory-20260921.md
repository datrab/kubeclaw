# Independent source review: LocalWorkerRuntime configuration inventory

Status: bounded inventory and LC1–LC5/LC-DOC direction accepted. This is a read-only source review, not an implementation or runtime acceptance. The reviewer did not author the inventory. All eight source snapshots match their recorded digests, sizes and current files; the [independent comparison](../../evidence/independent-config-worker-local-runtime-inventory-20260921/source-check.json) records that binding. No tests, host operations or production edits were performed.

The three constructor fallbacks and bounds are accurately reported: drain 300,000 ms and cancellation 30,000 ms each require safe integers from 1 through 2,147,483,647; replay 65,536 requires a safe integer from 1 through 1,000,000. `runAttempt` reclaims expired inactive accepted identities before duplicate/replay-capacity checks. The ledger is an in-memory instance field: in the observed Buster path a new runner/runtime is created per prepared job. The replay limit is therefore per runtime instance, not a new service-wide durable quota. Migration must retain that lifetime and scope.

The actual default production chain is `production.ts::configuredService` → `BusterRemotePlanService` → `executeBusterPreparedJob` → `runPlan` → `TestPlanRunner` → `LocalWorkerRuntime`. The runner supplies concurrency and clock, omits all three policy fields, marks the runtime ready and later calls only `runAttempt`. The explicit alternate executor/runtime seams do not prove this default path and must not be used to bypass the future production replay test.

The no-drain distinction is confirmed by the complete private runtime field use and runner interface, not merely by an absent text match. `WorkerAttemptRuntime` exposes only `runAttempt`; runner finalization calls fixture cleanup. Remote service shutdown separately aborts job controllers and waits for submitted/executing operations with its own supplied timeout. The executor combines that external signal with the local worker signal. Provider capability `drain()` and native launcher drain are different objects and do not constitute a LocalWorkerRuntime drain call. Forwarding the two Core timeout settings must not silently add a new Buster shutdown lifecycle or claim to control its existing shutdown timer.

The proposed single `worker-core.config.json` local-runtime owner is consistent with D17 if delivered through the existing full bundle and passed as one validated immutable policy into Core. Existing per-job concurrency and host pool capacity remain their distinct existing authorities. Required options, two real profiles, preserved original assertions/deadlines, all three fallback mutants, and a genuine default production replay consumer test make the LC criteria suitable. Core drain/cancellation tests must remain separately identified from Buster lifecycle behavior.

The inventory correctly leaves Buster evidence/admission-store quotas and readiness fallbacks open. The review does not approve implementation details that have not yet been written, does not classify every Core constant, and does not close the full CONFIG finding. Operator documentation should retain the per-runtime replay scope and the no-production-drain distinction when this slice is implemented.
