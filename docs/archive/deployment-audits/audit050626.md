# KubeClaw Deployment Audit - 2026-06-05

Senior production readiness, reliability, and security review of the current KubeClaw deployment surface.

Archive note: this file is historical source material, not the public deployment entry point. Current public docs live under `docs/deployment/**`, `docs/architecture/**`, `docs/operators/**`, and `docs/reference/**`.

Reviewed from repository files and rendered manifests:

- Helm chart: `charts/kubeclaw`
- Production values: `my-values/nova-values.yaml`, `my-values/buster-values.yaml`
- Infra values/manifests: `my-values/infra/*`

The existing deployment verifier passed, including kubeconform validation for rendered Nova and Buster manifests. Local live-cluster checks were not run because `kubectl` was not installed in the audit shell.

## Architecture Map

KubeClaw is deployed as one namespace-local swarm with shared infra and two persistent agent releases:

- Nova release `agent-nova`
  - Helm Deployment from `charts/kubeclaw/templates/deployment.yaml`
  - OpenClaw gateway on port `18789`
  - Optional bridge port `18790`
  - Prism preview sidecar serving workspace designs on port `3456`
  - NodePorts configured in `my-values/nova-values.yaml`
  - Persistent config PVC and workspace PVC from `charts/kubeclaw/templates/pvc.yaml`
  - Init container clones `ForgeStack`, copies first-run workspace files, writes OpenClaw config, writes swarm config, and merges packaged skills with optional custom skills

- Buster release `agent-buster`
  - Helm Deployment from `charts/kubeclaw/templates/deployment.yaml`
  - Sandbox image with privileged Podman-in-Pod
  - Same main container starts both `node /app/skills/buster-pipeline.ts` and `node /app/openclaw.mjs gateway`
  - Redis-backed task/completion flow
  - Kubernetes API access via `agent-buster` ServiceAccount, ClusterRole, and ClusterRoleBinding
  - Podman storage on `emptyDir` at `/var/lib/containers`
  - Sandbox workspace on `emptyDir` at `/sandbox`
  - Registry config points Podman at `registry-local` and `registry-mirror`

- Shared infrastructure
  - Redis: Bitnami standalone chart, `my-values/infra/redis-values.yaml`
  - PostgreSQL: Bitnami standalone chart for LiteLLM state, `my-values/infra/postgresql-values.yaml`
  - Qdrant: single StatefulSet from Qdrant Helm chart, `my-values/infra/qdrant-values.yaml`
  - LiteLLM: raw Deployment/Service, `my-values/infra/litellm-deployment.yaml`, config from `my-values/infra/litellm-config.yaml`
  - Registry mirror: pull-through Docker Hub cache, `my-values/infra/registry-mirror.yaml`
  - Registry local: writable test image registry, `my-values/infra/registry-local.yaml`
  - Buster namespace fence: ValidatingAdmissionPolicy for namespace create/delete only, `my-values/infra/buster-namespace-fence.yaml`

## Action Plan

The plan is sorted so each layer reduces risk for the next. Do not start by polishing probes or CI before Buster's privilege boundary and exposed control planes are contained.

### 1. Contain Buster's Kubernetes Authority

Severity: Critical

What:

Buster has a privileged container and a mounted ServiceAccount token with broad cluster-scoped permissions. The current namespace fence only restricts namespace create/delete names. It does not prevent Buster from mutating secrets, pods, exec, PVCs, services, configmaps, or serviceaccounts in existing non-test namespaces.

Where:

- `charts/kubeclaw/templates/rbac.yaml:14-30`
- `charts/kubeclaw/templates/rbac.yaml:39-52`
- `charts/kubeclaw/templates/serviceaccount.yaml:9`
- `charts/kubeclaw/templates/deployment.yaml:379-395`
- `my-values/infra/buster-namespace-fence.yaml:19-33`

Why:

This is the strongest tenant/isolation failure mode. If Buster or anything inside its privileged sandbox is compromised, it can use the ServiceAccount token to operate outside intended test namespaces. The current VAP protects production namespaces from deletion by name, but not resource writes inside already-existing namespaces.

Recommended solution:

- Replace the broad ClusterRole with the smallest possible bootstrap authority.
- Prefer a controller-style flow:
  - Buster may create only test namespaces with approved prefixes.
  - A separate trusted controller creates namespace-scoped Roles and RoleBindings inside each test namespace.
  - Buster receives only namespaced permissions inside those ephemeral namespaces.
- If a controller is too heavy for the first fix, add ValidatingAdmissionPolicy coverage for all Buster CREATE, UPDATE, PATCH, DELETE operations on namespaced resources and require namespace names to match `buster-*` or `test-*`.
- Remove unnecessary verbs and resources from the ClusterRole, especially `secrets`, `serviceaccounts`, `pods/exec`, and broad `patch/update` where not needed.
- Keep `automountServiceAccountToken` disabled unless the pod is explicitly in Kubernetes-test mode.

Verification:

```bash
kubectl auth can-i create secrets -n kubeclaw \
  --as=system:serviceaccount:kubeclaw:agent-buster

kubectl auth can-i patch deployments -n kube-system \
  --as=system:serviceaccount:kubeclaw:agent-buster

kubectl auth can-i create pods -n test-example \
  --as=system:serviceaccount:kubeclaw:agent-buster
```

Expected result: production namespace checks return `no`; approved test namespace checks return only the exact verbs required by Buster suites.

### 2. Close Public NodePort Exposure

Severity: Critical

What:

Multiple sensitive services are exposed through NodePorts: Nova gateway, Buster gateway, Prism preview, LiteLLM, and writable registry-local.

Where:

- `charts/kubeclaw/values.yaml:190-198`
- `charts/kubeclaw/templates/service.yaml:1-34`
- `my-values/nova-values.yaml:48-54`
- `my-values/buster-values.yaml:68-69`
- `my-values/infra/litellm-deployment.yaml:75-82`
- `my-values/infra/registry-local.yaml:53-58`

Why:

NodePorts expose control planes and write surfaces at the node network boundary. The gateway is token-protected, but token exposure, browser-origin fallback behavior, or network reachability mistakes can turn this into direct operator-control access. Registry-local is writable and intentionally insecure for local pulls; exposing it broadly creates image injection risk.

Recommended solution:

- Make all default service types `ClusterIP`.
- Add explicit values such as `exposure.mode: clusterip | tailscale | ingress | nodeport-breakglass`.
- Require a separate `*-local-exposure.yaml` override for NodePorts.
- Protect LiteLLM and gateways behind a single authenticated ingress or Tailscale serve path.
- Keep registry-local reachable only from the cluster and the node-local container runtime path needed by k3s.
- Add NetworkPolicies limiting gateway/LiteLLM/registry-local sources.

Verification:

```bash
helm template agent-nova charts/kubeclaw -n kubeclaw -f my-values/nova-values.yaml \
  | rg -n "type: NodePort|nodePort:"

helm template agent-buster charts/kubeclaw -n kubeclaw -f my-values/buster-values.yaml \
  | rg -n "type: NodePort|nodePort:"

rg -n "type: NodePort|nodePort:" my-values/infra
```

Expected result: no NodePorts in production values unless using an explicit break-glass exposure file.

### 3. Stop Persisting Runtime Secrets Into PVC Config

Severity: High

What:

Init writes `openclaw.json` to the persistent config PVC on first start, then replaces `__LITELLM_API_KEY__` and `__DISCORD_TOKEN__` with literal secret values. The config PVC is retained across Helm uninstall.

Where:

- `charts/kubeclaw/templates/deployment.yaml:136-148`
- `charts/kubeclaw/templates/deployment.yaml:151-162`
- `charts/kubeclaw/templates/pvc.yaml:8-9`
- `charts/kubeclaw/templates/pvc.yaml:30-31`
- `charts/kubeclaw/values.yaml:304-307`

Why:

Secret rotation cannot be trusted if old values are embedded in retained PVC files. Config drift also means Helm changes to `openclaw.json`, `swarm.config.json`, `.semgrep.yml`, or `eslint.config.mjs` may not apply to existing deployments unless override flags are manually set.

Recommended solution:

- Keep secret references in config as env-backed references, not literal values.
- Render a runtime-only config into `emptyDir` or memory-backed volume at pod start.
- Keep mutable user config separate from chart-owned config.
- Add explicit config schema/migration steps for retained PVC state.
- Add a checksum or version marker and fail startup when retained config is too old to migrate safely.

Verification:

```bash
kubectl exec -n kubeclaw deployment/agent-nova -c kubeclaw -- \
  sh -c 'grep -R "__LITELLM_API_KEY__\\|litellmApiKey\\|discordToken" -n /home/node/.openclaw || true'
```

Expected result: no literal API keys or Discord tokens in PVC-backed files.

### 4. Replace TCP-Only Agent Probes With Dependency-Aware Health

Severity: High

What:

Agent readiness and liveness only check whether TCP port `18789` accepts connections. This does not prove OpenClaw auth works, Redis is connected, Qdrant is usable, LiteLLM is reachable, or Buster's pipeline loop is healthy.

Where:

- `charts/kubeclaw/templates/deployment.yaml:403-417`
- `charts/kubeclaw/values.yaml:244-256`
- `scripts/deploy.sh:445-451`

Why:

A pod can be Ready while the pipeline silently cannot dispatch Buster tasks, persist memory, call models, or perform completions. Kubernetes would route traffic and operators would see green status even though the deployment is degraded.

Recommended solution:

- Add a gateway health endpoint or command that checks:
  - gateway auth with `OPENCLAW_GATEWAY_TOKEN`
  - Redis ping/auth
  - Qdrant `/readyz`
  - LiteLLM `/health` or model-list call
  - Buster pipeline heartbeat file/endpoint
- Use `startupProbe` for slow first boot and dependency warmup.
- Keep `readinessProbe` strict for serving traffic.
- Keep `livenessProbe` conservative so transient dependency outages do not cause crash loops.

Verification:

```bash
kubectl exec -n kubeclaw deployment/agent-buster -c kubeclaw -- openclaw gateway status
kubectl exec -n kubeclaw deployment/agent-buster -c kubeclaw -- redis-cli -h "$REDIS_HOST" -a "$REDIS_PASSWORD" ping
kubectl exec -n kubeclaw deployment/agent-buster -c kubeclaw -- curl -fsS "$QDRANT_URL/readyz"
kubectl exec -n kubeclaw deployment/agent-buster -c kubeclaw -- curl -fsS "$LITELLM_URL/health"
```

Expected result: readiness fails when any required dependency is unavailable.

### 5. Supervise Buster Pipeline And Gateway Separately

Severity: High

What:

Buster starts two long-running processes in one shell and exits `1` when either exits. TCP probes observe only the gateway port. A hung Buster pipeline can remain Ready, while a normal child exit forces the whole pod to restart.

Where:

- `my-values/buster-values.yaml:15-28`
- Rendered from `charts/kubeclaw/templates/deployment.yaml:276`

Why:

Buster is a persistent task worker. Its failure mode must be clear: gateway alive but worker dead is a serious degraded state, not healthy. Restart behavior should distinguish expected shutdown, worker crash, gateway crash, and dependency backoff.

Recommended solution:

- Prefer separate containers in one pod:
  - `gateway`
  - `buster-pipeline`
- Or use a small supervisor that tracks both process health and exits with meaningful codes.
- Add Buster pipeline heartbeat/health file and readiness check.
- Emit termination logs for which child exited and why.

Verification:

```bash
kubectl exec -n kubeclaw deployment/agent-buster -c kubeclaw -- pkill -f buster-pipeline.ts
kubectl get pod -n kubeclaw -l app.kubernetes.io/instance=agent-buster -w
kubectl describe pod -n kubeclaw -l app.kubernetes.io/instance=agent-buster
```

Expected result: pod becomes NotReady or restarts with a clear termination reason.

### 6. Pin Runtime Images And Tooling

Severity: High

What:

Production images and base images use mutable tags. Some build installs can fail while the image still succeeds.

Where:

- `docker/Dockerfile.general:4`
- `docker/Dockerfile.sandbox:5`
- `docker/Dockerfile.sandbox:38-50`
- `my-values/nova-values.yaml:8-11`
- `my-values/buster-values.yaml:30-33`
- `charts/kubeclaw/values.yaml:23-29`
- `my-values/infra/litellm-deployment.yaml:27`
- `.github/workflows/build-images.yaml:87-105`

Why:

The same Git commit can deploy different runtime bytes depending on when it is built or pulled. `npm install ... || true` can hide missing browser/test tools until Buster fails at runtime.

Recommended solution:

- Pin all production images by digest.
- Use immutable app image tags for Helm values, ideally commit SHA tags.
- Fail Docker builds on install failures.
- Pin npm and pip package versions where they affect runtime behavior.
- Generate SBOM/provenance for GHCR images.
- Add CI verification that rendered production manifests do not include `latest`, `main-latest`, or unpinned raw images.

Verification:

```bash
rg -n "latest|main-latest|\\|\\| true" docker my-values charts .github
```

Expected result: no mutable production image tags and no swallowed install failures.

### 7. Add NetworkPolicies For The Full Namespace

Severity: Medium

What:

Redis and PostgreSQL render NetworkPolicies, but their ingress allows any pod to connect to the service port. Qdrant, LiteLLM, registry-local, registry-mirror, and agent gateways do not have local NetworkPolicy coverage in this repo.

Where:

- `my-values/infra/redis-values.yaml:1-11`
- `my-values/infra/postgresql-values.yaml:1-13`
- `my-values/infra/qdrant-values.yaml:1-6`
- `my-values/infra/litellm-deployment.yaml:7-82`
- `my-values/infra/registry-local.yaml:12-58`
- `my-values/infra/registry-mirror.yaml:24-90`
- `charts/kubeclaw/templates/service.yaml:1-34`

Why:

Credentialed services are still too reachable inside the namespace or cluster. If one workload is compromised, lateral movement to Redis, LiteLLM, Qdrant, or registry-local is unnecessarily easy.

Recommended solution:

- Add default deny ingress/egress for the `kubeclaw` namespace.
- Allow only:
  - Nova/Buster to Redis
  - Nova/Buster to Qdrant
  - Nova/Buster to LiteLLM
  - Buster to registry-local and registry-mirror
  - Operator ingress/Tailscale path to gateway if explicitly enabled
- Keep DNS egress open only to kube-dns.

Verification:

```bash
kubectl run np-deny-test -n kubeclaw --rm -it --image=curlimages/curl -- \
  curl -fsS http://redis-master.kubeclaw.svc.cluster.local:6379
```

Expected result: unrelated pods cannot reach protected services.

### 8. Make Infra Rollout Failures Explicit

Severity: Medium

What:

The deploy script treats several infra rollout failures as warnings and continues.

Where:

- `scripts/deploy.sh:87-98`
- `scripts/deploy.sh:271-294`

Why:

This can produce a deployment that appears complete while LiteLLM, registry mirror, or registry-local is not actually ready. Later agent failures then look like pipeline issues instead of infra readiness issues.

Recommended solution:

- Split infra into required and optional components.
- Fail hard on required components for production: Redis, PostgreSQL, Qdrant, LiteLLM, registry-local if Buster Kubernetes suite is enabled.
- Allow warning-only behavior only behind `ALLOW_PARTIAL_INFRA=1`.
- Add a final dependency matrix check before deploying agents.

Verification:

```bash
./scripts/deploy.sh infra
./scripts/deploy.sh smoke
```

Expected result: `infra` exits nonzero when a required dependency is not ready.

### 9. Harden Registry-Local And k3s Pull Path

Severity: Medium

What:

Buster pushes test images to a writable, unauthenticated registry-local, exposed on NodePort `30051`. k3s host registry config maps the cluster service name to `127.0.0.1:30051`.

Where:

- `my-values/infra/registry-local.yaml:1-10`
- `my-values/infra/registry-local.yaml:53-58`
- `my-values/infra/k3s-registries.yaml:7-19`
- `my-values/buster-values.yaml:71-83`
- `scripts/deploy.sh:230-244`
- `scripts/deploy.sh:377-418`

Why:

The registry is intentionally insecure to support local verification. If exposed beyond the node-local path, it can be used to inject images into test runs. If k3s registry config is missing, Buster Kubernetes tests fail at image pull time.

Recommended solution:

- Keep registry-local ClusterIP for in-cluster clients.
- For k3s host pulls, use a tightly firewalled host-local endpoint or documented port-forward flow.
- Add a preflight that proves containerd can pull from `registry-local.kubeclaw.svc.cluster.local:5001`.
- Add garbage collection/cleanup for registry-local images.

Verification:

```bash
crictl pull registry-local.kubeclaw.svc.cluster.local:5001/kubeclaw-smoke:latest
kubectl run registry-deny-test -n default --rm -it --image=curlimages/curl -- \
  curl -fsS http://<node-ip>:30051/v2/
```

Expected result: node-local pull path works; broad network access is denied.

### 10. Bound Sandbox Storage And Recovery

Severity: Medium

What:

Buster uses `emptyDir` for Podman storage and sandbox workspace. Podman uses `vfs`, which can grow quickly during image builds.

Where:

- `charts/kubeclaw/templates/deployment.yaml:352-364`
- `charts/kubeclaw/templates/deployment.yaml:468-480`
- `charts/kubeclaw/values.yaml:265-268`
- `docker/Dockerfile.sandbox:20-26`

Why:

Image-heavy test runs can exhaust node ephemeral storage or lose cached test state after restart. Recovery behavior is not explicit beyond pod restart.

Recommended solution:

- Add explicit `ephemeral-storage` requests/limits to Buster resources.
- Add sandbox cleanup after each task and on startup.
- Record disk usage in Buster telemetry.
- Consider a dedicated PVC/cache only if test runtime cost justifies it.

Verification:

```bash
kubectl exec -n kubeclaw deployment/agent-buster -c kubeclaw -- df -h /var/lib/containers /sandbox
kubectl exec -n kubeclaw deployment/agent-buster -c kubeclaw -- sandbox-cleanup
```

Expected result: storage use is bounded and cleanup is observable.

### 11. Fix Deployment Context Hygiene

Severity: Medium

What:

There is no `.dockerignore`, while `my-values/*` is tracked and contains personal deployment IDs and project-specific infrastructure references. `scripts/setup.sh` still says `my-values/` should stay private.

Where:

- `.gitignore:1-35`
- `scripts/setup.sh:49-55`
- `my-values/nova-values.yaml`
- `my-values/buster-values.yaml`
- `my-values/infra/litellm-config.yaml:5-38`
- Docker build context in `scripts/deploy.sh:190-199`

Why:

Docker builds may send unnecessary deployment values and personal config to the build context. The repository also mixes example values, personal production values, and audited deploy surfaces without a clear boundary.

Recommended solution:

- Add `.dockerignore` excluding `my-values`, `.swarm`, logs, local caches, and secrets.
- Rename personal production values to an ignored location, or convert them into sanitized examples.
- Update `scripts/setup.sh` comments to match the real repository policy.
- Add a verifier that fails if private-looking values are tracked.

Verification:

```bash
git ls-files my-values
docker build --no-cache -f docker/Dockerfile.general -t kubeclaw-context-check .
```

Expected result: private deployment values are either intentionally sanitized examples or excluded from Docker context.

### 12. Expand Deployment Verification

Severity: Medium

What:

The current verifier is useful and passed, but it mostly asserts rendered agent chart shape and recent Buster startup fixes. It does not yet verify the main production failure modes above.

Where:

- `tests/verification/deployment/check-deployment-truth.mjs`
- `tests/verification/deployment/README.md`
- `scripts/deploy.sh:435-460`

Why:

The deployment can be schema-valid and still be unsafe, overexposed, drifted, or dependency-degraded. Verification should prevent regressions in the exact areas most likely to break production recovery.

Recommended solution:

Add checks for:

- Buster RBAC negative permissions.
- No production NodePorts unless explicit break-glass values are used.
- Rendered infra charts for Redis, PostgreSQL, Qdrant, LiteLLM, registry-local, registry-mirror.
- NetworkPolicy presence and expected selectors.
- No mutable tags in production manifests.
- Pre-seeded PVC config migration.
- Secret rotation does not leave literal old tokens in PVC files.
- Dependency outage readiness behavior.
- Buster pipeline/gateway child-process failure behavior.
- registry-local push/pull preflight.

Verification:

```bash
node tests/verification/deployment/check-deployment-truth.mjs --source-root "$PWD"
./scripts/deploy.sh verify-live
```

Expected result: local render checks catch unsafe manifests before cluster deploy; live verification catches runtime dependency and recovery failures.

## Residual Risk Until Fixed

Until the first two plan items are implemented, treat the deployment as suitable for a trusted local cluster only. Do not assume tenant isolation, do not expose NodePorts to untrusted networks, and do not run Buster against repositories or workloads where privileged Kubernetes access would be unacceptable.
