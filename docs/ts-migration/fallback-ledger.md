# Fallback, Compatibility, and Shim Ledger

Purpose: capture every `legacy`, `compat`, `fallback`, `shim`, compatibility projection, alternate status reader, and old-shape adapter discovered during Phase 0.

Each finding must receive one decision:

- delete during migration
- rename as canonical default
- keep as external adapter only
- needs user decision

## Resolution policy

Default stance: **delete or strictify legacy compatibility unless the entry proves it is intentional modern behavior**.

The ledger was produced during discovery. Existing decisions such as `rename as canonical behavior`, `rename as canonical default`, or `keep external adapter only` are not blanket approvals to preserve old behavior. During migration, each entry must be interpreted through these rules:

1. **Pure re-export shims are accepted.** Role-local Buster/Nova files that only re-export from `skills/common/...` may remain as import-path/package facades. They do not carry runtime behavior and are not migration blockers.
2. **Legacy shapes are not an end state.** Internal support for old payload/result/status/config shapes, mixed aliases, fallback authority readers, compatibility projections, and inferred legacy identity must be deleted or strictified in the owning TypeScript slice unless explicitly approved.
3. **“Canonical behavior/default” requires proof.** A fallback may be kept only if we would intentionally design it today as product/runtime policy, independent of legacy data compatibility. Examples: bounded timeout defaults, idempotent cleanup, fail-closed contract validation, or non-authoritative observability that must not crash orchestration.
4. **External adapters must be narrow and temporary unless pure facades.** CLI/env/API compatibility can exist only at the external boundary, must normalize immediately into the canonical typed contract, and must not leak into runners, registries, lifecycle state, plugin contracts, or authorities.
5. **Authorities fail closed.** Status lifecycle, gate results, worker results, Redis completion, session identity, Git ownership, and registry/plugin contracts should reject malformed or legacy-shaped internal input after their TypeScript slice owns the contract.
6. **Open policy questions are batched.** Remaining `needs user decision` entries should be grouped by semantic policy area instead of debated row-by-row: Buster suite skip/fail semantics, side-effect failure handling, Git safety, lifecycle/state strictness, public/barrel surfaces, and disabled/dead paths.

Fast delete/strictify signals:

- `new_field || old_field` inside internal code
- camelCase/snake_case alias support outside a boundary normalizer
- old status/result/config projections used as authority
- registry/plugin bypasses
- unknown or malformed objects accepted as valid
- broad barrels that preserve obsolete import culture without a current public API need
- fallback reads from legacy files or alternate state stores

Migration rule: **TypeScript conversion must not fossilize compatibility debt.** Accepted behavior should become explicit typed policy; legacy compatibility should either be removed immediately in its slice or isolated at a documented external adapter boundary with an exit criterion.
