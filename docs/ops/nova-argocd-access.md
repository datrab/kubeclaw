# Nova → Argo access

The authorized access path is maintained as the `nova-argocd-access` Argo
Application, generated by `scripts/argocd-self-management.mjs`. Unlike existing
manual platform handovers, this new network-only application auto-syncs without
pruning so no cluster credential is needed to bootstrap the connection.
It creates no Role, service account token, password or cluster-wide exception.

`resources.yaml` creates only the targeted standalone Service. The current
cluster rejects `cilium.io/v2` discovery, so including a CiliumNetworkPolicy in
this application prevented the entire sync. The optional Cilium allowance is
retained separately in `cilium-optional.yaml`, excluded by the exact Argo
`directory.include: resources.yaml` filter. Apply it only on a cluster that
actually supports Cilium and after reviewing its existing isolation model.

No generic NetworkPolicy replaces it: selecting Nova with a new Egress policy
would itself introduce isolation and could interrupt unrelated working tools.
This fix creates no NetworkPolicy, removes no live policy, and changes no existing
network/RBAC enforcement. Existing policies and tailnet ACLs remain authoritative.
A policy-blocked path still needs an explicitly scoped operator-managed allowance.

The standalone egress Service targets only `argocd.tail576648.ts.net` and reuses
the existing operator OAuth configuration and tailnet grants. No new Tailscale
auth key or account invitation is required. Tailnet access may still need a grant
from the existing operator proxy tag to the Argo tailnet device. Do not silently
replace that with an allow-all tailnet rule. See the official
[operator egress architecture](https://tailscale.com/docs/kubernetes-operator/egress).

The operator changes `Service.spec.externalName` to its own headless Service.
Argo respects that single field's ignore rule; the destination annotation, port,
namespace and policy selectors stay managed and reviewable.

After automatic reconciliation, verify without credentials from the actual Gateway:

```bash
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 \
  --connect-to argocd.tail576648.ts.net:443:nova-argocd-egress.kubeclaw.svc.cluster.local:443 \
  https://argocd.tail576648.ts.net/api/version
```

This preserves the original TLS SNI, Host and certificate verification while using
the egress Service for routing. Do not add `--insecure`. Request Argo credentials
only after this path passes. Protected Secret Store values additionally require a
supported Gateway HTTPS-egress consumer and exact allowed host; a successful
unauthenticated curl alone does not qualify protected-secret substitution.

Before publication, gateway DNS resolved the internal Argo Service but connections
to Service TCP80/443 were refused; the MagicDNS hostname was unresolved. The
repository's central default-deny rules lacked an explicit Nova→Argo allowance.
These observations motivate this path but do not alone prove which live component
rejected it. Source tests and review are separate from operator/tailnet/live checks.
