## Reader result

The extension entry page now helps a technical reader select the smallest change
that owns the required behavior. It separates these choices:

- project and platform configuration;
- pipeline stage, observer, capability adapter, test provider, and report adapter;
- OpenClaw extension and Codex plugin or skill;
- Worker engine and runtime-role composition;
- Core or Foundation change.

The page explains why each option fits, when it does not fit, and which component
owns the result. A decision flow, a quick table, 14 representative requests, and a
ten-question design check support the choice. Text below the diagram gives the same
decision path without requiring Mermaid rendering.

The page also distinguishes discovery, Nova activation, test-plan binding, and
Buster execution. A present manifest does not prove that executable code can run.
Project input cannot install new code, create a new role, or add an unknown
capability. The page keeps pipeline, OpenClaw, and Codex host paths separate.

## Boundary result

The guide records current product limits instead of presenting planned mechanisms as
implemented features. In particular:

- the capability vocabulary is closed;
- plugins cannot change canonical lifecycle state directly;
- current activation does not provide a persistent isolated host for an external
  long-lived capability adapter;
- `plugin.json` does not load a Worker engine;
- runtime roles are build-time package compositions;
- active runs bind immutable package identity and do not hot-reload package bytes.

These limits guide a reader toward an existing public contract or toward explicit
Core, Foundation, engine, role, packaging, and deployment work.

## Source evidence

The page contains 23 narrow code links pinned to the assessment revision. The AP08
choice-guide checker resolves every linked path and line range with `git show`. It
also requires the critical headings, boundaries, inventory counts, and representative

A second manual source review corrected four overbroad statements. Foundation
activation covers stages, observers, and capability adapters only. Buster uses
separate sandboxed loaders for test providers and report adapters. Registration
configuration and capability fields differ by surface. Report-adapter binding comes
from test-plan resolution, not independent project-side loading. The review also
separates Foundation plugin grants from the bounded grants inside a resolved Buster
provider plan.
