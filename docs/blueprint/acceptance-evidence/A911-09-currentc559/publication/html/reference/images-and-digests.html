Choose the task and authority

Use this page to identify which image was selected, what produced it, which platform it can describe, and what still needs observation before rollout or rollback. A source recipe, a stored receipt and a running container answer different questions. Keep all applicable identities in the change record.

A pull request (PR) proposes a Git change for review and merge. GitOps keeps the deployment's desired state in Git. Argo is the reconciler on the selected GitOps path: it brings the cluster toward that desired state. Merging a selection can authorize deployment when that path is enabled and bootstrapped.

Do not equate these identities

Open Container Initiative (OCI) formats describe image indexes, manifests and configuration. A descriptor identifies another object by media type, digest and size. A digest is a content hash; it does not authenticate the producer or prove that a container ran. A tag is a mutable name pointing to an object.

Here rootfs means the image's root filesystem. Configuration metadata does not prove that layer bytes or a running container were inspected.

Three code-bundle roles are not three more images

Role archives are nova, buster and prism; their role manifests select packages, plugins and entrypoints. The bundle manifest binds role, commit, runtime surface, packages/plugins and dependencies. The code receipt binds URLs, archive SHA-256, contract v2, source run and attempt. A role archive is not a Nova caller grant, Buster service credential or native-host permission. Use Roles and package ownership for that boundary.

The build workflow can package role archives after deployment-only changes without rebuilding compatible images. selectedCode compares image-input identity between the selected image commit and code commit; it does not require those commits to be identical. A difference in image inputs rejects with CODE_RELEASE_REQUIRES_NEW_IMAGES. Retaining an older compatible image does not prove the newer bundle is active in a running workload.

Versions, defaults and architecture limits

ARG declares a Dockerfile build-time parameter. TARGETARCH names the selected target architecture where a recipe uses it. A source branch does not prove that every named architecture was built or published.

versions.json owns central OpenClaw version/base digest and managed build arguments plus applicable per-image overrides. versions.mjs generates the recipe ARG defaults, rejects unmanaged/unused overrides and requires pinned base syntax. OpenClaw inputs have one authority; they cannot be overridden independently per role. The workflow separately supplies source revision and database-refresh controls. These declarations do not prove the final builder used every expected base, context byte, lock or tool result.

Neither the runtime nor Ops build workflow declares an explicit platforms option. Recipes with TARGETARCH branches/checksums for amd64/arm64 do not prove both architectures were published. A runner label such as ubuntu-latest is not descriptor evidence for the resulting artifact. Select a concrete os/architecture[/variant] and verify the actual descriptor relation.

The current checked-in recipe guard requires both complete exact recipe-byte hash equality and the retained selected-instruction hash equality. Its finite nine-recipe scope is not all twelve recipes or complete image provenance. The narrow source-guard witness does not build/run Docker, verify actual bases, context, registry publication or deployed contents. This page adds no recipe to that guard and changes no versions or pins.

Descriptor inspection: useful, bounded, not a running-container verdict

Only after the existing release/maintenance prerequisites are met may the source inspector be selected. It needs the repository working directory, accepted selection/source bytes, actual Node/dependency/tool/Git context, explicit platform, approved GHCR access and, when selected, a protected bearer token file. GHCR is GitHub Container Registry. Do not print or copy token contents.

CLI syntax only, not a ready-to-run example or an executed command:

node scripts/updates/inspect-release-image.mjs <runtime|ops> <image-slot> <os/architecture[/variant]> [registry-bearer-token-file]

selectedRelease can launch materialization --check; the inspector can read the token file and make bounded registry requests. It is not a new offline, write-free inspection tool. Before use, follow the existing release acquisition procedure with the accepted selection and original source checkout. Its required tools and dependencies, explicit platform, and approved registry/token-file access must be available; stop if a prerequisite is missing.

The resolver hashes raw bytes and checks descriptor size/media type before interpreting the selected relationship. If the root is an index it requires exactly one matching platform child; missing/duplicate choices and nested indexes fail rather than selecting the first child. It then validates the manifest/config platform and rootfs/layer descriptor relations. It does not fetch or verify layer bytes, run a container, prove active code or authenticate signed build provenance. Signed-blob redirects are bounded and constrained; registry authorization is not forwarded to the signed blob host.

Its output retains scope: descriptor-relationships-only and these distinct false flags: layersVerified: false, runningContainerVerified: false, activeBundleVerified: false. Do not turn a successful descriptor result into any of those claims. An index digest, selected platform manifest, configuration digest and runtime-specific Pod image ID require their actual relationship, not a universal string-equality test.

Coverage and follow-up evidence

This reference covers the two named workflow families, twelve first-party slots, three bundle roles and their selected source/receipt/render/descriptor readers. It does not inventory every upstream chart, external image, extra-container override, pipeline/provider build, sandbox/native-host image, registry mirror or dynamically produced image. Conditional supported routes still need an owning source and operational evidence; absence here is not an exclusion or permission to substitute them.

Actual builder platform, remote run/assets, provenance signatures, layer bytes, current cluster/Pod/CRI relations, active bundle and original application/data behavior were not observed. Current local Ops data is not remotely reverified; runtime selection remains absent. The new manuscript does not repair an older generic imageID comparison into a universal OCI normalization algorithm.

Keep source changes connected to the existing maintenance and reader ownership routes. Slot/role/recipe removal or rename must update consumers and links; a stored hash or a complete-looking table is not add/change/remove drift proof. The current page generators do not make this authored reference an image inventory generator. No build, scan, OCI inspection, workflow, Helm render, registry/network call, container, deployment or rollback ran here.
