Start with the first owning boundary

An error tells you where a boundary rejected or lost confidence in work. It does not, by itself, prove that no external action occurred. A timeout can follow a completed remote action whose acknowledgement was lost. A failed result can also retain cleanup work that has not finished.

Use this page when you have a code, reason, failed result or HTTP error:

  1. Preserve the first diagnostic and its cause chain, exact target, time window and non-secret run/attempt/job/effect identity. Keep partial output too.
  2. Identify the representation in the table below. Do not search only the beginning of the human message.
  3. Select the owning component and its detailed procedure. Establish whether work was rejected, accepted, completed, or remains uncertain before retry.
  4. Stop if the owner, terminal receipt, cleanup or target identity cannot be established. Preserve the current state for the responsible component owner.

A terminal receipt is the durable record of an operation's final outcome. A cause chain preserves the underlying failure even when another component wraps or translates it. Neither a success-shaped HTTP response nor a closed connection replaces the owning operation's bound result and cleanup evidence. For the incident setup and independently reachable administration conditions, use Diagnose. For retained-state procedures, use Recovery; this hub does not authorize a reset or replay.

Dynamic families and detail parameters

A stable family can be constructed from a finite prefix/suffix set. Preserve that construction and the call site: a list of uppercase string literals can miss typed codes, translated reasons and interpolated families.

Exact family / parameters Actual trigger and phase Effect and safe action
WORKER_ATTEMPT_INPUT_{BYTE_LIMIT,NODE_LIMIT,DEPTH_LIMIT,TYPE_INVALID,CYCLE} preflightJson checks the constructor envelope with the WORKER_ATTEMPT_INPUT prefix Correct the rejected representation and retain the exact limit/detail. This check precedes that executor's operation; do not generalize that ordering to result checks
WORKER_RESULT_{BYTE_LIMIT,NODE_LIMIT,DEPTH_LIMIT,TYPE_INVALID,CYCLE} The same helper checks the specialist result after operation and again after optional result finalization Work can already have happened. Preserve result/attempt/cleanup evidence; changing input and rerunning is not a substitute for resolving the original outcome
${phase}_TIMEOUT Deadline helper reaches the named phase limit; non-maintenance claim expiry can instead emit WORKER_CLAIM_EXPIRED Find the actual phase call and its settlement/termination evidence before deciding retry
WORKER_PHASE_UNRESOLVED:${phase} Aborted work does not settle within the drain interval, or a later phase is already fenced Quiescence is unproved. Reconcile owned work; do not treat cancellation as a successful kill
PRISM_NATIVE_BUDGET_NOT_ACCEPTED:{cpuTimeMs,maximumMemoryBytes,maximumTasks} Budget is not requested, or a new unrecovered attempt exceeds the host maximum Correct producer envelope/policy. Recovery status affects the comparison; do not raise host policy inside the Worker to force acceptance
SECURE_REDIS_TRANSPORT_POLICY_VIOLATION / MISSING_DEPENDENCY Typed transport-policy or dependency constructor Preserve code/details/dependency/cause separately from the English message; neither is a successful delivery

In the JSON preflight, TYPE_INVALID covers unsupported representations such as non-plain objects or accessor/non-enumerable properties. CYCLE is the helper's diagnostic for repeated object identity in its traversal; do not infer a different serializer's behavior from that label. Size/node/depth checks apply at their actual caller, not at a universal product boundary.

Translation changes the reader's decision

StageExecutor turns an EFFECT_OUTCOME_UNRESOLVED or EFFECT_RECOVERY_* message into outcome blocked, reason core.effect_reconciliation_required, empty artifacts and the preserved original message. Other failures can become core.attempt_cancelled, core.attempt_timed_out or core.plugin_runtime_failed. The result is then recorded as an attempt event; a result's reason and the event's type are different fields.

Do not erase the first error when a wrapper translates it. In particular, core.effect_reconciliation_required means the original effect must be reconciled, not that no effect occurred. The Worker also promotes unsettled phase/execution state to WORKER_PHASE_UNRESOLVED unless termination itself failed; the original fault context remains part of its diagnostic.

Readiness is a separate boundary. The selected Prism worker returns HTTP 503 and PRISM_NATIVE_RECONCILIATION_REQUIRED while native readiness is false. In HMAC mode, a failed nonce-database check returns HTTP 503 and PRISM_NONCE_DATABASE_UNAVAILABLE. HMAC is a shared-secret authentication mechanism. This readiness probe checks nonce-table availability only; it does not authenticate a request or consume its nonce. Separate per-request authentication verifies HMAC and consumes the nonce to reject replayed requests. These readiness errors do not describe a successful attempt result or authorize bypassing replay checks. A ready service can still reject a later envelope or budget.

Diagnose uncertainty before retry

Observation First distinction Preserve / next decision
Schema or trust rejection Which validator/owner rejected which exact bytes? Input/version/package identity and error details; correct only that authority
Timeout, disconnected client or lost acknowledgement Was work accepted, and does a terminal receipt exist? Original request key/job/effect/attempt; reconcile before a new submission
Report or evidence import failed Did execution already finish while import remained incomplete? Original result and evidence digests/import state; repair import, not test execution
Cleanup or termination unresolved Can the current owner prove all owned work stopped? Native scope/process/claim, cleanup and fault evidence; keep new admission fenced
Normal failed assertion Did the required test actually execute and produce findings? Executed/skipped/missing case data; do not hide an engine failure as a finding
Unknown external error Which dependency and operation own it? Full first cause and selected version/target; unsupported recovery stays explicit

For an interrupted diagnostic, retain the first error and partial output before deciding another attempt. For audit specifically, do not assume the journal stayed byte-identical: use the audit acquisition conditions, including the correctly bound inactive-copy rule when originals must be retained.

Expected completion of diagnosis is an identified owner and cause class, a supported next action with its stop condition, and the bound evidence needed to prove recovery and cleanup. A new green status without those identities does not resolve the original uncertain operation.

Coverage and maintenance limits

This page covers the selected current Foundation, Nova, Worker, Prism, Buster-generator and OpenClaw transport sources above. Product-wide emitting, wrapping, HTTP and result-translation paths across every language and package have not all been discovered. Dynamic families need their complete callers, parameters and effect states; a string count is not that proof. Unknown external codes and unsupported recovery routes remain owned by the relevant component, not silently assigned a generic retry rule.

Use Documentation maintenance when an error's code, trigger, representation, owner or retry behavior changes. Keep generated facts separate from authored interpretation; update the affected reader route as well as the exact source identity. The existing Buster generator does not generate this central hub. We ran no extractor, diagnostic, audit, restart, retry, repair or live recovery command for this page.
