One logical publication

.swarm/progress.json and .swarm/pipeline.json describe different parts of one project generation. A generation is an exact stored pair with one identity. Project setup publishes both files through one pointer. The strict pair reader rejects module/gate authoring and test-provider policy from different generations.

  • progress.json holds project, ordering, modules, gates, and classic policy selections generated from progress.scaffold.json.
  • pipeline.json holds lint inputs and module/gate test-provider declarations.
  • .scaffold-publication/ holds immutable generation members and the committed pointer (current.json) that makes one pair current.

A loose file is a current copy outside the immutable generation directory. A materialization is the publisher-created loose copy of a generation member. Immutable means that the publisher can create or verify stored bytes, but cannot replace them with different bytes under the same generation identity.

Neither file is Nova runtime progress. Attempts, facts, waits, and results live under the platform storageRoot.

Supported workflow

This procedure publishes and verifies a local pair. It does not compile a Nova project, contact a test endpoint, or start a provider. Use the recorded source revision, Linux, Node.js 24, Git, Bash, util-linux flock at /usr/bin/flock with --timeout support, GNU coreutils, and the dependencies from Locked Dependency Installation. Run from the repository root as its checkout owner. The owner needs write access to the new temporary directory; no Kubernetes, model-provider, or production-storage permission is required.

Before creating the disposable project, check the required locking command:

set -euo pipefail
publication_flock_help="$(/usr/bin/flock --help 2>&1)"
case "$publication_flock_help" in
  *--timeout*) ;;
  *) printf '%s\n' 'Required /usr/bin/flock lacks --timeout; stop' >&2; exit 1 ;;
esac

BusyBox flock does not meet this prerequisite. Changing PATH cannot correct it because the durable store uses an absolute path. Install the required host tool through the host owner before proceeding; do not bypass the lock.

The example uses a disposable Git repository with one module. FORGE.md is its implementation instruction, and BUSTER.md is its test instruction. Discovery creates an HTTP health declaration and a blocking dependency-security scan. The HTTP declaration needs an origin that the author must supply. The loopback origin below is authoring data only. Publication checks its presence; it does not prove reachability or provider admission. Before using this plan in a real run, resolve it with the selected registry and grants and prove the endpoint from the provider's execution location. See Project test pipeline.

Authoring authority and effective defaults

Discovery reads the committed pair with loose-copy comparison disabled. It then reads the existing scaffold. Scaffold version, description, notes, defaults, and execution order take precedence over progress values. For these fields, missing, null, or empty-string values fall back to progress and then discovery defaults. Empty arrays and objects, false, zero, and whitespace-only strings do not trigger this fallback. Some discovered text fields, such as module title and thinking level, instead reject whitespace-only strings and use their fallback. These rules prepare a form; they are not complete type validation. An existing scaffold policy object wins as a whole; discovery does not merge its missing policy fields with defaults. Existing module and gate entries override discovered entries by field, with a shallow merge. Nested objects are replaced.

An existing scaffold pipeline is preserved as a whole. An invalid object or mismatched project stops regeneration before any write. New modules can therefore need new authored pipeline scopes after regeneration. Without that scaffold field, discovery builds a provider plan from the prior pair and discovered controls. See Project test pipeline for provider choices and their separate resolution rules.

Discovery supplies version 1 and module defaults of 300 minutes, three failures, and adaptive thinking. Its initial policy enables architecture validation and telemetry, and disables pipeline review and case study. Generation layout and identity

For names progress.json and pipeline.json, the publisher:

  1. Serializes each value as indented JSON with a final newline.
  2. Rejects either member above 64 MiB.
  3. Records each member's exact byte length and lowercase SHA-256 digest.
  4. Calculates the generation ID as SHA-256 of the ordered [name,digest,bytes] tuples.
  5. Writes immutable members below .scaffold-publication/<generation>/ using create-only files and links.
  6. Materializes both loose current files through temporary-file rename.
  7. Atomically writes .scaffold-publication/current.json last.
  8. Reads the committed pair again and verifies every byte.

current.json is a closed logical manifest:

{
  "schemaVersion": "published-json-pair.v1",
  "generation": "<64 lowercase hex characters>",
  "members": [
    { "name": "progress.json", "digest": "<64 lowercase hex>", "bytes": 123 },
    { "name": "pipeline.json", "digest": "<64 lowercase hex>", "bytes": 456 }
  ]
}

The member order is part of the generation identity. Member names must be different and match the publisher's lowercase JSON filename rule.

Reader behavior

If .scaffold-publication is absent, the reader accepts available loose files; this supports a project that has not yet used coupled publication. The reader rechecks that the publication directory did not appear during the loose read.

If the directory exists, the reader requires a valid current pointer, valid immutable generation, matching member digests/lengths, stable directory identities, and—by default—byte-identical loose materializations. Damage never causes fallback to loose files. The exported test-scope and lint loaders use this strict mode.

The scaffold discovery path reads with loose-copy verification disabled so it can prepare a corrected publication from the committed generation. That is a repair input path, not execution authority.

The test-scope loader requires .swarm/pipeline.json and exactly one module or gate selector. It returns the selected declaration's coverage, suites, tests, fixtures, and concurrency limits. The lint loader uses the same strict reader; absent lint returns null, while a present declaration must select kubeclaw.lint.full and at least one explicit input. Pair errors become TEST_PLAN_PIPELINE_INVALID with the original error as cause. Inspect that cause to distinguish publication damage from a missing scope. These loaders do not validate the complete progress contract or compare both project fields. Scaffold validation establishes that identity for this workflow. Custom publishers must preserve the contracts of both members.

Concurrency and file safety

The publisher pins directory device/inode identities, rejects symlinked or multi-linked current targets, uses a durable store lock, writes immutable generation files, fsyncs files/directories, and commits with one pointer update. Concurrent substitution or mutation produces PUBLISHED_PAIR_CHANGED.

The lock covers publication, not scaffold edits or the CLI's earlier change summary. Keep other authors stopped while validating and applying one input. The lock waits up to five seconds; lock failure stops that attempt. Readers do not acquire the writer lock. They reject a changing or divergent pair during an interrupted publication, so they can be unavailable until repair. The publisher does not automatically retry or select an older generation.

Compatibility and change impact

The current publication manifest is published-json-pair.v1. Generation identity is based on exact serialized bytes, so whitespace from another writer can create a different generation even when JSON values are equivalent. Use the supported publisher for stable formatting.

Repeated apply with identical scaffold values computes the same generation. It verifies existing immutable members and replaces current materializations and the pointer through the publisher. It can report progress.json is already current before discovering publication damage; that summary compares JSON values only. A zero apply exit plus the final strict read establishes success.
