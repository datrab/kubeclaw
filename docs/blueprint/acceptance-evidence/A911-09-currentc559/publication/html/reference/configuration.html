Find the setting before changing it

Start with the process or artifact that consumes the value, not its filename. A Helm value, a platform grant, and a stage setting can share a name without sharing authority. Changing one does not override the other two.

  1. Find the consumer in the family table below.
  2. Open its detailed reference and identify the exact field, version, and default rule.
  3. Use the change class and diagnostic route for that consumer before activation.

For a schema keyword or a contract that describes an input or result, use Schema authorities. For a package name versus a caller grant or native-host permission, use Roles and package ownership.

Determine the effective value

There is no global last-writer-wins rule. Record the family first, then apply its precedence rules. Keep these cases distinct:

Case What to establish What not to infer
Omitted field Whether the exact schema requires it; whether the actual resolver or consumer supplies it A displayed schema default means every caller inserts it
Empty string Whether that field permits it, uses ??, or requires non-empty text Empty equals omitted; ?? only replaces null or undefined
null Whether schema type/branch allows null before consumer fallback A null value always clears a setting
false or 0 Exact type and allowed range, then the real consumer condition False/zero means missing or disable everywhere
Object / array Exact family merge or replacement behavior Helm, compact profiles, provider config and platform JSON share one merge algorithm
Relative path The loader's path origin and canonical-file handling Every path is relative to the shell working directory
Secret reference Named Secret/key or file plus the actual receiving process A reference proves the credential exists, is valid, or is authorized

The platform loader uses strict validation without a default-insertion option. It resolves installation roots, trusted built-in roots, storage root and optional cgroup root relative to the real platform file's directory, then freezes the result. It does not merge an environment object into that file.

Registered configuration has two deliberately different operations:

  • Validate: check the provided value without inserting defaults. Stage, enabled observer/adapter, and validateTestProviderConfiguration use this route.
  • Resolve provider configuration: clone the supplied value, validate the clone with default insertion, and return a provider-configuration.v1 record with contract ID, schema digest and resolved values. The original input is not rewritten. Resolution still does not install or grant a provider.

Concrete route: a missing provider option

Suppose a provider field has a default in its registered schema. First open Provider configuration and identify the contract ID and field. Check whether your caller resolves configuration or only validates it. A successful validation alone does not prove that the provider received a filled-in value. Retain the non-secret resolved contract ID/schema digest and the exact provider field, rather than printing the whole resolved object. If the provider is unavailable, diagnose installation, selection, grants and service availability separately from field validity.

Concrete route: a Prism URL

loadControlServerConfig uses PRISM_WORKER_URL ?? 'http://prism-worker:8080' and constructs a URL. An omitted variable selects that loader fallback; an empty string is not replaced by ?? and must still be a valid URL. The composition function copies the environment before asynchronous authority loading. Changing a deployment Secret or shell variable does not update the already captured process configuration.

Change and reload boundaries

Use Configuration change impact for the complete procedure. The following distinctions prevent unsafe shortcuts:

Changed authority Required boundary to check Preserve before changing
Platform packages, providers, grants, adapters, observers or graph Existing run snapshots pin effective authority and graph/package identities; changed authority normally belongs to a new run Prior platform, original graph, package identities and run ID
Platform shutdown/effect-lock timeouts Recreate the consuming objects; new CLI invocation or restart if startup-loaded. Timeout-only change is not itself a new-run requirement in the recorded runtime subset Original values, drain state and first shutdown diagnostic
Provider plan or coupled .swarm files Republish a consistent generation, then use its new resolved plan/run Original pair/generation and plan digest; do not fix only one loose copy
Pod template, environment or startup-mounted configuration Identify the rendered receiving workload and its restart/rollout behavior; no general hot reload promise Redacted rendered values, workload identity and previous generation
Signing material or trust identity Component-specific coordinated credential rotation and restart/reload rule Old/new acceptance window and identity; never publish private bytes
Native pool policy or capacity Host preparation, actual cgroup/identity checks, then worker readiness Policy identity, host state, active attempts and drain status
Persistent location or data format Component backup/restore/migration procedure, not just a values edit Proven backup and restore route, ownership and store identity

These are selection rules, not permission to run a deployment or migration. A value is hot only where the named consumer explicitly watches or rereads it. See the source-linked change matrix for recovery pins and field-specific exceptions.

Diagnose without exposing secrets

  1. Retain the first diagnostic, artifact version, canonical input path and source/package identity. Redact tokens, private keys, Secret contents and credential-bearing URLs. Do not paste a full environment or config dump.
  2. Match the prefix to Configuration errors.
  3. Correct the owning input, not a different layer with a similar name.
  4. Follow that family's validation route before restart, republish or new run. Preserve the prior working bytes and unresolved cleanup state if activation fails.

Facts, generated tables, and coverage limits

Plugin configuration, Helm values and Environment variables retain their existing field inventories. This page is an authored selector; it is not another manually copied field table and is not a newly generated inventory output. The documentation generator's current write map does not generate this hub.

The current configuration discovery has separate YAML/Helm, runtime environment and owned CLI routes. Its registered-schema selector covers platform plus configSchema registrations under skills/common/plugins, skills/nova/plugins and skills/buster/plugins. That selector does not discover every contract, embedded validator, host input or dynamically constructed source.
