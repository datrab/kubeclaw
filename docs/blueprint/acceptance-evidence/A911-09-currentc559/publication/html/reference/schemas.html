Choose an authority, not a file suffix

A schema describes what a value may contain. The actual validator determines which document, definitions, defaults and additional semantic checks apply. A file called *.schema.json is not proof that runtime loads it. Conversely, a compiler can enforce a public input contract without a separate schema file.

  1. For a configuration value, start with Configuration and the family-specific generated field table.
  2. For a stage input/result or observer checkpoint, find the exact registration and schema path in the catalogue below.
  3. For Worker, chart, API or Nova input, use its distinct authority row and consumer. Do not substitute the plugin-config validator.

Identify an authority by path + embedded JSON pointer or symbol + declared version/dialect + actual consuming caller. Shared files can serve multiple registrations; those are different caller edges, not duplicate contracts.

Other authority kinds and version selection

A custom resource definition (CRD) is a Kubernetes CustomResourceDefinition: it declares the schema of an additional API resource. Common Expression Language (CEL) rules attached to that schema express object constraints for API-server admission—whether the API server can accept a create or update. Admission is not controller reconciliation: the Buster controller separately reads a lease's spec and status and acts on it. These are different consumers, not two names for the same validation step. For this lease, the chart condition, installed API group/version, and the receiving API server's support for those rules still apply; no live validation or controller run is demonstrated here.

Interpret nested constraints and defaults

Start from the consuming root and follow every selected branch. A valid leaf is not enough if its parent, alternative or relationship rejects the object.

Construct Reading rule Common mistake to avoid
properties, required, additionalProperties Read together at each object level; requiredness belongs to that object/branch Treating every listed property as required or permitting unknown siblings
items, prefixItems, maps Follow item/tuple/map-value constraints and cardinality, including nested objects Checking only the container type
$ref / $defs Resolve the actual document namespace and exact pointer, retaining repeated/cyclic relationships Flattening a reference into a field name or assuming network resolution
allOf, anyOf, oneOf Combine constraints according to the actual validator; oneOf requires exactly one valid alternative Combining all alternatives into a permissive union
if / then / else Evaluate the condition before selecting the applicable dependent constraints Applying both branches or treating a condition as a default
not and forbidden combinations Preserve negation and branch polarity Reporting a forbidden required-field pattern as a positive requirement
dependent rules / cross-field checks Trace both presence relationships and executable semantic checks Accepting individually valid fields whose relationship is invalid
default, examples, deprecation Distinguish annotations from actual resolver mutation, fallback, migration and version policy Treating an example as permission, or an older filename as deprecated
bounds, format, enum and pattern Preserve exact type/unit/range/format enforcement at the selected validator Converting missing numbers to zero or weakening a string to make it load

Registered document validation uses an immutable schema and isolated validators. The ordinary route does not insert defaults. Provider resolve clones input and uses a default-inserting validator. Neither route changes grants, selects an installed provider or promises runtime success. Platform and manual validators have separate behavior; do not transfer this rule to Helm or CRDs.

Validate, diagnose, and change the right contract

  1. Identify the exact input/output kind and its consuming caller; record the path, pointer, version, package identity and non-secret diagnostic.
  2. Read the complete selected constraints and actual default/manual checks.
  3. Use that family's existing validation instructions. Schema syntax or a test declaration is not an observed validator result, deployment, or API admission.
  4. On failure retain the first schema path/error pointer and original input. Use Configuration errors. Fix the owning value or consumer relationship; do not remove the rejecting condition.
  5. For a change, follow Compatibility and Change impact. A new file version does not migrate retained records, running package snapshots or controller state.

REGISTRY_RESULT_INVALID names a failed referenced value; determine whether that caller was checking configuration, input, result or checkpoint before editing it. REGISTRY_MANIFEST_INVALID can mean the schema itself is invalid. Neither error licenses bypassing strict validation.
