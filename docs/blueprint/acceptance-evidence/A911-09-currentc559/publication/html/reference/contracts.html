Identify the contract before changing a version

A contract is the agreement between a producer and its consumer about data and behavior. A producer writes or returns a value. A validator checks the selected shape and semantic rules. A consumer acts on it. These can be three different components; passing one validator does not prove that every consumer accepts it.

  1. Identify the logical contract, record marker, producer and actual reader.
  2. Match the direction in the matrix below: new write, read, recovery or rejection.
  3. Retain original bytes, package/content identities and affected durable state before considering an upgrade, migration or removal.

For exact recursive fields use Schema authorities. For package owners versus grants use Roles and package ownership. For retained data use Stores and retention. This page routes contract changes; it is not a migration command or an all-contract compatibility guarantee.

Read the direction, not just the version number

  • Write: a named current producer creates this format for new work.
  • Read: a named reader validates and consumes this format in a selected route.
  • Recover: a reader can continue retained state with the required original graph, package, configuration and semantic identities. Readability alone is insufficient.
  • Reject: the boundary stops rather than guessing a conversion.
  • Unestablished direction: this finite source set does not prove the writer, reader, downgrade, conversion or retirement route. Do not infer support.

Configuration compatibility gives the detailed artifact-specific vocabulary. No row below promises universal migration or rollback between arbitrary versions.

A readable snapshot can still be unrecoverable with changed inputs

The current writer creates run-snapshot.v4. The reader accepts explicitly listed retained snapshot versions and validates their profile fields. It does not add newer profile fields to old bytes to make them current. Snapshot version 1 also uses its version-specific digest serialization; retained graph v2/v3 is rebuilt using the stored graph marker before digest comparison.

Recovery then checks the registry dependency-identity format, original package set and content, effective runtime configuration and supported explicit package upgrade evidence. A schema-valid snapshot with changed runtime authority can therefore reject. Use original pinned runtime where required; do not edit the stored digest or start a new identity and call it recovery.

Plan a change or retirement

Retirement removes old data or an interface only after its readers and retained work no longer require it. Migration is a defined transformation with its own writer, destination, validation and recovery procedure. Neither follows solely from publishing a newer schema or package.

  1. Record the exact current writer, logical ID, record version, encoding, content digest, installed registration and known internal/external readers.
  2. Identify active and retained runs/records that pin the old authority. Keep original package bytes and required credentials, keys, profiles and readers.
  3. Establish the supported direction with the actual consuming validator and semantic rules. Stop if conversion, downgrade, external reader or recovery applicability is unknown; do not relabel bytes as a newer version.
  4. Preserve a consistent data group and writer fence using Recovery. A fence prevents conflicting owners from writing; a lock-file name alone does not establish that work stopped.
  5. Use only the component's supported migration or drain procedure. Retain original input/output identities, first diagnostic and partial failures.
  6. Before removal, verify recovery through the original application readers and required external consumers. Schema syntax or a native database check alone is not that proof. Keep unresolved readers and cleanup ownership visible.

One narrow example: the notification observer README directs retained runs that enabled its retired audit registration to drain with their pinned runtime. The current registrations are notifications and preview-delivery, with separate grants/attempts/checkpoints. That does not establish historical consumer absence, a universal retirement date or permission to delete journals. Audit also has the physical acquisition effects described in Stores and retention.

Failure and coverage limits

If a consumer rejects a marker, digest, profile, package set or relation, retain that original diagnostic and exact bytes. Correct the intended producer or use the supported original runtime; do not weaken validation, fabricate an empty accounting field or rewrite retained state to make it load. A partial migration needs its domain owner and supported recovery route before writers resume. Unknown external consumers are a stop condition for removal.

The eight families above are source-bounded examples with concrete selected callers, not an exhaustive inventory of logical IDs, schemas, embedded validators, all engine operations or every writer/reader pair.
