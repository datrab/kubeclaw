API object updates

Status: source-backed reference; live update behavior unverified Audience: operator, platform maintainer Owner: platform operations Evidence: scripts/deploy.sh; charts/gitops/templates/applications.yaml Applies to: authored Deployment update operations and the selected upstream source baselines Last verified: pinned source revisions listed below; no live update result

A manifest describes the desired API object. A changed manifest is an input to an update operation. It is not the complete object that Kubernetes will validate. The client can combine that input with a stored object and earlier configuration. The API server then applies defaults, admission and update validation. A receiver contract states the rules that the consuming component applies to a field. Read that contract after selecting the operation below.

A field manager is the identity recorded with a managed set of fields. A last-applied configuration is the manifest stored in an annotation by client-side apply. These are different state. Neither permits a change that fails parent validation, an immutable-field check, access control or admission policy.

This page describes source behavior. This explanation includes no execution of any API request, rollout, hook, eviction, cache event or volume publication. Client-side apply

A map associates keys with values; a list contains items. A scalar is one value, such as a number or string. Client-side apply first reads the live object. If it is absent, the client records the apply annotation, removes null-valued map entries and creates the object. Fresh typed decoding/defaulting follows at the API server. A null manifest leaf at this create step therefore cannot be treated as a retained typed scalar null case. A present list element or its parent can still fail decoding or validation. v1.35 create route. Argo's v0.36.1 client create route.

For an existing Deployment, the client obtains the old manifest from the last-applied annotation. It builds a strategic merge patch from three objects: that old manifest, the new manifest and the current live object. It combines changes from current to desired with deletions from old to desired. The patch can delete a field that the new manifest removes from the old manifest. Outside a selected retainKeys directive, live-state presence alone does not cause deletion. This rule applies when both old and new manifests omit the field. Malformed stored annotation data or missing list merge keys can stop patch construction. The client warns about a missing annotation; it does not turn the operation into server-side apply (SSA). v1.35 patch selection. three-way construction. Argo client patch selection. Argo client's three-way construction.

Deployment spec.strategy uses retainKeys. When the generated patch includes a $retainKeys list, applying it removes live strategy keys outside that list. For example, changing the desired strategy to type: Recreate can remove live rollingUpdate settings even if the old applied manifest never contained those settings. The directive must include every nonnull key supplied in that patch; an invalid directive fails. Inspect the selected client and resulting patch before relying on omission to preserve a live strategy member. Strategy patch declaration. retained-key construction. directive validation and removal.

An explicit null in the resulting strategic patch removes that map member. A nonnull object patch merges its children. An empty object consequently does not clear every existing child. Lists with a strategic merge key combine matching items and preserve unrelated items unless a deletion or replacement directive applies. Lists without strategic merge instead replace as a complete list; for those lists, [] clears the list. Changing a merge-key value selects another item identity; it is not a rename of the existing item. The field reference exposes each list's actual strategic merge key beside its schema. Strategic null and nested dispatch. merge versus replacement list handling.

Client-side apply defaults overwrite to true. It can overwrite a different live value; it does not run the server-side apply ownership-conflict check. With overwrite false, a conflicting change against the old manifest causes patch construction to fail. API conflicts trigger bounded re-read and patch reconstruction. Client force deletion is a separate option: after a conflict or invalid update, it can delete and recreate the object. Those force flags are absent from the selected deployment-script apply calls. If force recreation is explicitly enabled elsewhere, restoration of the old object after create failure is only an attempt and can itself fail. The original object UID and its workload lifecycle are not restored by creating a new object. Default overwrite. construction conflicts. retry and conditional recreation.

Argo operation selection

Argo passes Application options into the sync engine. Resource annotations and operation settings then affect the selected request. Replacement takes precedence over apply: for a live Deployment it uses replace, and for an absent Deployment it uses create. Force on the replacement route selects delete/recreate. These are whole-object operations; omitted fields do not have three-way apply preservation. For ordinary apply, Argo sets overwrite true. When it selects server-side apply, it sets ForceConflicts true independently of its client force-deletion setting. A live Deployment with another manager can therefore lose that manager's conflicting ownership under the selected Argo SSA route. Do not interpret Force=false as SSA conflict protection. Controller option binding. replace/apply choice. Argo apply options. kubectl replace versus force. force deletion and absence wait.

Argo disables SSA during its client dry run and when the target resource has the disable-SSA annotation. Otherwise Application SSA or the target SSA annotation selects it. Selected client-side ownership migration runs before the final request, can modify managed fields and can fail synchronization before that request. Even a selected replacement passes through this earlier migration condition when SSA is also selected. The operator must inspect both desired and live annotations, manager state and migration result. A diff result or dry run does not prove the operation that the real synchronization will send. SSA predicate. migration before operation.

The checked-in Application template does not enable these alternative update modes. When you inspect an Application or diagnose a changed live configuration, use the exact option names. ServerSideApply=true selects SSA at Application level. A target resource can select it with argocd.argoproj.io/sync-options: ServerSideApply=true. A target annotation containing ServerSideApply=false disables SSA for that resource. Replace=true selects replacement and Force=true can select deletion and recreation on that route. Desired and live resource annotations participate in replacement and force selection. These options can change ownership or delete an existing object; inspect them before retrying a failed synchronization. Option names. Application option selection. desired and live replacement options.

Client-side ownership migration is enabled by default. The Application sync option ClientSideApplyMigration=false disables it. Its default source manager is kubectl-client-side-apply; a nonempty Application annotation argocd.argoproj.io/client-side-apply-migration-manager selects a different source manager. Argo's final SSA manager is argocd-controller. Enabled migration runs only when SSA is selected, the request is not a dry run, and the live object needs migration from that source manager. The source manager, final manager and authenticated Kubernetes identity have different roles; a field-manager name grants no API permission. Migration option and default manager. Application manager selection. migration annotation. final manager. migration condition.

Server-side apply

SSA sends an unstructured apply object with a manager and a force-conflicts choice. The API server converts the stored and submitted objects using the API schema and calculates managed field sets before defaulting the merged result. It rejects a submitted managedFields member and duplicate submitted list identities. A field omitted by this manager can be removed only when this manager previously applied it and no other applier retains ownership. A field never owned by this manager is not removed by that omission. A changed field that intersects another manager's fields produces a conflict without force; force transfers conflicting field ownership. An equal value can be co-owned. Parent atomic boundaries and list identity decide the size of that ownership set. Apply request and force. typed conversion and later defaults. conflicts and ownership transfer. manager omission and pruning.

The field reference preserves x-kubernetes-list-type, map atomicity and SSA list map keys. For example, container ports have strategic merge identity containerPort, but SSA identity includes both containerPort and protocol. A TCP-to-UDP change can consequently act on a different SSA item while the strategic route matches the same numeric port. SSA manages an atomic list, such as arguments, as a whole; a keyed list such as containers gives each name its own member identity. Atomic selector objects make their children share the atomic ownership boundary. Do not apply a scalar ownership rule to a child inside one of these atomic parents. Container fields and port identities. container keyed membership. atomic label selector.

The structured validator accepts null scalar, map and list values. Scalar and atomic map/list merge keeps a present submitted null as that leaf value; later conversion/defaulting and validation determine its typed result. A null item inside a keyed associative list instead fails before merge. Granular maps and associative lists merge their members: a submitted null or empty collection is not a blanket removal of live members. SSA first merges, then removes previously owned members that this manager omitted and that no other manager retains. Null and an empty map also contribute their parent path to the submitted field set; ownership can consequently differ from an absent parent. This explains why a typed omission case cannot predict an SSA clear. Null scalar validation. null collections and rejected keyed null items. submitted leaf precedence. list/map merge boundary. null/empty map field membership.

Parent validation and recovery

Every selected operation must produce a whole Deployment that passes its selected API route. A changed selector is rejected on normal update, even with force-conflicts. A template must match that selector, use restartPolicy Always and contain valid containers; a retained nonempty ephemeralContainers list is forbidden. Changing only replicas follows scaling; changing the template can create a new ReplicaSet and new Pods. It does not change those fields in existing Pods. Normal Deployment update preserves stored status; a /status request selects separate validation, including nondecreasing collisionCount. Deployment update strategy. selector immutability. template validation. ephemeral prohibition.

The platform/workload operator must retain the desired manifest, the selected options, the live object, the stored apply annotation or managed fields, and the actual request/error. If construction, ownership or admission fails, stop before treating the field as effective. Correct the exact input or agreed ownership boundary, read current state again and inspect the subsequent admitted object. After an uncertain response, establish whether the request took effect before repeating a force or replacement action. API success is only the next boundary: verify the selected controller, new Pod, scheduler, volume, identity or application observation separately.
