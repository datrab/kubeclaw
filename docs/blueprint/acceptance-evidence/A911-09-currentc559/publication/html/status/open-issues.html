Capability work is missing from the attempt budget

Status: in-progress. Severity: high.

Problem and impact

The attempt resource receipt measures the provider process. It does not exclusively own and account for all capability, browser, adapter, and completion work that Buster launches.

A cheap provider can report low resource usage while its other local work exceeds the claimed CPU, memory or process budget.

Components and current state

  • Buster Runner
  • Provider process
  • Capability RPC
  • Report adapters
  • Shared Worker Core

Core now performs early and final resource observations. runner.measure still reads instance.resources(); moving the observation later does not create exclusive whole-attempt ownership. Durable fixture readiness/control, separate readiness/completion promises, a bounded fourth process pipe and native launcher ownership primitives exist as locally tested building blocks. The production runner still constructs LocalWorkerRuntime; the native lifetime API is not its production execution path.

Remaining work

  • Integrate durable attempt/claim-bound local execution ownership across Core and Buster, including provider work, parent capability execution, browser/command children, adapters, evidence and finalization.
  • Define aggregate measurement and hard budget enforcement. Distinguish cumulative CPU from CPU rate and processes from cgroup tasks. Required missing observations must fail. Declare remote BuildKit/Kubernetes work separately.
  • Preserve retained fixtures through durable ownership transfer, fences and crash recovery; coordinate with the restarted-job workspace recovery issue in this register.
  • Connect the actual Buster attempt host, restricted role-specific launch policy/broker and durable fixture lifetime to the runner. Keep broker and capability work inside the attempt scope. After the verified cutover remove the superseded executable runner, file-capability launch and sampling paths; retain no executable fallback.

Reproduction and verification procedure

  • Run the original provider in an actual delegated cgroup. Keep its own load small and launch two real capability children whose combined load exceeds the attempt budget although individual limits pass.
  • Put load separately in the report adapter and finalization. Compare the original receipt and terminal state with aggregate counters; unrelated concurrent service work must not be charged to this attempt.
  • Exercise short-lived children, descendants surviving their leader, missing counters, cancellation and drain failure. Fake cgroup files are not positive containment evidence.

Completion criteria

  • Every claimed local phase has exclusive ownership or demonstrably non-overlapping equivalent accounting.
  • Aggregate overrun or missing required observations prevent completed; successful drain leaves no local work running.
  • Original Core/Buster claim, timeout, fixture and evidence guarantees remain covered.
  • Fixture readiness is journaled before dependency acknowledgement, teardown fences acknowledgement races, and only the original Core terminal journal seals completion. Historical readiness cannot authorize new dependents.

Separate environment acceptance

Actual delegated cgroups and real providers/browsers are required. Acceptance in the deployed worker container is separate.

Restarted terminal jobs retain source workspaces without a durable quiescence proof

Status: partially-implemented. Severity: medium.

Problem and impact

After a worker or host crash there is no durable proof that every process belonging to a job has stopped. Source and working directories therefore remain retained.

Repeated interrupted jobs can consume disk and quotas. Deleting from terminal metadata alone could remove inputs still used by live descendants.

Components and current state

  • Buster RemotePlanService
  • terminal-workspace
  • Provider/capability/adapter ownership

Normal confirmed execution cleans inputs. Durable status write and read failures stop admission; shutdown waits for pending admission writes. recover() explicitly retains inputs because a terminal record does not prove orphan quiescence.

Remaining work

  • Publish durable job/attempt/claim ownership before launch and include capability children, adapters and retained fixtures.
  • On restart reconcile the exact fenced owner and require authoritative complete termination. Preserve and diagnose unknown ownership instead of guessing.
  • Authorize the existing narrow idempotent input cleanup only after that proof; preserve valid result, evidence and log receipts.

Reproduction and verification procedure

  • Crash and restart the original worker with a live provider plus actual capability/adapter children. Distinguish leader death from complete process termination.
  • Exercise crash windows around ownership publication, drain and file removal; reused or namespace-mismatched PIDs must never authorize cleanup.
  • Read completed/failed/cancelled job receipts and retained-fixture transitions after restart.

Completion criteria

  • No active or uncertain owner loses its inputs.
  • After complete quiescence is proved, only authorized inputs are removed; repeated recovery is safe.
  • Real quota release and retained result/evidence access are demonstrated on original jobs.

Separate environment acceptance

Native crash and containment tests are required. Log retention and external demo lifetime are independent of source-workspace cleanup.

Problem and impact

Components and current state

  • RecordStore
  • Attempt/Admission
  • ArtifactStore
  • Buster jobs
  • Nova dispatch/import
  • Operator delivery

Telemetry, admission, imported attempt results, redundant dispatch archive copies and causal operator projections have bounded implementations and local evidence. They do not remove all job counts, evidence objects or shared blobs. The dispatch projection has a real one-POST replay result while retaining logical job, receipt and source blob. Its native provider execution failed; that failure does not invalidate the bounded storage transition or prove successful native execution.

Remaining work

  • Inventory active/completed owners, all current reopen/accept/read/replay consumers and shared references.
  • Implement explicit manual release with durable consumer completion and required idempotency/uncertainty tombstones, atomically across those consumers. Keep every still-required reference resolvable.
  • Release actual byte and record quotas rather than moving data into unaccounted sidecars. D07 does not permit automatic age-based log deletion.

Reproduction and verification procedure

  • Use small real store quotas with active, waiting and completed runs and shared artifacts; measure actual bytes and entries before/after authorized release.
  • Replay old deliveries after restart and exercise competing writers and SIGKILL between durable transitions.
  • Use original result, evidence, artifact and operator readers on retired and deliberately retained history.

Completion criteria

  • Only authorized and fully confirmed history is released; active and uncertain work remains intact.
  • Released capacity admits new actual writes. Replays do not repeat an external action or fabricate delivery outcomes.
  • All affected consumers understand the same retirement state and retain the existing projection guarantees.

Separate environment acceptance

Prism approval notification is rejected by the installed messaging adapter

Status: open. Severity: high.

Problem and impact

When Nova selects the installed kubeclaw.operator-messaging adapter for operator.request, the Prism stage publishes architectureDigest as a top-level notification field. The closed messaging payload contract rejects that field.

Control can already have admitted design work and wait-store can already have committed a record. The stage returns blocked while Core has no active approval wait. The intended Studio-to-Nova handoff cannot complete through this path.

Components and current state

  • Nova Prism stage
  • Operator messaging adapter
  • Nova AdapterRuntime and Core lifecycle
  • Wait-store adapter
  • Prism Control

The linked implementations show dispatch, wait-store creation, then notification parsing failure before delivery reservation, secrets or network. AdapterRuntime wraps the error as EFFECT_OUTCOME_UNRESOLVED::OPERATOR_PAYLOAD_UNKNOWN_FIELD:architectureDigest; the stage catches it as prism_design.dispatch_failed without a returned wait. A direct parsePayload probe reproduced the narrow rejection; no full-stage or deployed result is established.
