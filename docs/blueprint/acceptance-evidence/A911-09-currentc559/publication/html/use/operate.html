Objective

Configure one governed runtime, start work, inspect durable results, and continue supported waits. This page also identifies controls that the current CLI does not provide.

Canonical Start, Readiness, and Observation Procedure

This section is the sole authority for start-readiness-observe. Start with an installed source-bound release, explicit <context> and <namespace>, selected component list, independent administration, and no active change. Run cluster commands from the administration machine. Kubernetes owns process and Service state; scripts/deploy.sh and the health program embedded by the chart own component checks; a completed application transaction owns functional proof.

Before any cluster command on this page, complete Bind Cluster Authority. Keep the same bound shell for the whole task. Every raw kubectl, Helm, or scripts/deploy.sh command below must inherit its exported read-only KUBECONFIG; every shown <context> must equal EXPECTED_CONTEXT. Run assert_cluster_binding immediately before each command block. Stop on any mismatch and follow the binding section's recovery; never fall back to the default kubeconfig.

Record source and release identities, context, namespace, time, and evidence directory. Stop if the current context, selected images, or ownership differs from the install record.

Observe the four levels in order:

  1. Process:

    assert_cluster_binding
kubectl --context "<context>" -n "<namespace>" rollout status deployment/agent-nova --timeout=300s
kubectl --context "<context>" -n "<namespace>" rollout status deployment/agent-buster --timeout=300s
kubectl --context "<context>" -n "<namespace>" get pods -o wide

    Expected observation: each selected Deployment completes rollout and every selected Pod is running without restart growth. Omit a role only when the install record says it is disabled.

  2. Service:

    assert_cluster_binding
kubectl --context "<context>" -n "<namespace>" get service agent-nova agent-buster
kubectl --context "<context>" -n "<namespace>" get endpointslice \
  -l kubernetes.io/service-name=agent-nova
kubectl --context "<context>" -n "<namespace>" get endpointslice \
  -l kubernetes.io/service-name=agent-buster

    Expected observation: each selected Service exists and has at least one ready endpoint. A Service without an endpoint is not ready.

  3. Dependency:

    assert_cluster_binding
bound_deploy smoke-agent nova
bound_deploy smoke-agent buster

    Expected observation: each command exits zero after rollout, Pod readiness, gateway, startup record, Redis-aware readiness, code bundle, skills, and runtime configuration checks. These checks do not prove a user transaction.

  4. Functional: execute the registered non-production deployment success exercise with its exact project, provider, receipt, and cleanup checks. Expected observation: the project returns terminal succeeded, the audit agrees, and all external effects have terminal receipts. This is technical proof; use Deliver a Demo for a separate human decision.

At any failure, stop at the first failed level. Use symptom diagnosis; do not restart all roles to hide a dependency or functional failure. Recovery is the narrow owning-layer repair followed by all four levels again. Cleanup belongs to the functional exercise. Retain every command, output, exit status, selected image ID, events, audit, receipts, cleanup result, and blocked step.

Canonical Run Control Procedure

This page is the sole authority for run-control. The supported start state is a pipeline-platform.v2 and project or explicit graph at the original source and package snapshot, with writable durable storage and a reconciled prior effect state. Run from <repository-root> on the administration machine. Nova's CLI and durable journal are authoritative; process state and plugin logs are diagnostic only.

Complete Validate Before Starting, Start a Project Run, Inspect a Run, Approve or Resume a Wait, and, after interruption, Recover After Interruption. The Cancellation Boundary is mandatory. Stop on an unknown run, changed graph/package digest, unresolved effect, stale or expired wait, issuer mismatch, or terminal run. Retain input digests, output, audit, wait and signal bytes, effects and receipts, failure, retry decision, and final state. Follow Evidence to Retain for protected raw copies and signal bytes; a digest alone does not authorize deletion.

Before Each Operation

Run from <repository-root> unless a command states another location. Set no implicit Kubernetes context.

The machine that runs Nova's CLI needs Linux file locking and /usr/bin/flock with --exclusive, --timeout, and --conflict-exit-code support. Nova uses that fixed executable to protect durable state updates. A BusyBox flock that lacks these options is insufficient. Stop before a run or resume if this interface is unavailable; a lock error does not prove that a signal was accepted. Preserve the journal and diagnose the executable before retrying. Lock acquisition and release.

Record these inputs:

  • Full source commit.
  • Platform configuration path and digest.
  • Project or pipeline path and digest.
  • Selected role and plugin package revisions.
  • Operator identity for an approval or administrative decision.
  • Durable storage root and its free capacity.

Do not start work while the project repository contains uncommitted changes. The project command rejects a changed baseline or dirty worktree.

Supported Versions

Use the shared version rules. This procedure applies to pipeline-platform.v2 and the pipeline command at the recorded source revision. Start a new governed run when a platform, project, graph, package, or state format is not compatible with that revision.

Configure the Platform

The operator owns the platform configuration. Project content cannot add trusted packages, providers, adapters, or grants.

The configuration must declare these groups:

Group Operator decision Verification question
installationRoots Package locations that the registry may discover Do all paths exist at the selected revision?
trustedBuiltinRoots Package roots allowed as built-ins Does each path belong to the reviewed release?
externalTrust Allowed external source digests and attestations Does each external package match its approved digest?
providers One selected provider for each capability Does the provider registration exist and activate?
grants Resource limits for each registration and capability Does each grant allow only the intended resource?
adapters Adapter configuration Do referenced endpoints and stores exist?
activeAdapters Adapters that start in this runtime Does every required capability have one active provider?
observers Observer configuration Is required delivery reachable and bounded?
storageRoot Durable run storage Is it persistent, writable, private, and monitored?
issuer fields Nova and administrative identities Do resume signals use an authorized exact identity?

Relative package and storage paths resolve from the platform file directory. This prevents the shell working directory from changing their meaning.

Source evidence — platform authority

Claim: The operator-owned platform document selects trusted package roots, providers, grants, adapters, observers, durable storage, and decision issuers. Relative paths use the platform file directory.

Implementation: The platform schema declares its required fields, schema version, and installation roots. It also declares trust, providers, and grants. It defines adapter, observer, and storage authority. The loader validates the document and resolves paths from its directory.

Contract or setting: pipeline-platform.v2 is the required schema version.

Test evidence: The platform test checks path resolution, immutability, validation, and rejection of project-controlled installation roots. The test passed on 2026-09-16.

Validate Before Starting

Compile the project without running stages:

npm run pipeline -- \
  --platform "<platform.json>" \
  --project "<project.json>" \
  --compile "<new-pipeline.json>"

The output path must not exist. The compiler refuses to overwrite it.

Expected output contains:

  • status equal to compiled.
  • One derived runId.
  • stageCount.
  • definitionDigest.
  • completionScope.

Compilation validates runtime registrations and grants. It does not call an external provider or prove deployment reachability.

Review the compiled graph for stage types, dependencies, limits, and selected repair paths. Retain its digest with the run record.

Start a Project Run

Starting condition:

  • Project repository HEAD equals baseRevision.
  • Project repository has no uncommitted file.
  • Platform storage has enough monitored capacity.
  • Required providers and adapters are reachable.
  • No existing process owns the same intended run.

Start the run:

npm run pipeline -- \
  --platform "<platform.json>" \
  --project "<project.json>"

Expected output is one JSON object. It includes runId, status, completionScope, acceptanceReadiness, and stage states.

Exit code zero means the returned run status is succeeded. It does not mean human acceptance or complete live acceptance.

For an explicit graph, use:

npm run pipeline -- \
  --platform "<platform.json>" \
  --pipeline "<pipeline.json>" \
  --run-id "<new-run-id>"

Use a new run identity. Do not reuse a prior terminal run identity.

Inspect a Run

Before every audit, recovery, or resume command, confirm that the run owner has exited and no new operation can write this run or its adapter stores. Make a new verified capture for each command, including a retry or a deliberately wrong signal. Stop if ownership is unknown. Use the original platform path and run ID from the retained start command. Do not discover the run by auditing it first.

Audit is not a read-only storage operation. The audit reader opens FileJournal. It constructs FileJournal, creates an append-lock file, and acquires its lock. If events.jsonl ends without a newline, the constructor removes all bytes after the last newline and synchronizes the shorter file before it parses the retained records. It can therefore change evidence even when audit later fails. A complete hash chain needs no tail repair. Recovery and resume also open journals through this constructor; they can create locks and repair tails before rejecting a run or signal. Constructor and tail recovery and append-lock creation define these storage effects.

Preserve the raw run directory before every audit, recovery, or resume, whether or not the prior command ended cleanly. Also preserve the owning adapters' stores through their declared backup procedure while their writers are stopped. The copy must retain partial bytes, original signals, effects, snapshots, and lock files. Do not parse, truncate, or repair the source to make the copy pass.

In Bash at the repository root, set the platform and run ID from the original command record. Set RUN_CONTROL_EVIDENCE_ROOT to an existing private durable directory selected by the incident audit owner, outside the run and adapter stores. The owner must confirm its capacity, access restrictions, retention period, and protection from automatic temporary-file removal before capture. Stop if that location or its retention authority is absent. Define preserve_run_state in the same terminal. It uses the platform loader and the actual run-root resolver without opening FileJournal. The resolver selects the hashed or verified legacy directory. Each call makes a new restricted copy outside the run root and verifies all file bytes. Symlinks and special files require the owning store's backup procedure; this command stops on them.

export RUN_CONTROL_PLATFORM="<original-platform.json>"
export RUN_CONTROL_RUN_ID="<original-run-id>"
export RUN_CONTROL_EVIDENCE_ROOT="<absolute-private-durable-evidence-root>"
preserve_run_state() {
  umask 077
  local observation_root
  test -n "${RUN_CONTROL_EVIDENCE_ROOT:-}" && test -d "$RUN_CONTROL_EVIDENCE_ROOT" || return 1
  observation_root=$(mktemp -d "$RUN_CONTROL_EVIDENCE_ROOT/nova-raw-state.XXXXXXXX") || return 1
  export RUN_CONTROL_OBSERVATION_ROOT="$observation_root"
  node --input-type=module <<'NODE'
import fs from 'node:fs';
import path from 'node:path';
import crypto from 'node:crypto';
import assert from 'node:assert/strict';
import { loadPlatformConfig } from '@kubeclaw/plugin-foundation/config/platform';
import { runRoot } from './skills/nova/core/execution/run-root.ts';
import { parseHashJournal } from './skills/common/plugin-runtime/foundation/observability/hash-journal.ts';
const platform = loadPlatformConfig(process.env.RUN_CONTROL_PLATFORM);
const runId = process.env.RUN_CONTROL_RUN_ID;
const source = runRoot(platform.storageRoot, runId);
const target = process.env.RUN_CONTROL_OBSERVATION_ROOT;
if (!fs.lstatSync(source).isDirectory()) throw new Error('Run directory is required');
if (target === source || target.startsWith(source + path.sep)) throw new Error('Evidence must be outside the run root');
function inventory(root, relative = '') {
  return fs.readdirSync(path.join(root, relative)).sort().flatMap(name => {
    const file = path.join(relative, name);
    const stat = fs.lstatSync(path.join(root, file));
    if (stat.isDirectory()) return inventory(root, file);
    if (!stat.isFile()) throw new Error('Unsupported evidence entry: ' + file);
    const bytes = fs.readFileSync(path.join(root, file));
    return [{ path: file, bytes: bytes.length, sha256: crypto.createHash('sha256').update(bytes).digest('hex') }];
  });
}
const original = inventory(source);
if (!original.some(file => file.path === 'events.jsonl')) throw new Error('Event journal is required');
fs.cpSync(source, path.join(target, 'run'), { recursive: true, force: false, errorOnExist: true });
assert.deepEqual(inventory(source), original);
assert.deepEqual(inventory(path.join(target, 'run')), original);
fs.writeFileSync(path.join(target, 'raw-manifest.json'), JSON.stringify({ runId, source, capturedAt: new Date().toISOString(), files: original }, null, 2) + '\n', { flag: 'wx', mode: 0o600 });
console.log(JSON.stringify({ rawState: target, runId, source, filesVerified: original.length }));
for (const entry of original.filter(entry => entry.path.endsWith('.jsonl'))) {
  const file = path.join(target, 'run', entry.path);
  parseHashJournal(fs.readFileSync(file), file);
}

}
preserve_run_state || exit 1

The helper verifies the raw copy before it parses the copied journals. Even when a partial record causes parsing to fail, keep that directory and manifest. Require exit zero before ordinary audit, recovery, or resume. Comparison failure means the copy is not a verified consistency point. Stop and establish the stopped writer state before making a new copy. Hash equality checks the copied bytes; it does not prove that every external effect completed.

For non-mutating journal inspection, use the existing strict parser on the preserved bytes. It rejects an incomplete final record, empty records, wrong sequence, wrong previous hash, or wrong record hash. It does not repair files or create locks. The pure parser defines these rejection rules. This command checks every journal below the preserved run root:

node --input-type=module <<'NODE'
import fs from 'node:fs';
import path from 'node:path';
import { parseHashJournal } from './skills/common/plugin-runtime/foundation/observability/hash-journal.ts';
const root = path.join(process.env.RUN_CONTROL_OBSERVATION_ROOT, 'run');
function inspect(directory) {
  for (const name of fs.readdirSync(directory).sort()) {
    const file = path.join(directory, name);
    const stat = fs.lstatSync(file);
    if (stat.isDirectory()) inspect(file);
    else if (!stat.isFile()) throw new Error('Unsupported evidence entry: ' + file);
    else if (name.endsWith('.jsonl')) {
      const records = parseHashJournal(fs.readFileSync(file), file);
      console.log(JSON.stringify({ file, records: records.length, journalHead: records.at(-1)?.hash ?? null }));
    }
  }
}
inspect(root);
NODE

Stop on a parse error. Keep the complete raw copy, including the rejected tail. Determine which writes and external effects were interrupted. Do not use audit's automatic truncation as proof of successful recovery. If the owning incident procedure permits canonical tail recovery, keep the verified raw copy first, reconcile external effects, then record the audit or recovery command and its actual changes. A checksum proves byte preservation, not permission to retry an accepted external request.

For a complete verified journal, use the Core audit command for either command form. Capture its outputs and exit status in the retained observation directory:

npm run pipeline -- \

  --audit "$RUN_CONTROL_RUN_ID" \

printf '%s\n' "$audit_status" > "$RUN_CONTROL_OBSERVATION_ROOT/audit.exit" || exit 1

The command rebuilds its audit view from durable run state. Retain the whole output; npm can print a script banner before the CLI JSON. Compare it with the preserved journal and any previously trusted journal head. A new internally valid chain alone cannot prove that no old records were lost.

Approve or Resume a Wait

The CLI uses a typed resume-signal file. It does not provide a separate approve verb.

Before creating a signal, complete Inspect a Run. Use the original platform, run ID, project or graph, package snapshot, storage root, and runtime configuration from the retained start record. Confirm stopped run and owning-adapter writers, preserve new verified raw run and adapter copies, and require strict parsing of the copied journals. Read the active wait from that preserved evidence. Stop on unknown ownership, changed identity, failed copy verification, incomplete records, or a journal chain error. Copy no identity from an earlier wait. There is no non-mutating live audit command that can replace these prerequisites.

Read waitId, signalType, authorizedIssuer, expiresAt, and the payload requirements from the active wait-request.v2 record. The signal must contain all eight fields in this example:

{
  "schemaVersion": "resume-signal.v2",
  "signalId": "signal:approval-2026-09-17T120000Z",
  "idempotencyKey": "approval:wait-7:decision-1",
  "waitId": "wait:7",
  "signalType": "approval.resolved",
  "issuer": {
    "type": "operator",
    "id": "operator:release"
  },
  "issuedAt": "2026-09-17T12:00:00.000Z",
  "payload": {
    "decision": "approved",
    "issuer": {
      "type": "operator",
      "id": "operator:release"
    },
    "reason": "Approved the exact source and report in wait:7."
  }
}

This example is valid for the shared envelope schema. Its payload is the approval payload used by the approval path. Another wait type can require a different payload. Never copy this payload without checking the active wait.

The issuer object is unsigned and self-asserted by the caller. Nova checks that its type and ID equal the active wait's authorizedIssuer, but the signal schema contains no signature and the CLI does not authenticate the human or an external identity provider. Protect access to signal creation and the CLI as the effective authority. Do not describe issuer matching as identity proof.

Apply these matching rules:

  • Create a new signalId for one decision event. Nova uses it as the cause of the wait.resolved event.
  • Create one idempotencyKey for the exact signal content. Reuse that key only to retry the same bytes. Signal storage treats an identical stored record as a no-op and rejects the same key with different content. A retry after wait resolution is stale and stops before this storage check.
  • Copy waitId and signalType from the active wait.
  • Copy the authorized issuer type and ID. This satisfies runtime matching only; it does not authenticate who created the file.
  • Set issuedAt to a valid date-time at or after creation of the active wait.
  • Build payload from that wait's request and plugin contract. Include the current source, decision, or repair digest when that contract requires it.

Nova validates the closed envelope before recording the accepted signal and its durable wait.resolved transition. It rejects unknown fields, a stale or unknown wait, an expired wait, a mismatched type or issuer, and a signal issued before wait creation. After Nova records one signal for a wait, a different signal cannot resolve that wait again.

Storage can change before those checks. Resume opens the administrative and event journals before wait and signal validation, and run ownership acquires durable lock state first. Opening a journal can create an append lock or truncate an incomplete tail. A rejected envelope, wrong issuer, stale wait, or terminal run therefore does not prove that canonical files are unchanged. Preserve original raw bytes through Inspect a Run before every submission.

Use an operator-controlled signal file with restricted permissions. Before each submission below, including a retry, replay check, or wrong-signal check:

  1. Reconfirm the original platform and run ID, project or graph bytes, package snapshot, storage root, and runtime configuration against the retained start record. <original-project.json> and <original-pipeline.json> mean those exact original inputs, not a new candidate.
  2. Confirm the prior run owner has exited. Stop new writes to the run and its owning adapter stores. Unknown ownership stops the command; containment alone does not prove that an external effect completed.
  3. Reconcile accepted external effects through their owning contracts. Stop while any outcome is unknown or no supported continuation exists.
  4. Follow Inspect a Run to make and verify a new complete raw run copy and new owning-adapter copies through their declared backup procedures, with writers stopped. Define its preserve_run_state helper and evidence-root inputs in this Bash shell.
  5. Require successful strict parsing of every copied run journal. Retain raw bytes and stop on a copy, identity, incomplete-record, sequence, or hash failure. Do not use automatic tail truncation to make submission possible.
  6. Verify that the signal still names that active unexpired wait. Retain the exact signal bytes, ID, issue time, and idempotency key. Submit one of the following forms, using the same original identities.

Project form:

preserve_run_state || exit 1
resume_status=0
npm run pipeline -- \
  --platform "$RUN_CONTROL_PLATFORM" \
  --project "<original-project.json>" \
  --signal "<resume-signal.json>" \
  > "$RUN_CONTROL_OBSERVATION_ROOT/resume.stdout" \
  2> "$RUN_CONTROL_OBSERVATION_ROOT/resume.stderr" || resume_status=$?

For an explicit graph, supply the original run identity:

resume_status=0
npm run pipeline -- \
  --platform "$RUN_CONTROL_PLATFORM" \
  --pipeline "<original-pipeline.json>" \
  --run-id "$RUN_CONTROL_RUN_ID" \
  --signal "<resume-signal.json>" \

Expected observation: an accepted signal records one matching resolution, and continued execution gives the resumed stage a new attempt identity. Exit zero requires succeeded; a nonzero exit can contain a waiting, failed, blocked, or rejected result. Retain stdout, stderr, and the actual exit status before any follow-up. The command response alone does not prove adapter or external process quiescence. If the response or exit status was lost, retain partial output and record that result as not observed; do not invent an exit status.

After every submission, including rejection or a lost response, confirm that the owner has exited and re-establish stopped run and adapter writers. If ownership is unknown, retain the previous capture and command output and stop; do not audit or submit again. Otherwise make new verified run and adapter copies through Inspect a Run, require strict copied-journal inspection, then capture its audit outputs and exit status. Keep the previous captures and compare the new journal head, original identities, actual wait transition, attempt budget, and external receipts with the submitted signal. Do not reuse the pre-submission copy for this later audit.

Stop after an issuer mismatch, expired wait, digest mismatch, or stale signal. Do not edit the journal or change the signal identity to force acceptance. An exact retry needs the same bytes and key, a still-active wait, known effect outcomes, and the complete fresh preservation sequence above. A replay after resolution is stale or terminal and does not prove unchanged lock files. Any later incident-owner-authorized canonical tail repair must retain the verified original raw bytes and record the command and its actual changes.

Source evidence — signal contract and replay rules

Claim: A resume signal uses a closed eight-field envelope. Nova compares its caller-supplied issuer with the active wait. An identical retry has no second effect, and a conflicting retry fails.

Implementation: Nova validates wait identity, signal type, issuer, expiry, and issue time. Nova makes identical retries idempotent and permits only one recorded signal for each wait.

Contract or setting: The contract requires all eight envelope fields and rejects extra fields.

Test evidence: The recovery test exercises accepted, repeated, stale, and expired signals. The publication check also validates the example on this page against the canonical schema.

Revision: 1c30980c132e3ff0b45dc8eeaf4b46a37d6d77de.

Limit: The envelope has no signature. Its issuer is self-asserted by the caller, and repository checks do not authenticate the human or external identity provider.

Recover After Interruption

Recovery reopens durable state after a process interruption. It does not approve a wait or resolve an uncertain external result.

Before every audit or recovery attempt after interruption, including a retry, stop new admission, confirm that the prior owner has exited, and verify stopped owning-adapter writers. Follow Inspect a Run to preserve and verify new raw run and adapter copies through their declared backup procedures. Define its preserve_run_state helper and evidence-root inputs in this Bash shell; require strict copied-journal parsing before the command. Stop on an incomplete or corrupt journal. Audit can truncate an incomplete tail; retain the original bytes before any permitted canonical repair. Confirm the original platform, graph or project, package snapshot, run ID, storage root, and configuration. Retain the audit output only after this preservation step. Reconcile every accepted external effect that lacks a terminal receipt. Stop while any outcome remains unknown.

Project form, with the original project bytes:

preserve_run_state || exit 1
recovery_status=0
npm run pipeline -- \
  --platform "$RUN_CONTROL_PLATFORM" \
  --project "<original-project.json>" \
  --recover "$RUN_CONTROL_RUN_ID" \
  > "$RUN_CONTROL_OBSERVATION_ROOT/recovery.stdout" \
  2> "$RUN_CONTROL_OBSERVATION_ROOT/recovery.stderr" || recovery_status=$?
printf '%s\n' "$recovery_status" > "$RUN_CONTROL_OBSERVATION_ROOT/recovery.exit" || exit 1

Explicit graph form:

preserve_run_state || exit 1
recovery_status=0
npm run pipeline -- \
  --platform "$RUN_CONTROL_PLATFORM" \
  --pipeline "<original-pipeline.json>" \
  --recover "$RUN_CONTROL_RUN_ID" \
  > "$RUN_CONTROL_OBSERVATION_ROOT/recovery.stdout" \
  2> "$RUN_CONTROL_OBSERVATION_ROOT/recovery.stderr" || recovery_status=$?
printf '%s\n' "$recovery_status" > "$RUN_CONTROL_OBSERVATION_ROOT/recovery.exit" || exit 1

Recovery must use the original graph and package snapshot. Start a new run when governed configuration must change.

Expected observation: a permitted recovery writes one JSON result for the same run ID. Exit code zero requires terminal status succeeded; retain a nonzero result as a failed or blocked recovery, not as proof that restart completed. Recovery opens journals and can reconcile observer state before returning. It can change journals, effects, observer state, and adapter stores, including before a failed or blocked return. The pre-recovery capture cannot prove the bytes that the next audit will open.

After every recovery attempt, including failure, rejection, or a lost response:

  1. Retain the pre-command raw copies, available command stdout/stderr, and actual exit status. Record a lost response or exit status as not observed. Confirm that the run owner has exited and re-establish stopped run and owning-adapter writers. Stop if ownership is unknown.
  2. Reconfirm the original run, platform, project or graph, package, storage, and configuration identities. Make and verify new adapter-store copies through their declared backup procedures, then call preserve_run_state again through Inspect a Run. Require successful strict parsing of every copied run journal. Keep rejected bytes and stop on failure.
  3. Only then run the audit block in Inspect a Run. It captures stdout, stderr, and the actual exit status in this new observation directory. Never reuse the pre-recovery copy or overwrite the earlier audit.
  4. Compare the before/after audits, original graph and package identities, committed journal heads, external effects and receipts, and returned state. A successful recovery needs a final audit that agrees with terminal succeeded and contains no unexplained duplicate effect. A failed, waiting, blocked, or uncertain result remains that result.

Before any further recovery retry, repeat the original-identity, stopped-writer, new raw run/adapter copy, and strict-inspection prerequisites. Later authorized canonical tail repair retains the original bytes first and records its actual changes; it does not turn an uncertain external outcome into success.

Use the exact failure before choosing the next action:

Observation Meaning Safe action
RECOVERY_SIGNAL_REQUIRED:<wait-id> The run has an active wait; restart cannot invent its decision Read the active wait and use Approve or Resume a Wait with one matching signal
RECOVERY_RUN_TERMINAL The durable run already ended as succeeded, failed, blocked, or cancelled Do not recover it; retain the audit and start a new governed run only for new work
RECOVERY_COOLDOWN_NOT_DUE:<stage-id>:<time> A persisted retry time has not arrived Do not bypass the clock; wait until the recorded time, then repeat the same recovery command with new stopped-writer raw run/adapter copies and strict inspection
RECOVERY_GRAPH_*, RECOVERY_PIPELINE_ID_MISMATCH, or PROJECT_RECOVERY_RUN_MISMATCH The supplied graph, project, or run does not match durable state Restore the original input bytes; never edit the snapshot or reuse the run ID for a changed graph
RECOVERY_PINNED_PACKAGE_*, RECOVERY_PACKAGE_UPGRADE_*, or RECOVERY_REGISTRY_SNAPSHOT_INVALID Installed package identity differs from the recorded snapshot Restore the recorded package set; use only the separate authorized package-upgrade procedure when its exact contract applies
RECOVERY_RUNTIME_CONFIGURATION_MISMATCH or RECOVERY_DEPENDENCY_IDENTITY_MISMATCH Runtime configuration or dependency identity changed Restore the recorded runtime configuration and dependency set, or start a new governed run
RECOVERY_EFFECT_OUTCOME_UNRESOLVED:<effect-id> An accepted external request has no known receipt outcome Query the external authority with the original identity and reconcile it before any recovery retry
RECOVERY_EXTERNAL_CONTINUATION_REQUIRED:<effect-id> An external effect has a receipt, but its interrupted attempt needs explicit continuation Follow the owning plugin or provider continuation contract; do not replay the effect through generic recovery

Recovery has no separate temporary runtime object to clean up. Preserve all before/after raw run and adapter captures, manifests, partial or rejected tails, audits, exact commands, output, exit status, effect queries and receipts, repair changes, and the final decision under Evidence to Retain. Do not delete a nova-raw-state.* observation directory because its digest was recorded or a later command passed. Only a successful recovery result plus the matching final audit and reconciled external receipts proves the intended recovery; containment or a completed audit alone does not prove success.

Cancellation Boundary

The current pipeline CLI has no supported operator cancellation command. Do not present process termination as durable run cancellation.

An internal abort signal can cancel active work during runtime shutdown. That mechanism is not an external operator control surface.

When urgent containment is necessary:

  1. Preserve available command, process, and component observations through supported paths. Do not audit while run or adapter writers remain active.
  2. Stop new admission through the owning service boundary.
  3. Use the approved incident process for workload containment.
  4. Reconcile every accepted external effect.
  5. After the owner has exited and run/adapter writers are stopped, complete Inspect a Run before audit or another run-control command. Preserve new verified raw run/adapter copies and strictly inspect the copied journals. Unknown ownership or rejected bytes stops this inspection path.
  6. Do not claim cancelled unless durable lifecycle evidence records it.

This is an implementation limit, not a documentation shortcut.

Inspect Results and Demo Readiness

A successful run can report technical-only or demo-handoff completion. Only the latter can report ready-for-acceptance.

Human acceptance remains a separate action. It binds to the exact source, run, result, and exposed demo.

Check result artifacts through their owning store. Verify content digests before sharing or importing them.

For exposure and handoff, follow Deliver a Demo. That procedure supplies a local contract rehearsal and identifies the additional authorities required for live delivery. KubeClaw does not supply a complete live demo-delivery journey. Stop before Tailnet exposure until product operations has registered the deployment procedure, stage configuration, exposure receipts, and cleanup required by that canonical procedure.

Safe Retry Decision

Every permitted audit, recovery, or signal retry must first repeat the original-identity, stopped run/adapter writer, new verified raw run/adapter copy, and strict copied-journal inspection steps in Inspect a Run. An earlier successful capture does not cover a later command's storage state. Stop if a required check or owning-store backup procedure is unavailable.

Condition Next action
Command failed before durable request acceptance, with a verified complete journal and unchanged active authority Correct the rejected input and review one submission
Durable request exists with a terminal failure Follow its declared retry or repair decision
Request exists and provider outcome is absent Inspect through a documented provider status operation; if the outcome remains uncertain, preserve evidence, stop, and escalate
Provider completed but local response was lost Use an exact provider-specific idempotent import operation only when its contract documents one; otherwise preserve evidence, stop, and escalate
Wait remains active, unexpired, with complete history and no prior resolution Follow Approve or Resume a Wait, including new stopped-writer raw run/adapter copies and strict inspection before each submission; retain exact signal bytes and identities
Wait expired or resolved, or signal identity conflicts Stop; preserve raw state before audit. Do not issue a new signal identity to force acceptance
Graph, package, or policy digest changed Start a new governed run
Terminal run Do not recover or resume it

There is no generic Core operation that reconciles an uncertain external effect and imports its result. See the current reconciliation boundary. A provider-specific normal result import is safe only when that provider documents the request identity, result identity, idempotency rule, authority, and durable transition. External inspection alone does not authorize a retry, resume, journal edit, or result import.

Evidence to Retain

  • Platform, project, graph, and signal digests.
  • Complete command and nonsecret arguments.
  • Start output and run identity.
  • New verified raw run and owning-adapter copies and manifests before every audit, recovery, resume, retry, and wrong-signal check, and after each command before the next audit. Keep rejected or partial bytes as evidence.
  • Audit output before and after recovery or signal handling, with any tail repair recorded.
  • Provider request, receipt, and reconciliation record.
  • Artifact identities and verified digests.
  • Prism decision and demo identity when applicable.
  • Unsupported-control finding when an operation stops at a missing surface.

The incident audit owner must record each capture's durable location, access identity, retention period, and final-disposition authority. Retain complete raw run and adapter bytes, manifests, rejected tails, exact signal bytes, command records, and actual repair-change evidence for that period. A digest records integrity; it cannot replace the bytes. Keep these captures separate from disposable working copies. If evidence must move, use the audit owner's verified complete-copy procedure and retain its receipt; stop if byte preservation or retention cannot be proved.

Only named disposable candidate files or redundant working signal copies may be removed after their prescribed retention and the owner's recorded final-disposition decision. First prove that the original signal bytes and all required evidence remain in the protected retained capture. Original raw observation directories and their contents require the audit owner's explicit final disposition after the retention period; ordinary run cleanup does not authorize their removal.
