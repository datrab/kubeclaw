Maintain and Retire

Status: source-backed maintenance boundaries; no general runtime upgrade pair or generic rotation command is currently established Audience: release maintainer, platform operator, security operator Owner: release engineering and platform operations Evidence: versions.json; releases/ops-images.json; scripts/deploy.sh Applies to: current release-selection and deployment contracts Last verified: 2026-10-11; local projection, snippet and synthetic teardown checks only; no live upgrade, rotation or retirement result is available

Objective

Change software, data, credentials, certificates, or capacity without losing rollback evidence. Remove KubeClaw only after data and access have named owners.

Cluster Authority Binding for Every Maintenance Task

Before any cluster command on this page, complete Bind Cluster Authority. Keep the same bound shell for upgrade, rollback, rotation, GitOps, or decommission work. Every raw kubectl, Helm, or scripts/deploy.sh command below must inherit its exported read-only KUBECONFIG, NAMESPACE, and PRISM_NAMESPACE. The binding section validates and freezes both namespace names before any command here; every shown <context> must equal EXPECTED_CONTEXT. Run assert_cluster_binding immediately before each command block. Stop on any mismatch and follow the binding section's recovery; never fall back to the default kubeconfig.

Canonical Upgrade and Rollback Procedure

This section is the sole authority for upgrade-rollback. Start with a healthy installed release, independent administration, a complete old/new version pair, verified isolated restore media, enough capacity, and no uncertain external effect. Run source planning from <repository-root> and deployment checks from the administration machine. Release receipts, data-schema authorities, Helm or Git desired state, running image IDs, and application readers are authoritative.

The current compatibility matrix is deliberately empty:

Component Supported old version Supported new version Data compatibility Result
Nova/Buster runtime release None recorded None recorded Not established Stop before mutation
Prism application and database None recorded None recorded Not established Stop before mutation
Shared Redis/PostgreSQL/LiteLLM None recorded None recorded Component-specific proof absent Stop before mutation

An image, chart, or tool version in versions.json is not an upgrade-pair claim. Until a row names and proves an exact pair, the commands later in this page may verify or redeploy the currently selected release but must not be used to claim an upgrade.

For a future supported pair, complete Prepare a Release Change, Change Plan, Render and Compare, Upgrade Order, the component section, and Rollback Decision. Gate every step on the expected native and application observation. Abort before the irreversible point on a failed gate. After an incompatible data write, image rollback is forbidden; use the declared data recovery or forward repair.

Expected completion is the intended immutable release, compatible data, four-level readiness, functional reader success, and reopened admission. Retain old/new receipts, pair proof, backup and restore evidence, rendered diff, commands and output, each health gate, irreversible point, running identities, rollback or forward-repair result, cleanup, and final acceptance.

Canonical Rotation Procedure

This section is the sole authority for rotation. Start with a healthy system, complete producer/consumer inventory, credential or trust authority access, an authority-specific issue and revoke operation, a maintenance window, and a tested emergency route. Run cluster observation from the administration machine and issuance/revocation only through the external owning authority.

Before changing trust, capture non-secret references and consumers:

  -o yaml > "<evidence-dir>/credential-consumers.yaml"

Do not store Secret data. Use Credential Rotation for the ordered transition and Certificate and SPIRE Rotation for its current limit. Stop before issuance if the authority-specific command, dual-trust capability, full consumer list, positive/negative check, expiry, or rollback owner is absent. The repository provides no generic rotation command.

Expected completion is new-identity success, unrelated-identity denial, old-identity denial after revocation, all consumers healthy, temporary material removed, and an independent recovery path retained. Recovery before revocation is to restore the exact old consumer configuration; after revocation, follow the external authority's recovery process. Retain only names, versions, timestamps, consumer rollout identities, positive/negative observations, revocation receipt, cleanup, and blocked boundary.

Rotation Failure Distinction

Observation Cause class Safe response
Old identity works and new identity fails New issuance, distribution, mount, or consumer reload Keep old trust active and repair the named new path
Both intended identities fail Authority, shared trust root, or consumer configuration Stop the rotation and use independent access
New identity works and old identity still works after recorded revocation Revocation or cache propagation Keep the window open and reconcile the external authority
Unrelated identity works Grant, allowlist, or peer-verification failure Restrict access and treat the result as a security incident
Service is ready but protected data is unreadable Encryption-key or data-version mismatch Keep writers fenced and restore the exact prior key/configuration set

Canonical Decommission Procedure

This section and Controlled Retirement are the sole authority for decommission. Start only after new admission is disabled, external exposure is restricted, active and uncertain work is reconciled, final backups and isolated restore proof pass, and every Kubernetes and external resource has an owner and retain/delete decision. Run from independent administration, not the target Ops Pod.

The application namespace must be dedicated before broad teardown. If any resource in it is shared or unregistered, do not run teardown or teardown-all; use separately approved resource-specific removal instead. Before broad removal, establish the complete deletion window and compare the original and current object identities. Keep the exclusion through final verification. Retain the pre-removal inventory, final backup group, access revocation receipts, command confirmations and output, post-removal inventory, retained audit location and retention end date, and every failed cleanup. There is no automatic rollback after PVC or namespace deletion; recovery is from the final verified media through the canonical restore procedure.

Retire the Former Qdrant Installation

Use this procedure only for the former qdrant release in namespace kubeclaw. Qdrant is not a current platform dependency. A PersistentVolumeClaim (PVC) is a namespaced request to use storage. A PersistentVolume (PV) is the cluster-wide record of a volume. Its claimRef identifies the claim by namespace, name, and UID. A UID identifies one lifetime of an object. resourceVersion is an opaque version of the object. The reclaim policy selects the action after claim release. This procedure sets Delete on selected bound PVs and deletes selected PVCs. It is not a general storage cleanup command.

Run from an independent administration host and the pinned source checkout. Use Bash, Python 3, Helm, kubectl, and the shared version and tool boundary. Record actual client, server, and storage-driver versions. The platform owner must accept that combination; the repository supplies no compatibility matrix. Complete Bind Cluster Authority with NAMESPACE=kubeclaw. Keep that bound shell and its read-only KUBECONFIG.

The authenticated administrator needs PVC get/list/watch/delete access in kubeclaw and PV get/list/watch/patch access at cluster scope. Deletion waits first get the object. If it remains present, positive-timeout waits list/watch that resource with a name selector. Named StatefulSet deletion and Helm release removal also need the relevant dependent-workload get/list/watch permissions in kubeclaw, plus Helm release-record reads/deletion and removal permissions for the installed release resources. The platform owner must verify the exact resource/verb combinations for the installed release and selected clients before any destructive request; use scoped grants where the authority supports them. The script deletes StatefulSet qdrant, Services qdrant and qdrant-headless, Secrets qdrant-auth and qdrant-tls, and NetworkPolicy kubeclaw-qdrant-ingress. It attempts to delete the same-named CiliumNetworkPolicy only when its own API discovery succeeds and matches ciliumnetworkpolicies.cilium.io. Successful discovery before invocation does not guarantee successful discovery inside the script. Confirm removal later through a successful named read-back. Inventory and diagnosis need discovery, workload/event reads, and, when used, StorageClass, CSIDriver, VolumeAttachment, and controller-log reads. Confirm these permissions with the platform owner before starting. Do not grant broader access merely to make a failed command succeed. Namespace selection does not limit PV authority.

Establish the deletion window

Complete the decommission prerequisites and retained evidence decisions first. Stop former Qdrant consumers and writers. The storage owner must approve each selected claim and backing volume for deletion. Record the data owner, backup location, retention end date, disposal owner, and isolated restore result if the data must remain recoverable. Keep backups and audit evidence outside the target storage. Stop on shared storage, uncertain ownership, incomplete backup, or missing required restore proof.

Before any destructive operation, the platform and storage owners must confirm a window that excludes concurrent PVC replacement, PV recreation under a reused name, rebinding, and competing policy edits. Identify and suspend competing administrators and desired-state controllers through their owning authorities. Keep the exclusion in effect until all uncertain results are reconciled. Storage deletion controllers must remain available. Stopping consumers alone does not establish this window. Stop before running the script if the owners cannot establish or maintain it.

The script has no concurrency fence. Its initial read compares only the PV claimRef namespace/name/UID with the selected PVC. Its later JSON Patch tests those same three fields before adding persistentVolumeReclaimPolicy=Delete. It does not test PV UID, resourceVersion, or the prior policy. The later PVC delete uses the captured name without a UID precondition. The external window and the original/current comparisons below are required because these guards do not exclude replacement objects or competing edits.

The script prechecks all selected bound PV references, then uninstalls Helm and removes the named remaining workload/access resources. Only then does it patch each PV, delete its PVC, wait up to 180 seconds for that PVC, and wait up to 180 seconds for PV API deletion. A later failure can leave earlier claims or resources removed. A stored Delete policy permits irreversible storage removal after release. Neither a patch response nor a wait duration proves storage deletion. Review output for the last completed operation, but reconcile current state even on exit zero.

The script runs its Cilium API-discovery pipeline inside an if. Bash does not stop the script when that pipeline fails. For example, a discovery Forbidden error can skip Cilium policy deletion, permit later PV patches and PVC deletions, and still produce exit zero. Output is redirected during this invocation; the operator inspects it after the script returns. This procedure does not provide an automatic stop before those later writes. Review both standard output and standard error in the captured file, and perform the full original-identity and named-resource read-back even after exit zero. A discovery error or missing Cilium removal observation leaves cleanup uncertain. Stop further operator writes, retain the exclusion, and have the platform and storage owners reconcile all preceding and later effects. If successful discovery shows the API, require a successful named policy read-back; absence from a failed discovery or a failed read is not proof of removal.

Deletion-wait access can fail after the server accepted a deletion. In the pinned kubectl source, delete --wait can tolerate a Forbidden or unsupported wait result and return success. Thus an exit status alone cannot prove that the object is gone. The separate PV wait also needs list/watch access while the object remains present. Read back the original identities and deletion state through the owning authority before any continuation on a denied wait.

For each original row, copy <claim-name>, <pv-name>, and <original-pvc-uid> from before, not from a new selection. Run the PVC query for all rows; run the PV and PV-event queries only for bound rows. These queries show identities, policy, deletion state, and finalizers (entries that delay API removal until required cleanup completes). Save their output and status in new private observation files; do not overwrite the originals. --ignore-not-found permits a successful empty result, but an API error does not prove absence.

Distinguish failure before another write

On any failed or uncertain operation, stop further writes, retain the exclusion, and preserve output, status, original policy, current stored policy, identities, deleting state, events, and owner observations. Use the queries above before choosing a continuation. The following observations require different actions:

Observation Distinguishing check Safe action
Binding, tool, read, or initial ownership precheck fails Check exit/output; compare current PVC UID/volume and PV reference with before No script removal precedes a failed initial precheck. Correct access or tools through their owners; on identity mismatch stop and obtain a new plan. A pre-existing deletion remains possible.
Forbidden or Unauthorized Identify the denied request/resource/verb in output; ask the authority to verify that exact permission and read back earlier resources Stop. A denial of one request does not undo earlier removals. Do not widen grants or rerun blindly.
Discovery fails inside the script, including Forbidden, even with exit zero Review captured stderr and the named Cilium policy; read back every original PVC/PV and named release/access resource Cilium deletion can have been skipped while later storage writes completed. Later patch rejects a test, reports 422, validation failure, admission denial, conflict, or NotFound Read the same PV name and compare original UID/reference/policy/version; inspect the returned error Earlier Helm/access removal can already be complete. Preserve both states; resolve ownership or admission with the platform owner. Matching claimRef alone is insufficient.
Patch response is lost or interrupted Read original PV/PVC identities, policy and deletion state; ask the storage owner for the original handle's result No response does not mean no write. Delete may already be stored and deletion may have started. Stop until reconciled; do not resend the patch.

Controllers can continue deletion while the script is stopped. A controller retry is not authority for an operator retry. Any continuation requires owners to reconcile each original resource and backend effect, confirm the exclusion, and specify the exact remaining operation and new evidence. There is no general partial-resume command. Do not blindly repeat the script or change the policy back as rollback. A policy change cannot recover erased data. After storage removal, recovery requires retained verified media and the storage owner's restore procedure.

Verify completion and retain evidence

Repeat the release, named workload/access, and original PVC/PV observations. Repeat successful API discovery through the platform authority, and read back the named Cilium policy if the API is present. If discovery fails, keep Cilium cleanup unresolved; do not treat the script's skipped branch as API absence. Expected Kubernetes result: the former release and named resources are absent, each original selected claim is absent, and each bound original PV is absent, with successful reads and no replacement UID. An unbound row has only a claim-removal result. Record unexpected new selected claims and stop; do not expand removal scope. Obtain separate storage-owner disposal receipts for each original handle and the selected retention decisions. API absence and the script's completion message do not prove backend erasure. Roll out updated agents through their approved deployment procedure to remove former Qdrant health probes.

Retain the owners' approvals and window record, actual versions, source commit, original/current inventories, original policy and storage identity, sanitized output/status/timestamps, observations, backend receipts, backup/restore proof, retention end date, recovery owner, and unresolved cleanup. The script deletes its temporary claim inventory on exit; that inventory is not retained evidence. Release the exclusion only after owner reconciliation. Dispose of temporary administration access through its credential owner after verification; retain required audit and recovery data until its recorded retention end. No live retirement, backend erasure, or restore result is established by this guide.

Source evidence — bounded Qdrant retirement

Claim: The script's fixed selector captures claim name/UID/volumeName. The script prechecks the reference and removes release/access resources. It then applies three reference tests plus add Delete, deletes PVCs by name, and waits for PVC/PV API deletion.

Implementation: Intent, context, tools, and temporary inventory. Exact selection. Precheck. Release/resource removal. Patch and waits.

Contract or setting: The seven selected existing-PV receiving contracts explain the ordered patch, guard limits, and controller/backend boundary. These source expectations use Kubernetes v1.35.0, not a live compatibility claim. The API server rejects malformed or failed JSON patches. Deletion reconciliation is separate, and backend removal can precede finalizer failure.

Wait permissions and limit: Positive-timeout deletion waits get, then list/watch the named resource, with the selected list/watch calls. The delete command invokes that wait and can tolerate a denied or unsupported wait. These pinned client expectations do not prove the operator's actual permissions.

Reason: The producer comment says PVC deletion alone can leave retained PVs and data. Inference: setting Delete connects approved claim retirement to storage disposal. The historical reason for these specific incomplete concurrency guards is unknown. Platform operations owns reassessment when ownership, drivers, or retention requirements change.

Test evidence: Local command syntax, synthetic exact selection, sanitized capture, read-only observation, discovery-denial and binding-refusal checks do not execute retirement against Kubernetes.

Supported Versions

Maintenance Principles

  • Change one governed release set, not isolated image tags.
  • Use immutable image and code-bundle identities.

Establish the complete deletion window

Before any removal, the platform and storage owners must establish and verify an externally enforced exclusion for the complete deletion window. It must prevent recreation of the original namespace, replacement of a PVC or PV under a reused name, new PVC creation, new provisioning, rebinding, and competing configuration or retention changes. Identify every administrator, controller, operator and desired-state reconciler that can make those changes. Their owners must restrict or suspend those actions and reconcile in-progress provisioning before approving removal. Keep storage deletion controllers available to complete approved disposal. Record the enforcement method, owners, affected identities, start time, checks that prove exclusion, and loss-of-exclusion stop condition. Stopping application writers alone does not establish this window.

Preserve an independently approved original inventory outside the target namespace and storage. For each namespace, retain its name and UID. For every PVC, retain its name, namespace, UID, bound PV name and storage class. For each bound PV, retain its name, UID, complete claim reference (namespace/name/UID), reclaim policy, driver and provider asset identity. The storage owner supplies non-CSI and Pending-claim identities, reconciliation of in-progress allocation, and exact provider observation procedures; an absent PV does not prove that no asset exists. Retain provider snapshots, replicas and backup/export identities with each data owner's separate retain/delete approval and recovery scope. The names-only resource listing above is discovery, not this identity record.

Immediately before removal, capture current identities in new evidence files through the owning authorities. Compare the full namespace/PVC/PV sets, UIDs, bindings, policies and provider assets with the approved original inventory. Review controller-driven version or disposition changes with both owners. Stop for a new or replacement object, changed binding, incomplete inventory, failed read, missing provider proof, or any unapproved data scope. Require a new reviewed plan rather than expanding the deletion set. These comparisons are non-atomic observations: they do not make a later name-based delete safe by themselves. The externally enforced exclusion must remain proven during all removal, uncertain-result reconciliation and final independent verification.

If either owner cannot prove or maintain that exclusion, do not run teardown or teardown-all. Keep the data and evidence. The owners must supply a separate exact-resource procedure that protects each original identity at the destructive request, covers backing assets and dependent resources, states required rights, and provides independent read-back and recovery. There is no universal fence or provider cleanup command in this repository. Broad removal can resume only after both owners qualify the exclusion and unchanged approved identities; an alternative can proceed only after its own identity and recovery proof.

2. Restrict exposure and stop new work

Disable public or Tailnet admission, new pipeline/project admission, scheduled jobs, and external writers through their owning authorities. Revoke interactive access that is no longer needed, while retaining one independent emergency administrator until verification finishes.

The repository has no generic command for DNS, OAuth, Tailnet, GitHub, registry, backup, or monitoring authorities. Record each authority's exact command and receipt in the plan. Stop if any required authority-specific operation is missing; do not delete workloads first and leave reachable unmanaged access.

3. Resolve existing work

Let safe work finish. Reconcile external effects. Record blocked work and its evidence.

The CLI has no separate cancel command. Use the approved incident boundary for necessary containment.

4. Export and back up

Create final verified backups for every authoritative store. Copy them to the retained independent destination.

Export release receipts, configuration digests, decisions, and audit records. Keep credentials in their separate authority.

Re-run integrity and the supported isolated component restore before deletion. Stop if a final group or its encryption/key authority is incomplete.

5. Revoke workload identities and external resources

After work is quiescent and evidence is independently readable, revoke workload credentials, SPIRE registrations, deploy keys, provider tokens, registry write access, and application-specific DNS or exposure. teardown is destructive even though it keeps the namespace and Secrets. After other removals, cleanup_leftover_pvcs() enumerates and deletes all remaining PVCs by name without a UID precondition, including claims retained by a Helm keep policy.
