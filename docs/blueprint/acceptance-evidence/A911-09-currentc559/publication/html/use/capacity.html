Purpose

Measure pressure before it becomes data loss and apply retention only where an authority defines eligible data and a safe deletion mechanism. This page is the only canonical capacity and retention procedure.

Canonical Capacity and Retention Procedure

Supported start state, version, location, and authority

Start with an existing reachable cluster, an explicit context and namespace, and independent access that does not depend on the workload being measured. Apply the shared version and tool boundary before measuring. Record the actual kubectl client and Kubernetes server versions, selected Helm version when used, and each storage or product query tool/server pair. Record the installed release, immutable images, data formats, and the platform and component owners' acceptance of these actual combinations. Stop until they accept the combination. Build inputs in versions.json do not establish compatibility: general build tools and Ops image overrides select different clients. KubeClaw does not define a Kubernetes, CSI (storage driver), registry, Redis, PostgreSQL, or filesystem compatibility range.

Run cluster commands from the administration machine. Run product-specific queries only through the owning product's documented administration surface. The Kubernetes API is authoritative for requested PVC size and object state; the CSI/storage product is authoritative for free bytes and expansion; each application is authoritative for whether records are disposable.

Before any cluster command on this page, complete Bind Cluster Authority. Keep the same bound shell for the whole measurement or retention task. Every raw kubectl, Helm, or scripts/deploy.sh command below must inherit its exported read-only KUBECONFIG; every shown <context> must equal EXPECTED_CONTEXT. Run assert_cluster_binding immediately before each command block. Stop on any mismatch and follow the binding section's recovery; never fall back to the default kubeconfig.

Preconditions

Use Bash for the command blocks. Replace every placeholder before execution. Freeze the recorded context, namespace list, evidence directory and observation window for this task; a changed target requires a new binding and inventory. Keep credentials outside both the evidence directory and the command output.

Kubernetes RBAC (API authorization) must permit get on the named kube-system namespace for its UID, and get on each independently supplied service namespace for its UID. Record those namespace UIDs before inventory. The inventory requires list on core persistentvolumeclaims, pods, and events, and on batch cronjobs and jobs in each exact namespace. Metrics capture additionally requires list on pods.metrics.k8s.io there. Client discovery/version requests need the applicable non-resource get permissions on /version, /api, /api/*, /apis, and /apis/*. If a selected owner method reads a named StorageClass, PV, Node, or kubelet configuration, include its exact get permission separately. The installation access inventory explains cluster versus namespace and native-node access; its installation write grants are not measurement prerequisites.

Before a product query, its owner must supply the exact read-only method, identity, tool/version, endpoint or filesystem, selector, and permissions. Examples are a database role's approved read queries, Redis ACL commands, or host-file read access; Kubernetes access does not grant them. Record only non-secret identity and permission evidence. Permission denial stops the affected measurement. Ask that owner to correct access or supply an authorized read-only observation; do not select a more privileged credential.

  • <context>, <namespace>, <evidence-dir>, and the observation window are recorded.
  • <evidence-dir> is new, mode 0700, and outside workload PVCs.
  • Data owners are named for Nova runs, Buster jobs, Prism data and backups, Redis, LiteLLM, registry data, BuildKit cache, Ops data, and telemetry.
  • No deletion, compaction, backup, restore, rotation, or release change is in progress.
  • The storage owner has supplied a real free-space measurement method. PVC capacity alone is not free space.

Stop if any store has no owner, the context is unexpected, the evidence path is inside disposable storage, or measuring a store would require an unapproved credential.

1. Capture the cluster-side inventory

Record every namespace that the selected services use. Include the bound application and Prism namespaces, and each infrastructure namespace supplied by its owner. Run the block below once per recorded namespace. Replace <namespace> with that namespace; keep the bound cluster context unchanged. Use a separate output prefix for each namespace. An access failure leaves that service's budget incomplete and requires its owner to supply the measurement.

Create the evidence directory once before the first capture:

umask 077
mkdir "<evidence-dir>"

For each namespace, first read its UID and compare it with the identity independently supplied by the platform owner. Stop on a missing or different UID; a recreated namespace is a new target even when its name is unchanged.

assert_cluster_binding
kubectl --context "<context>" get namespace "<namespace>" \
  -o jsonpath='{.metadata.uid}{"\n"}' > "<evidence-dir>/<namespace>-uid.txt"

For each recorded namespace whose UID matches, capture its inventory:

assert_cluster_binding
kubectl --context "<context>" -n "<namespace>" get pvc \
  -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,CLASS:.spec.storageClassName,REQUEST:.spec.resources.requests.storage,CAPACITY:.status.capacity.storage' \
  > "<evidence-dir>/<namespace>-pvc.txt"
kubectl --context "<context>" -n "<namespace>" get pods -o wide \
  > "<evidence-dir>/<namespace>-pods.txt"
kubectl --context "<context>" -n "<namespace>" get events \
  --sort-by=.metadata.creationTimestamp > "<evidence-dir>/<namespace>-events.txt"
kubectl --context "<context>" -n "<namespace>" get cronjob,job \
  > "<evidence-dir>/<namespace>-jobs.txt"

Expected observation: every selected PVC is Bound; its class, request, and capacity match the intended store; events contain no recurring mount, provisioning, eviction, inode, or space failure. A successful command does not prove free bytes inside the volume.

If Metrics Server is installed, capture workload usage separately:

assert_cluster_binding
kubectl --context "<context>" -n "<namespace>" top pods \
  > "<evidence-dir>/<namespace>-pod-usage.txt"

If this command reports that metrics are unavailable, record that observation. Do not install Metrics Server as part of this task.

For every store, record current bytes, free bytes, inode use where applicable, oldest and newest retained item, and the same measurements from at least one earlier point. Calculate the observed growth rate and exhaustion time outside the target workload. Do not infer free space from a PVC request.

Prism temporary and native limits

Ingestion uses a quarantine-only emptyDir (Pod-local temporary volume) limited to 4 GiB. Its TTL (time to live) defaults to one hour and clamps to one minute–one day; reaping runs at startup and at intervals of at most one minute. Requests are limited to 2,000,000 bytes and acquired content to 6,000,000 bytes. The authenticated DELETE /v1/acquisitions/<digest> accepts one exact 64-character lowercase hexadecimal digest and returns 204, including when already absent. Control attempts exact-digest deletion after acquisition processing, including when publication failed. It reports publication and cleanup failures rather than treating a probe as evidence of cleanup. These controls expire acquisition bytes, not durable logs, reports, artifacts or Control replay. A Pod loss or expiry requires a new bounded acquisition.

Backup headroom

Keep separate budgets for live data, completed backup groups, incomplete attempts, and an independent destination. Headroom is unused capacity reserved for the next operation. Measure both free bytes and inodes; configured byte ceilings do not prove actual filesystem space.

Prism defaults to 80 GiB per group, 90 GiB retained bytes and a one-hour operation ceiling. Its allowance is the lesser of the per-group ceiling and retained ceiling - current backup-root bytes - 1 MiB. Copy accounting also reserves per-object overhead and final metadata. The backup PVC requests 100 GiB; its storage class follows artifactStorage.storageClass when set, otherwise the cluster default. Verify the resulting bound class and usable capacity. No complete or incomplete group expires automatically.

LiteLLM recovery selects a separate 64 GiB dump ceiling, 90 GiB retained ceiling, 100 GiB PVC and 1,800-second dump timeout. Its allowance subtracts 64 MiB from retained ceiling - current backup-root bytes before applying the dump ceiling. An interrupted dump remains .incomplete-* and consumes capacity. Neither script removes the last completed group to admit the next attempt. Preserve failed staging and its error until the owning backup procedure qualifies exact cleanup; this page supplies no stage-deletion command.

3. Select a supported response

Use exactly one response owned by the affected layer:

  1. Expand the storage through the storage product's procedure, if its class and workload support online expansion.
  2. Move an already verified backup group to an independent destination.
  3. Stop new admission and drain work before product-native compaction or garbage collection.
  4. Remove a specifically identified temporary object only when its owning procedure provides a selector, receipt, and recovery boundary.

KubeClaw currently provides no general command to delete old Nova runs, Buster evidence, Prism revisions, registry layers, Redis data, LiteLLM rows, or telemetry history. The narrow local projection controls above do not provide that general deletion capability. Age, a filename pattern, and low free space are not deletion authority. Stop and escalate when the selected store has no qualified cleanup procedure.

For complete environment removal, use the canonical decommission procedure, not retention cleanup.

4. Verify and close

Repeat read-only measurements only against the unchanged recorded identities, selectors, units and windows. If the target changed, restart binding and inventory. Repeat the same measurements after the owned response. Expected observation: free capacity or forecast time increases, application readers still resolve retained data, scheduled backups still complete, and no selected object loses its authority or reference.

Stop admission and use the symptom diagnosis procedure if usage continues to grow unexpectedly, a reader fails, or deletion effect is uncertain. Do not repeat a deletion. Reconcile the product receipt and storage state first.

Recovery, cleanup, and evidence

If an expansion or cleanup fails before mutation, retain its error and leave the store unchanged. After a confirmed mutation, restore only through the canonical backup and restore procedure; do not copy individual database files back into place.

Release temporary measurement access through its issuing authority. Remove only explicitly identified disposable local files after their evidence is retained. Do not remove workload files or a backup staging directory as evidence cleanup. Retain the before/after inventory, native measurements, calculation, threshold and owner, command output, deletion or expansion receipt, application reader result, and any blocked unsupported action. Never retain secret values.
