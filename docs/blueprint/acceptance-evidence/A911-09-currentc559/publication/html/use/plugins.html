Purpose

Select, activate, observe, drain, disable, replace, or retire a plugin without allowing project content to expand trust or permissions. This page is the only canonical plugin-lifecycle procedure.

The generated plugin catalogue is the published, dynamic package list. Counts and package names are not copied here because they change with the source tree.

Complete Operator Views

The generated rows below assign every discovered package to an operator task, host, role, surface, and declared dependency. They also assign every discovered registration to its external-service evidence. Publication fails when discovery and these rows drift. Canonical Plugin Lifecycle Procedure

This procedure operates Nova pipeline-plugin-v2 registrations selected through pipeline-platform.v2. It does not install or activate the OpenClaw extensions kubeclaw-agent-observer and kubeclaw-prism, or the Codex plugin kubeclaw-ops. Use the packaged OpenClaw host route and the Codex host lifecycle boundary for their version, deployment controls, observations, disable/removal limits, owners, and safe stops. Nova compile/start/audit cannot prove their host lifecycle.

kubeclaw.openclaw-agent-events:source belongs to this Nova procedure, but also requires an actual compatible OpenClaw SDK event source in the Nova process. Apply its SDK readiness and host-event proof boundary before claiming activation. Package discovery, injected SDK tests, and provider selection do not prove configured real-host subscription.

Supported start state, version, location, and authority

Start with a clean checkout at the exact source commit, an existing pipeline-platform.v2 file, an operator-supplied project or graph that uses the plugin, and writable durable storage. Run commands from <repository-root> on an administration machine with Node.js 24. The platform configuration owner, not project content, controls installation roots, built-in trust, external digests or attestations, providers, grants, adapters, observers, and storage.

The registry supports discovery and activation of packages already present in approved installation roots. Internal APIs can copy or remove a local external package, but the repository exposes no general operator CLI for those actions. Do not turn an internal API or a filesystem copy into an undocumented operator command.

Preconditions

  • Record the source commit and SHA-256 digest of <platform.json>.
  • Identify exact package ID, registration ID, contract version, content digest, capability grants, dependencies, secret names, and every active run that pins the package.
  • Complete the per-plugin external dependency matrix above and assign an owner to every required reachability check and failure response.
  • Keep plugin code and schemas available for every nonterminal pinned run.
  • Keep secret values only in the configured secret authority. Platform and project JSON may name secrets but must not contain their values.
  • Prepare a controlled project or graph whose external effects are safe and whose success proves the selected registration.

Stop when a package identity is ambiguous, its digest or attestation is absent, a dependency has no owner, a requested grant is wider than intended, or a procedure would place a secret in evidence.

1. Discover and select

First complete the canonical Locked Dependency Installation in the disposable checkout. Its retained evidence is part of this procedure's evidence.

git status --short
git rev-parse HEAD
npm run plugin-system:inventory:check
npm run verify:plugin-packages
sha256sum "<platform.json>"

Expected observation: the worktree has no unexpected change, inventory and package verification exit zero, and the recorded platform digest matches the file to be used. Inspect the dynamic catalogue and select by exact IDs and contract version, never by discovery order.

Check these platform fields together:

installationRoots Canonical roots allowed for discovery
trustedBuiltinRoots Which discovered roots are trusted built-ins

providers One registration selected for each required capability

2. Validate a candidate configuration without starting work

Have the platform owner create <candidate-platform.json>. Then compile a controlled project to a new output path:

test ! -e "<compiled-pipeline.json>"
npm run pipeline -- \
  --platform "<candidate-platform.json>" \
  --project "<controlled-project.json>" \
  --compile "<compiled-pipeline.json>"
sha256sum "<candidate-platform.json>" "<compiled-pipeline.json>"

Expected output is a JSON object with status equal to compiled, a run ID, stage count, and definition digest. Compilation validates discovery, trust, registrations, selected providers, schemas, configuration, and grants. It does not prove an external endpoint, account, credential, or live dependency.

3. Activate and prove health

Compilation imports enabled registration modules and checks their configuration, trust, and grants. It does not call adapter factories or adapter ready(), create a run, or prove a dependency. Treat compilation as code admission: approved plugin modules are loaded even though no pipeline work starts.

A run then starts adapters in dependency order and awaits each adapter's ready() result. The host races each factory and readiness call against shutdownTimeoutMs. A readiness failure first revokes the failing adapter's context and awaits its shutdown. Only after that cleanup settles can the outer startup rollback revoke the other started contexts and attempt their shutdown. No partially started adapter set becomes the usable runtime. Failed-readiness teardown and startup rollback abort their shutdown signal after shutdownTimeoutMs, but still await the adapter's shutdown promise. An adapter that ignores the signal can therefore leave run startup pending indefinitely. Pending failed-readiness cleanup also delays the outer rollback, so the earlier adapters' contexts have not yet been revoked by that rollback. See adapter startup and shutdown limits. This startup transaction cannot reverse an external effect already accepted by a service. After compile succeeds, start the controlled project only during its approved window:

npm run pipeline -- \
  --platform "<candidate-platform.json>" \
  --project "<controlled-project.json>"

Take <run-id> from the start command when it returns one. Before audit, complete Inspect a Run in the same Bash shell. Use that original candidate-platform path and run ID, confirm the run owner has exited, stop new run and owning-adapter writes, and preserve verified raw run and adapter copies. Audit can create locks and truncate an incomplete journal tail before parsing. Require successful strict parsing of the copied journals; retain rejected bytes and stop on any failure. Define the canonical preserve_run_state helper from that section before this block:

export RUN_CONTROL_PLATFORM="<candidate-platform.json>"
export RUN_CONTROL_RUN_ID="<run-id>"
preserve_run_state || exit 1
audit_status=0
npm --silent run pipeline -- \
  --platform "$RUN_CONTROL_PLATFORM" \
  --audit "$RUN_CONTROL_RUN_ID" \
  > "$RUN_CONTROL_OBSERVATION_ROOT/audit.json" \
  2> "$RUN_CONTROL_OBSERVATION_ROOT/audit.stderr" || audit_status=$?
printf '%s\n' "$audit_status" > "$RUN_CONTROL_OBSERVATION_ROOT/audit.exit" || exit 1
test "$audit_status" -eq 0 || exit 1

Retain the raw-copy path, manifests, audit stdout/stderr, and actual exit status. If an owner later authorizes canonical tail repair, keep original bytes, reconcile external effects, and record the command and actual file changes. If startup remains active, ownership is unknown, or adapter stores cannot be quiesced and copied, stop before audit. Keep the original command output and use the component owner's supported observation path. Process containment does not prove the controlled project succeeded.

Stop new admission on adapter startup or readiness failure, or when startup remains pending after its timeout. Retain the adapter ID, dependency, configuration digest, elapsed time, available run identity, and known or unresolved shutdown outcome. Do not treat the timeout or a process stop as proof that cleanup completed. The plugin-runtime maintainers own a stuck startup; the adapter owner must establish cleanup and remaining resource ownership. Restore the dependency through its owner and reconcile any uncertain external effect before retry. A process start proves only that the process exists; adapter readiness proves its declared startup checks; the controlled project's terminal result proves the selected business operation.

Expected observation: the selected registration appears in the resolved graph and attempt evidence, its functional result succeeds, and audit state agrees with the terminal command output. Registry activation alone is not health; the controlled functional result is the health proof.

For endpoint, account, or data failures, use the canonical symptom diagnosis procedure. Do not retry an accepted external effect until its request and receipt are reconciled.

4. Drain and disable

Stop admission of new projects that select the registration. Inventory each pinned run from its retained start record and supported component observations. Let safe active work finish under its original owner. Do not run audit while that run or its owning adapter stores have active writers.

For each run whose owner has exited, complete Inspect a Run before audit. Use its original platform and run ID, verify stopped writers, and preserve verified raw run and owning-adapter copies. Audit can change lock files and incomplete journal tails. Require strict copied-journal inspection to succeed; preserve rejected raw bytes and stop on failure. With the canonical helper defined in the same shell:

export RUN_CONTROL_PLATFORM="<original-platform.json>"
export RUN_CONTROL_RUN_ID="<run-id>"
preserve_run_state || exit 1
audit_status=0
npm --silent run pipeline -- --platform "$RUN_CONTROL_PLATFORM" --audit "$RUN_CONTROL_RUN_ID" \
  > "$RUN_CONTROL_OBSERVATION_ROOT/audit.json" \
  2> "$RUN_CONTROL_OBSERVATION_ROOT/audit.stderr" || audit_status=$?
printf '%s\n' "$audit_status" > "$RUN_CONTROL_OBSERVATION_ROOT/audit.exit" || exit 1
test "$audit_status" -eq 0 || exit 1

Retain a separate raw-copy path, manifests, audit output, and exit status for each run. If a writer remains active or its ownership cannot be established, keep the plugin and dependencies available and stop disablement. This page provides no non-mutating live audit command. An owner-supported containment procedure can stop a process, but cannot establish terminal completion. Any later authorized canonical repair retains original bytes and records actual changes through Inspect a Run.

There is no supported operator cancel command. If a run remains active or waiting, keep the plugin package, schema, configuration, secrets, and dependency available. Urgent process containment does not make the durable run cancelled.

After every pinned run is terminal, have the platform owner create a candidate that removes the registration from provider selection, active adapters, observers, and grants. Repeat the compile procedure. Expected observation: the replacement controlled project compiles without the disabled registration and unrelated registrations retain the same identities.

5. Replace or remove

For replacement, add and validate the new exact package before disabling the old one. Prove the new functional path, drain old pinned runs, then remove old selection and grants. Do not delete the old package while a run snapshot or validator can still reference it.

For external package removal, stop after drain unless an approved operator tool calls the owned removal API with authorization and a direct child of the installation root. The repository currently supplies no such general command. Manual filesystem deletion is unsupported. Built-in packages remain part of the selected source tree; remove their activation from platform configuration, not their files from a live checkout.

Recovery, cleanup, and evidence

Before activation, recovery is to discard the candidate configuration. After a new run begins, restore the previous compatible platform configuration only for new admission; existing runs remain bound to their original graph and package snapshot. Reconcile uncertain effects before another run.

Remove unused temporary compiled files and candidate files only after retaining their hashes and final decision. Revoke a plugin secret only after all consumers are drained and the old identity is proved unused. Retain source commit, catalogue identity, package and platform digests, grants, dependency owners, secret names, compile output, functional result, audit, drain inventory, replacement proof, cleanup result, and exact blocked step.

Source Authority

The platform schema defines operator-owned installation roots, trust, providers, and grants and adapters, observers, and storage. Activation rechecks package integrity and loads only enabled registrations. External package code validates policy, digest, manifest, limits, and modules before atomically publishing the package, while removal accepts only a direct child of the installation root (implementation).

Compilation prepares and validates the admitted registry, including enabled module imports. Run startup publishes the adapter set only after startup succeeds. The starter orders dependencies, calls factories and readiness, and attempts rollback on failure. Its factory and readiness timeout race does not bound the awaited failed-readiness teardown and startup rollback. Live external plugin activation has no verified outcome for this procedure.
