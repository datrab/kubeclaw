Purpose

Prove that intended workload identities can use protected paths and unintended identities cannot. This page is the only canonical Worker Trust procedure.

Canonical Worker Trust Procedure

Supported start state, version, location, and authority

Start after the canonical installation has created the application, spire-server, and spire-system namespaces and deployed the exact selected Nova, Buster, and Prism workloads. Run commands from <repository-root> on the independent administration machine. An SVID (SPIFFE Verifiable Identity Document) is a workload credential. These deployed paths use a short-lived X.509 certificate that contains the workload's SPIFFE identity. SPIRE owns SVID issuance, the CSI driver owns socket delivery, Envoy owns peer authentication, application allowlists own authorization, and the selected source owns the expected identities and test path. Successful identity verification does not grant application permission. The receiving application's allowlist must also permit that identity.

Before any cluster command on this page, complete Bind Cluster Authority. Keep the same bound shell for the whole trust exercise. Every raw kubectl, Helm, or scripts/deploy.sh command below must inherit its exported read-only KUBECONFIG; every shown <context> must equal EXPECTED_CONTEXT. Run assert_cluster_binding immediately before each command block. Stop on any mismatch and follow the binding section's recovery; never fall back to the default kubeconfig.

No broad Kubernetes/SPIRE compatibility range is established. Record actual cluster, SPIRE chart, Envoy image, workload image, code-bundle, and trust-domain identities.

Preparation starts earlier: complete the local receipt-authority check and the live-execution boundary check below before the installation's first disposable probe or workload mutation. Readiness of existing workloads does not resolve missing signing authority or the verifier's request, denial and cleanup evidence gaps.

Preconditions

  • The explicit context and namespaces match the install record.
  • Independent cluster access works without the protected workloads.
  • SPIRE server persistence, agents, CSI driver, workload ServiceAccounts, Envoy sidecars, and NetworkPolicies are present.
  • The operator can inspect Pods and execute the registered live test's temporary Jobs and ServiceAccounts.
  • A cleanup owner and deadline exist for every temporary live-test resource.
  • The production-operator receipt authority is qualified on this administration machine, separately from the pipeline source-attestation Secret.
  • The target is an approved isolated environment. The Prism data/agent owner accepts the retained design request and possible agent/provider work.
  • A maintained owner procedure supplies the missing original request and creating-resource identities, reconciliation, and independent cleanup observations described in the live-execution boundary.
  • The workload-identity owner qualifies a maintained denial-observation procedure for each negative route, with a reachable positive control and the actual peer or authorization rejection described below.
  • The selected Nova runtime receives BUSTER_V2_TOKEN and BUSTER_SOURCE_ATTESTATION_PRIVATE_KEY, and its buster / test.plan.execute provider selects buster-plan-v1. The unit preflight rejects missing inputs or another adapter. Verify selected configuration, Secret names/key references and the owning injection procedure without printing values. The Buster owner must confirm the corresponding authentication and source-verification inputs.

Stop if the trust domain, ServiceAccount, selected image, registration, or allowlist differs from the recorded release. Do not disable mTLS or broaden an allowlist to make a check pass.

Prepare the production-receipt authority

The registered live command ends with a separate Nova-to-Buster unit transaction and an operator-signed production receipt. Its signer requires KUBECLAW_PRODUCTION_RECEIPT_PRIVATE_KEY_FILE and the trusted public key at the fixed path /etc/kubeclaw/production-receipt-authority.pub. Both resolved files must be outside the repository. The public-key path is fixed by the deploy script; setting an environment variable does not replace it.

The production-operator signing owner must supply a maintained provisioning procedure: approve the key and fingerprint, install the trust anchor on this machine, protect private-key access, and define rotation, revocation, recovery, and disposal. This repository does not install that authority. Stop before the first probe or workload mutation if its procedure or qualified files are missing. Do not generate an ad hoc key to make the command pass. The pipeline-test-gate-source-attestation Secret signs Nova's source snapshots for Buster; it does not provide this operator receipt authority.

Run this local check from <repository-root> after the signing owner installs the files. <production-receipt-private-key-path> is the owner's absolute private-key path. <production-receipt-key-fingerprint> is the independently approved sha256: fingerprint of the public key's SPKI DER bytes, the binary public-key representation used by the receipt verifier. The command reads local keys and signs a local test message; it does not contact a cluster, print key material, or create a production receipt:

export KUBECLAW_PRODUCTION_RECEIPT_PRIVATE_KEY_FILE="<production-receipt-private-key-path>"
export EXPECTED_PRODUCTION_RECEIPT_KEY_FINGERPRINT="<production-receipt-key-fingerprint>"
node --input-type=module - "$KUBECLAW_PRODUCTION_RECEIPT_PRIVATE_KEY_FILE" \
  /etc/kubeclaw/production-receipt-authority.pub \
  "$EXPECTED_PRODUCTION_RECEIPT_KEY_FINGERPRINT" <<'NODE'
import fs from 'node:fs';
import path from 'node:path';
import crypto from 'node:crypto';
try {
  const [privateFile, publicFile, expectedFingerprint] = process.argv.slice(2);
  if (!/^sha256:[a-f0-9]{64}$/.test(expectedFingerprint)) throw new Error();
  const root = fs.realpathSync(process.cwd());
  for (const file of [privateFile, publicFile]) {
    if (!path.isAbsolute(file)) throw new Error();
    const resolved = fs.realpathSync(file);
    if (!fs.statSync(resolved).isFile()) throw new Error();
    const relative = path.relative(root, resolved);
    if (relative === '' || (!relative.startsWith(`..${path.sep}`) && relative !== '..' && !path.isAbsolute(relative))) throw new Error();
    fs.accessSync(resolved, fs.constants.R_OK);
  }
  const privateKey = crypto.createPrivateKey(fs.readFileSync(privateFile));
  const publicKey = crypto.createPublicKey(fs.readFileSync(publicFile));
  if (privateKey.asymmetricKeyType !== 'ed25519' || publicKey.asymmetricKeyType !== 'ed25519') throw new Error();
  const fingerprint = 'sha256:' + crypto.createHash('sha256')
    .update(publicKey.export({ type: 'spki', format: 'der' })).digest('hex');
  const message = Buffer.from('KubeClaw operator receipt key qualification');
  if (fingerprint !== expectedFingerprint ||
      !crypto.verify(null, message, publicKey, crypto.sign(null, message, privateKey))) throw new Error();
  console.log(JSON.stringify({ authority: 'kubeclaw:production-operator',
    publicKeyFingerprint: fingerprint, localKeyPairVerified: true }));
} catch {
  console.error('PRODUCTION_RECEIPT_AUTHORITY_UNQUALIFIED');
  process.exit(1);
}
NODE

Expected observation: exit zero and only the authority, approved fingerprint, and local keypair result. Retain this non-secret output, command exit, tool version, signing-owner approval and provisioning reference. Missing files, repository-local resolved paths, unreadable keys, a non-Ed25519 key, mismatched keys or a different fingerprint must stop the route. Ask the signing owner to repair the first failed prerequisite, then repeat the check. A matching pair does not establish owner approval, live trust, or receipt success.

3. Check the live-execution boundary

The implemented command is npm run verify:worker-core:trust:live. It runs deploy.sh worker-trust-e2e in this checkout.

After the owners qualify the signing, lifecycle and denial-observation prerequisites below, this implemented live command uses deployed workloads and a real unit process. It does not use a test-double server or fabricated completion result. Local synthetic checks remain separate from this live execution. This implementation fact does not establish a live result here or make ambiguous negative-probe JSON sufficient denial proof.

Its effects occur in this order:

  1. The live script waits for Nova, Buster, Prism Control, and Prism Worker, inspects loaded SVIDs, and checks protected proxy paths.
  2. Nova sends a Prism design request through its loopback proxy. The script generates a project key internally and uses it as the idempotency key. A 202 response admits durable work: Control persists the project and active design request, starts a design round, and admits a design-agent job. Agent execution can invoke its configured provider. This is not only a health request, and deleting test Jobs does not remove that work.
  3. The script checks plaintext rejection and creates two Jobs and two ServiceAccounts for wrong-identity tests, in the recorded application and Prism namespaces. It waits for the Jobs and emits live trust JSON.
  4. On exit, its trap attempts asynchronous Job and ServiceAccount deletion. The wrapper then runs the Nova unit production preflight. This submits a signed source snapshot to Buster, runs a real unit process, and imports its evidence. The operator signer checks the deployed Buster revision, signs the unit result, verifies it with the installed trust anchor, and writes dist/verification/unit-production-receipt.json in this checkout.

The current live script does not retain the design request's original key, architecture digest, project response, round, or agent-job response. It discards an accepted dispatch response. It also does not emit creating object UIDs or a cleanup receipt. Its internal RUN_ID is not an operator input or a guaranteed retained receipt. Raw kubectl output can incidentally expose resource names; that does not prove their creating identities or durable-request identity. The deletion trap uses --wait=false, suppresses output, and ignores errors. Exit zero and final live JSON therefore do not prove cleanup.

Required results and cleanup observations

After the owners resolve that prerequisite, retain the complete command output and exit status separately from each result. Live JSON with schemaVersion=worker-trust-cluster-e2e.v1 declares successful Nova-to-Buster, Nova-to-Prism, Prism-Control-to-Worker and Prism-Worker-to-Control paths. Its negative paths cover plaintext, wrong SVID and forged forwarded identity. A positive result without its paired denial is incomplete. This JSON does not contain source-signing proof or a cleanup result. It also does not establish why a negative request failed.

The wrong-SVID probes first check that the unintended SVID was loaded. They then accept any non-2xx response (a status outside 200–299), and also accept a fetch exception, as denial. TLS (Transport Layer Security) authenticates peers and encrypts the connection. The direct TLS probes accept any network error or timeout as rejection. Thus an unreachable proxy, connection refusal or HTTP 503 can still lead to success JSON. These outcomes do not prove that a peer or allowlist rejected the caller. Earlier positive requests use different callers or endpoints and occur at a different time; they do not establish the cause of a later failure.

Classify unavailable endpoints, timeouts and HTTP 5xx server-error responses as inconclusive. Stop approval, preserve the failed observation and repair reachability or the server through its owner. Even a non-2xx response such as HTTP 403 needs the owner's correlated identity and rejection evidence. Retain the actual peer or authorization rejection and its reachable positive control for each negative route before accepting the paired result. The plaintext, wrong-SVID and forged forwarded-identity paths remain mandatory. Do not replace them with smoke checks or treat the live command's exit zero as independent denial proof.

Failure distinction

Check in this order:

  1. context and namespace;
  2. SPIRE server persistence and agents;
  3. CSI socket mount;
  4. Envoy bootstrap, readiness, and loaded SVID;
  5. Service endpoint and target port;
  6. NetworkPolicy in both directions;
  7. application identity allowlist;
  8. source-signing key configuration;
  9. separate operator receipt signing and verification;
  10. durable request reconciliation and test cleanup.

A timeout, unreachable endpoint or HTTP 5xx response is inconclusive denial evidence. Diagnose reachability and server health first. An observed TLS/SVID rejection concerns identity issuance or peer verification. A correlated authenticated denial concerns the application allowlist. A successful wrong-identity request is a security incident: restrict the owning Service, retain evidence, and stop admission.

Use the exact error code to select the first repair. Do not weaken a trust rule to remove an error.

Error code Meaning First repair
WORKER_TRUST_PEER_MISSING The verified forwarded-certificate header is absent or contains more than one certificate entry. Inspect the destination Envoy ingress and confirm that traffic enters through it.
WORKER_TRUST_PEER_INVALID The header does not contain exactly one valid SPIFFE URI. Inspect the verified certificate URI SAN and Envoy SANITIZE_SET output.
WORKER_TRUST_POLICY_INVALID The application allowlist is empty or contains an invalid SPIFFE ID. Restore the exact expected identities before restarting the workload.
WORKER_TRUST_PEER_FORBIDDEN The authenticated SPIFFE ID is not in the application allowlist. Compare the caller namespace and ServiceAccount with the configured identity.
WORKER_TRUST_PROXY_REQUIRED Worker Core received forwarded identity from a non-loopback address. Route the request through the colocated Envoy listener.
REMOTE_TEST_GATE_SPIFFE_PROXY_NOT_LOOPBACK A remote-suite provider selected SPIFFE proxy authentication with a non-loopback endpoint. Set that provider endpoint to its Nova loopback Envoy listener.
NOVA_REMOTE_PLAN_SPIFFE_PROXY_NOT_LOOPBACK The Nova remote-plan transport selected SPIFFE proxy authentication with a non-loopback endpoint. Use http://127.0.0.1:28891 for the Buster plan route.
BUSTER_REMOTE_SPIFFE_POLICY_INVALID Buster has no valid trusted Nova SPIFFE ID. Restore the exact Nova identity in the Buster policy.
NOVA_SOURCE_ATTESTATION_PRIVATE_KEY_MISSING Nova did not receive the source-attestation private key. Inspect the pipeline-test-gate-source-attestation Secret reference and its privateKey key.
NOVA_SOURCE_ATTESTATION_PRIVATE_KEY_INVALID Nova cannot parse the private key or the key is not Ed25519. Replace the complete Ed25519 keypair and restart both key consumers in the maintenance window.
BUSTER_SOURCE_ATTESTATION_PUBLIC_KEY_MISSING Buster did not receive the source-attestation public key. Inspect the same Secret reference and its publicKey key.
BUSTER_SOURCE_ATTESTATION_CONFIG_INVALID Buster cannot parse an Ed25519 public key, or its trusted source authority is invalid. Compare the public key and authority with Nova's active signer configuration.
BUSTER_SOURCE_ATTESTATION_INVALID The received source snapshot does not pass signature, authority, or content verification. Stop execution. Compare the selected revisions, authority, archive digest, and active keypair before retrying.

The two loopback errors are separate because the plugin adapter and the Nova transport validate different configuration boundaries. Both reject a remote URL before any request can claim SPIFFE proxy authentication.
