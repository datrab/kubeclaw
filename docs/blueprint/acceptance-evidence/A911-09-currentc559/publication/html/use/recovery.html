Back Up and Recover

Status: executable component backups and native restore primitives; no self-contained isolated LiteLLM, external Prism, or full-platform operator restore Audience: platform operator, database operator, incident responder Owner: platform operations and data owners Evidence: charts/prism/files/prism-backup.sh; scripts/postgresql-recovery.sh; docs/status/open-issues.json Applies to: current selected runtime and state formats Last verified: 2026-10-12; local identity, selection, and snippet guards only; no live restore result is available

Objective

Protect every authoritative state before loss and restore it without broken references. Finish only after application readers verify the restored data.

The recovery point objective (RPO) is the maximum data-loss time window that the data owner approves. The recovery time objective (RTO) is the maximum recovery duration that the service owner approves. These are targets. Actual data loss and elapsed recovery time are separate measurements from a recovery exercise or incident. Compare those measurements with the approved targets; a target alone does not prove recovery performance.

This page supplies no environment-wide target values or measured proof that those targets can be met. Record owner decisions and execution results separately.

Canonical Backup and Restore Procedure

This page is the sole authority for backup-restore. Start with an owned component, compatible source and target versions, complete independently held credentials and keys, checksum-valid media, an empty isolated target, enough capacity, and an unchanged source. Run cluster inspection from the independent administration machine and restore tooling from the isolated recovery environment named by the component procedure. Backup scripts, database-native tools, immutable group metadata, and the original application reader are the authorities.

Before any cluster command on this page, complete Bind Cluster Authority. Keep the same bound shell for the whole recovery task. Every raw kubectl, Helm, or scripts/deploy.sh command below must inherit its exported read-only KUBECONFIG, NAMESPACE, and PRISM_NAMESPACE. The binding section validates and freezes both namespace names before any command here; every shown <context> must equal EXPECTED_CONTEXT. Run recovery_assert_namespace from Bind Recovery Objects immediately before each cluster command block. Stop on any mismatch, leave media and targets unchanged, and follow the binding section's recovery; never fall back to the default kubeconfig.

Complete State Inventory, Define a Backup Set, the six-step Procedure, Choose Restore Scope, the applicable component path or documented boundary, and Verification. Stop on a missing group member, checksum mismatch, wrong key or credential, unsupported version pair, nonempty target, same-server target where forbidden, unclear writer fence, or absent original application reader.

Final proof is a native integrity result plus a successful read through the original application, with writers still fenced until cutover. Retain exact commands, tool and source versions, group identity and checksums, encryption and credential authorities, isolated target identity, native and application results, measured loss/time, cutover, cleanup, and every failed attempt.

Bind Recovery Objects

Use Bash, Python 3, and the selected kubectl on the independent administration machine. Keep set -euo pipefail and umask 077 in the bound shell. Before a component Job, obtain its existing namespace UID from the platform owner independently of this kubeconfig. Set EXPECTED_APPLICATION_NAMESPACE_UID for LiteLLM and EXPECTED_PRISM_NAMESPACE_UID for Prism. Set only the scopes used in this incident. A shared namespace must have the same expected UID in both scopes.

The platform owner must exclude namespace replacement and competing changes to these manual Jobs and their Pods until evidence and cleanup finish. A UID comparison alone does not exclude a later replacement. The cluster identity needs get on the named namespace and source CronJob, create, get, watch, and delete on Jobs, list and get on Pods, and get on pods/log in the selected namespace. The inventory blocks also need list on PVCs, CronJobs, Jobs and Events in their selected namespaces. Check each required permission through Check authority for the selected scope. The evidence owner must keep these private files unchanged through capture and cleanup. No component backup Pod supplies this administration identity.

Define these helpers in the same shell. Their evidence directory is the new private directory created by the component procedure. A successful CREATE response establishes the Job UID; a later same-name lookup does not.

recovery_assert_namespace() {
  local expected
  assert_cluster_binding || return 126
  if [[ $1 == "$NAMESPACE" ]]; then
    if [[ $NAMESPACE == "$PRISM_NAMESPACE" && -n ${EXPECTED_APPLICATION_NAMESPACE_UID:-} && -n ${EXPECTED_PRISM_NAMESPACE_UID:-} ]]; then
      test "$EXPECTED_APPLICATION_NAMESPACE_UID" = "$EXPECTED_PRISM_NAMESPACE_UID" || return 126
    fi
    if [[ $NAMESPACE == "$PRISM_NAMESPACE" ]]; then
      expected=${EXPECTED_APPLICATION_NAMESPACE_UID:-${EXPECTED_PRISM_NAMESPACE_UID:?}}
    else
      expected=${EXPECTED_APPLICATION_NAMESPACE_UID:?}
    fi
  elif [[ $1 == "$PRISM_NAMESPACE" ]]; then
    expected=${EXPECTED_PRISM_NAMESPACE_UID:?}
  else
    return 126
  fi
  test "$(kubectl --context "$EXPECTED_CONTEXT" get namespace "$1" \
    -o jsonpath='{.metadata.uid}')" = "$expected"
}
recovery_create_job() {
  local ns=$1 cron=$2 job=$3 evidence=$4
  [[ ${#job} -le 63 && $job =~ ^[a-z0-9]([-a-z0-9]*[a-z0-9])?$ ]] || return 1
  test ! -e "$evidence/$job.create.json" || return 1
  recovery_assert_namespace "$ns" || return 126
  kubectl --context "$EXPECTED_CONTEXT" -n "$ns" create job \
    --from="cronjob/$cron" "$job" -o json > "$evidence/$job.create.json" || return 1
  python3 - "$evidence" "$ns" "$job" <<'PYTHON'
import json, pathlib, sys
root, ns, name = pathlib.Path(sys.argv[1]), sys.argv[2], sys.argv[3]
j = json.loads((root / (name + '.create.json')).read_text())
m = j.get('metadata', {})
if (j.get('kind') != 'Job' or m.get('namespace') != ns or
    m.get('name') != name or not isinstance(m.get('uid'), str) or not m['uid']):
    raise SystemExit('valid Job CREATE identity is required')
(root / (name + '.uid')).write_text(m['uid'] + '\n')
PYTHON
}
recovery_capture_job_logs() {
  local ns=$1 job=$2 container=$3 evidence=$4 log=$5 deadline pod
  recovery_assert_namespace "$ns" || return 126
  deadline=$(python3 - "$evidence/$job.create.json" <<'PYTHON'
import json, sys
j = json.load(open(sys.argv[1]))
deadline = j.get('spec', {}).get('activeDeadlineSeconds')
if type(deadline) is not int or deadline <= 0:
    raise SystemExit('positive Job deadline is required')
print(deadline + 30)
PYTHON
  ) || return 1
  kubectl --context "$EXPECTED_CONTEXT" -n "$ns" wait \
    --for=condition=complete "job/$job" --timeout="${deadline}s" || return 1
  kubectl --context "$EXPECTED_CONTEXT" -n "$ns" get pods \
    -l "job-name=$job" -o json > "$evidence/$job.pods.json" || return 1
  pod=$(python3 - "$evidence" "$ns" "$job" <<'PYTHON'
import json, pathlib, sys
root, ns, name = pathlib.Path(sys.argv[1]), sys.argv[2], sys.argv[3]
uid = (root / (name + '.uid')).read_text().strip()
items = json.loads((root / (name + '.pods.json')).read_text()).get('items', [])
if len(items) != 1: raise SystemExit('exactly one owned Pod is required')
p = items[0]; m = p.get('metadata', {})
if (m.get('namespace') != ns or not m.get('name') or not m.get('uid') or
    p.get('status', {}).get('phase') != 'Succeeded' or
    not any(o.get('kind') == 'Job' and o.get('uid') == uid and
            o.get('controller') is True for o in m.get('ownerReferences', []))):
    raise SystemExit('succeeded Pod with original Job ownership is required')
(root / (name + '.pod-uid')).write_text(m['uid'] + '\n')
print(m['name'])
PYTHON
  ) || return 1
  test "$(kubectl --context "$EXPECTED_CONTEXT" -n "$ns" get job "$job" \
    -o jsonpath='{.metadata.uid}')" = "$(cat "$evidence/$job.uid")" || return 1
  test "$(kubectl --context "$EXPECTED_CONTEXT" -n "$ns" get pod "$pod" \
    -o jsonpath='{.metadata.uid}')" = "$(cat "$evidence/$job.pod-uid")" || return 1
  kubectl --context "$EXPECTED_CONTEXT" -n "$ns" logs "$pod" -c "$container" \
    > "$evidence/$log"
}
recovery_delete_job() {
  local ns=$1 job=$2 evidence=$3
  recovery_assert_namespace "$ns" || return 126
  python3 - "$evidence" "$job" <<'PYTHON'
import json, pathlib, sys
root, name = pathlib.Path(sys.argv[1]), sys.argv[2]
uid = (root / (name + '.uid')).read_text().strip()
if not uid: raise SystemExit('original creating UID is required')
(root / (name + '.delete.json')).write_text(json.dumps({
    'apiVersion': 'v1', 'kind': 'DeleteOptions',
    'preconditions': {'uid': uid}, 'propagationPolicy': 'Foreground'}) + '\n')
PYTHON
  test "$?" -eq 0 || return 1
  kubectl --context "$EXPECTED_CONTEXT" delete --raw \
    "/apis/batch/v1/namespaces/$ns/jobs/$job" \
    -f "$evidence/$job.delete.json" > "$evidence/$job.delete-response.json" || return 1
  kubectl --context "$EXPECTED_CONTEXT" -n "$ns" wait \
    --for=delete "job/$job" --timeout=120s || return 1
  kubectl --context "$EXPECTED_CONTEXT" -n "$ns" get job "$job" \
    --ignore-not-found -o name > "$evidence/$job.after.txt" || return 1
  test ! -s "$evidence/$job.after.txt"
}

Expected result: namespace checks pass; each successful CREATE returns the exact Job kind, name, namespace and nonempty UID. Failed or unreadable CREATE output means uncertain ownership. Retain the response and stop. Ask the platform owner to reconcile the API request and its audit record; do not adopt a UID from a later lookup, retry the same name, or delete the object.

Cleanup sends the original Job UID as a server-side deletion precondition. It then waits at most 120 seconds and records a successful empty named read. A UID conflict, denied read, timeout, or present Job is a cleanup failure; retain the operation for owner reconciliation. This deletion removes the owned Job and its dependent Pods, so capture all required Pod evidence first. The UID precondition protects object identity, but the owner exclusion still protects namespace identity and the evidence window. Never infer absence from a failed read. Log capture requires one succeeded Pod owned by the creating Job UID, checks both current UIDs, and reads that exact Pod and container. Its wait uses the returned Job deadline plus 30 seconds; it does not assume a default duration. A wait or capture failure stops acceptance. Retain the CREATE response, collect available status/events/logs read-only from those same identities, and let the owners diagnose before retry or cleanup.

Supported Versions

Use the shared version rules. A restore supports only a source, application, schema, backup format, and database-client combination that the component procedure declares compatible. If that declaration is absent, stop before restore. The component owner must supply a versioned compatibility test procedure for an isolated target and accept its results before authorizing restore or cutover.

Prerequisites

  • Independent administration works without the target application Pods.
  • The operator knows the selected source, image, schema, and data versions.
  • Backup credentials and decryption keys remain available outside the target namespace.
  • The recovery target is isolated from current writers.
  • The operator has enough capacity for source, restore target, and retained evidence.
  • A named owner can approve cutover or stop recovery.

Nonnegotiable Rules

  • A PVC is not a backup.
  • A backup on the same node is not independent recovery media.
  • Database and referenced artifacts form one consistency group.
  • Credentials and encryption keys need a separate recovery authority.
  • Rebuildable indexes must never replace authoritative source data.
  • Restore into an isolated target before destructive replacement.
  • Preserve the old environment until application verification passes.
  • Never use the failed Ops Pod as the only recovery tool.
  • Repository-produced local Prism and LiteLLM archives are not encrypted by these scripts. Mode 0600 and checksums provide access restriction and integrity detection, not encryption. Store independent copies only in an encryption-at-rest authority with separately recoverable keys and record that authority with the group.

Define a Backup Set

For each state owner, record:

  • Source resource, namespace, PVC, database, or directory.
  • Consistency group and required writer fence.
  • Backup mechanism and exact tool version.
  • Destination and its failure domain.
  • Credential and key authority.
  • Schedule, retention, size limit, and alert owner.
  • Integrity check and application restore check.
  • Last successful restore proof.

Record the owner-approved RPO and RTO targets, their scope, and the owner's decision. If the owner has not approved a target, mark that target undecided. Record actual data loss and elapsed recovery time separately. Mark each missing measurement not measured, and record whether a completed restore met each approved target. A measured result does not set the target, and a CronJob schedule alone does not prove the actual data-loss window.

Procedure

Use the next six steps for routine backups.

1. Confirm Target and Capacity

Run from the administration machine:

recovery_assert_namespace "$NAMESPACE"
kubectl config current-context
kubectl -n "$NAMESPACE" get pvc
kubectl -n "$NAMESPACE" get cronjob,job
kubectl -n "$NAMESPACE" get events --sort-by=.metadata.creationTimestamp

Confirm destination free space before starting a manual backup. Keep the previous completed group when capacity is low.

2. Fence Administrative Changes

Stop migrations, deletion, compaction, key rotation, and artifact restoration. Use the component-specific writer fence where required.

Do not stop normal writers unless the selected backup contract requires it. If the component contract requires a stronger fence, follow that contract. Record the exact fence and its start time.

3. Run the Owned Backup Mechanism

Use the service-owned paths on this page:

  • Single-Service Restore for the LiteLLM PostgreSQL backup/restore boundary and explicit Redis limit.
  • Prism Restore for the Prism database and artifacts.
  • Recover Administrative Access for the optional Ops Pod and independent access.

For Nova, Buster, and role PVCs, use the approved storage backup product. The repository provides no universal backup command for those stores.

Quiesce the owning workload when that backup cannot provide a consistent snapshot. Record any downtime and incomplete attempt before the snapshot.

4. Verify Integrity

A completed backup needs more than successful upload. Check:

  • Manifest and metadata exist.
  • Every required group member exists.
  • Checksums match actual bytes.
  • Database archive listing succeeds.
  • Artifact filenames match content digests.
  • Backup identity matches source version and database.
  • Required key authority remains available.

5. Copy to an Independent Destination

Copy or replicate the completed immutable group to a different failure domain. Do not move an incomplete staging directory.

Verify checksums again at the destination. Record destination object identity and retention policy.

6. Release the Fence

Release writers only after local and destination verification pass. If verification fails, retain the previous completed group and failed evidence.

Prism Backup Group

Prism treats its database and immutable artifacts as one group. The backup script dumps the database first. It then copies the immutable artifact superset.

This order depends on durable immutable artifact publication before database references. The artifact writer synchronizes bytes and their published path, and the backup contract requires publication before a database reference. Administrative artifact deletion must not overlap the backup.

The chart creates these scheduled resources:

  • prism-backup.
  • prism-backup-verification.
  • prism-restore-proof.

Each verification and database-proof invocation selects latest independently. Use Prism Restore to compare observable group identities and recognize the unbound database-smoke limit. Inspect the three CronJob resources and retained labelled Pods. The chart puts app=prism-backup on Pod templates; it does not put that label on Jobs. This Pod observation can include both scheduled and manual attempts and does not establish the last completed Job:

recovery_assert_namespace "$PRISM_NAMESPACE"
kubectl -n "$PRISM_NAMESPACE" get cronjob prism-backup prism-backup-verification prism-restore-proof
kubectl -n "$PRISM_NAMESPACE" get pods -l app=prism-backup --sort-by=.metadata.creationTimestamp

Expected observation: the three named CronJobs are returned. The Pod command returns retained Pods with that label, or succeeds with an empty list when no matching Pod is retained. An empty list does not prove that no scheduled Job ran. A missing CronJob, denied lookup, or other nonzero command exit is a failed observation: stop and retain the error before owner diagnosis. For manual Job acceptance, use the original CREATE UID and owned-Pod checks in Prism Restore, not this label alone.

The backup PVC and artifact PVC carry Helm keep policy and Argo CD prune/delete exclusions. They remain in the same cluster failure domain until an operator copies them externally.

Source evidence — Prism consistency group

Claim: Prism protects one database snapshot and the immutable artifact superset as a single published group. Verification rebuilds the artifact index from the stored bytes.

Implementation: The backup script verifies an immutable database-and-artifact archive. It then creates and publishes a complete group without replacing an existing group. The database proof restores a temporary database and queries core tables.

Contract or setting: The chart defines the backup and verification schedules and commands. It also defines Secret inputs and volume mounts. All three modes mount the backup PVC writable for the shared lock and verification scratch files. Only backup mounts the artifact source, and that source mount is read-only. verify receives no database credentials; backup and database-proof receive the selected database Secret.

Test evidence: Capacity failures do not publish partial groups. The rendered jobs preserve commands, database separation, and read-only artifact access. The SQL proof owns a new temporary database and cleans failed proof attempts. The test failed on 2026-09-16 before positive backup proof because the host supplied BusyBox-incompatible utilities and the chart fixture failed its native-worker precondition. Single-Service Restore

Starting Conditions

  • The backup group passes integrity checks.
  • Source and target versions are compatible.
  • The target is isolated from current writers.
  • Required credentials and keys come from external authority.
  • The old service and media remain unchanged.

Procedure

The following list is a restore qualification checklist, not a general restore command or support claim. Continue only when the component subsection supplies every item with an owned executable path. The current LiteLLM and Redis subsections do not supply a complete isolated operator restore.

  1. Record source version, target version, and migration state.
  2. Create an empty isolated target.
  3. Restore with the documented component tool.
  4. Reject any missing, extra, corrupt, or wrong-key member.
  5. Run native database or store checks.
  6. Run the original application reader.
  7. Compare expected records, references, and content digests.
  8. Keep the restored target isolated until every check passes.
  9. Plan cutover and rollback as separate reviewed actions.

Do not substitute a filesystem copy for a database restore.

LiteLLM PostgreSQL Backup and Restore Boundary

The selected installation can create cronjob/litellm-postgresql-backup and pvc/litellm-postgresql-backup. This is an executable backup and verification path, not a complete isolated operator restore. Read the selected LiteLLM source and image boundary and rows and encryption inputs before selecting the application image or recovering keys. Start with the deployed source revision, its selected immutable LiteLLM image, externally owned master/salt keys, a healthy LiteLLM PostgreSQL service, and enough backup-PVC capacity.

Before creating the manual backup Job, fence LiteLLM writes as required by its backup-group contract. This component contract requires a stronger fence than the generic routine backup guidance. Use the database and LiteLLM owners' procedure for the deployed service. Stop before creating the Job if that procedure is missing or does not clearly specify how to apply and verify the writer fence. Record the fence and its start time.

The storage owner must also supply an authorized way to read and export a completed directory from pvc/litellm-postgresql-backup without changing its bytes. It must bind the PVC UID and source directory to a private local copy, exclude symlinks, preserve the four files, and keep the source group immutable through the copy. A completed Pod cannot be assumed to support exec or kubectl cp. This page creates no access Pod and supplies no generic PVC-mount or encrypted-storage transfer command. Stop before Job creation if the actual PVC access/export and encrypted independent-storage transfer procedures are missing. Record their owner, version, access identity and destination authority.

Use Bash and Python 3 on the independent administration machine. Set set -euo pipefail and umask 077 in the bound administration shell. Set LITELLM_BACKUP_JOB to litellm-backup-manual-<unique-id>, where <unique-id> is a new lowercase DNS-label suffix. Set LITELLM_BACKUP_EVIDENCE to a new private directory outside the backup PVC. The cluster identity needs permission to create/read/delete this exact Job, read its Pod identity/status and read its logs. Stop on any command failure; keep the fence and all previous media while the owners diagnose the failure.

Prism Restore

A Prism recovery point is one database dump and artifact set from the same immutable group. Never combine members from different groups. The current commands accept only backup, verify, or database-proof; they have no argument for a requested <backup-group>. Both checks independently select the lexically last backup-* directory when they run. The database proof prints its temporary database name, not the group it selected.

Each invocation holds the shared backup-PVC lock while it runs. That lock does not bind separate Jobs to one group. concurrencyPolicy: Forbid prevents overlap within each CronJob, but does not stop another CronJob or manual Job from publishing a new group between commands. Pipeline State Recovery

Use the original platform file, run ID, graph or project, package snapshot, storage root, and configuration from the retained start record. Run the inspection and recovery commands from the original Nova repository with the shared version and tool prerequisites. The Nova operator and each adapter-store owner must establish and verify the writer fence. Stop if ownership or the original identity is unknown.

Do not restore one journal file without its related effects, waits, artifacts, and snapshots. Restore the complete run root from one consistent point. Keep Nova and the owning adapter writers stopped after restoration.

Audit can change storage: it creates an append-lock file and can truncate an incomplete journal tail before parsing. Recovery and resume also open these journals. Backup checksums and the resulting audit JSON do not preserve the restored raw bytes.

After filesystem restoration:

  1. Verify file ownership, permissions, backup checksums, and the original run and platform identities.
  2. Complete Inspect a Run before audit, recovery, or resume. Preserve and verify a new raw copy of the restored run and the owning adapters' stores while their writers remain stopped. Keep partial journal bytes, signals, effects, snapshots, and lock files.
  3. Require successful strict parsing of every copied run journal. On a copy, identity, sequence, hash, or incomplete-record failure, retain the raw copy and manifest and stop. Do not run audit to make the journal pass.
  4. Only after those checks, capture the canonical audit and its exit status through Inspect a Run. Stop on audit failure or changed graph identity; retain both raw bytes and command output.
  5. Reconcile every accepted external effect without a terminal receipt through its owning contract. Stop while an outcome is unknown or no supported reconciliation method exists.
  6. Use Recover After Interruption only when its original-identity and reconciliation checks pass. That command reopens the original run; starting a new run is not recovery.
  7. After the command exits and writers are stopped, repeat raw preservation and strict inspection before the final audit. Compare the original and final state and retain recovery output, external receipts, and cleanup.

If the owning incident procedure later authorizes canonical tail repair, retain the verified original raw bytes first, reconcile external effects, and record the authorized command and its actual file changes. The automatic truncation is not proof that recovery succeeded.

Do not recover a terminal run. Do not resume a wait with a signal from before the restored point. Retain the writer-fence record and all failed attempts; release writers only through the owners' verified recovery procedure.

The restored authority matches one verified backup point. Every original consumer can read its required state and referenced content.

Rollback Boundary

Before cutover, rollback means returning clients to the unchanged old service. After new writes, that rollback can lose accepted data.

Do not use an old application image against a migrated incompatible database. Do not downgrade data through an image rollback.

At the irreversible point, record:

  • Last old write.
  • First new write.
  • Backup group.
  • Schema and application versions.
  • Operator and approval.
  • Recovery choice if verification later fails.
