Prepare a clean checkout

Use an isolated development checkout on Linux. Journal checks require GNU util-linux flock at /usr/bin/flock, including --timeout and --conflict-exit-code. A BusyBox command with the same name does not meet this requirement.

The journal uses fsync, which requests synchronization of a file's data and metadata (information about the file) with storage. Here, an inode is the underlying filesystem object that a lock protects. A pathname identifies that object. If a process removes or replaces the pathname while another process still uses the original object, a new process can open a different object and take a competing lock.

Use a filesystem qualified for the required Linux locks, complete append writes, and file synchronization. Do not assume a shared/network mount has the same durability behavior. Never unlink or replace a stable lock inode while a process can use it. Synchronizing the journal file does not by itself prove that the entry linking it into its parent directory survives a host crash. The C isolation launcher requires a C11 compiler named cc. Use Bash and GNU tar for bundle scripts. Use Git for checkout, source-identity, and compatibility fixtures. Keep fixture work outside a deployed run root.

Use Node.js 24, npm, and the committed root lockfile. CI selects Node 24 rather than an exact host patch. Container patches and digests come from versions.json; they are separate from the CI host. TypeScript 5.9.3 is a root development dependency. Do not substitute a global tsc for the lockfile-selected compiler. Root npm scripts put node_modules/.bin on PATH.

Select the smallest complete check chain

A small check chain must cover every changed invariant. It is not necessarily one script. Use these six questions to select it:

  1. Which local rule changes? Add a positive and a negative unit assertion.
  2. Which producer/consumer boundary can change? Run its contract and type checks.
  3. Which committed record can be replayed? Check live execution against replay.
  4. Where can a crash, cancellation, or uncertain external effect occur? Check recovery from that exact durable boundary.
  5. Which earlier bytes, identities, or consumers remain supported? Run the applicable compatibility fixtures and generated-output checks.
  6. Which reader procedure, reference, error explanation, or release input changes? Update its canonical page and validate its commands, links, and reference output.

An in-memory unit test does not exercise locks, process death, native authority, transport authentication, or a real service. Add the next layer only when the change reaches that layer. A missing environment remains an unexecuted required check. A skip is not a successful negative proof.
