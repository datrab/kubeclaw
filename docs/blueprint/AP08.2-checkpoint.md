## Reader Result

The product page now gives a complete first-plugin journey for a technical reader.
The reader can inspect and test a package, copy it into the Nova plugin root, add
explicit role ownership, build a role bundle, activate the stage, and inspect its
result. The same journey causes an intentional stage failure, rejects invalid input,
removes the package, and explains which earlier run evidence remains.

The example stays capability-free. This choice keeps the first journey focused on
package identity, schemas, role composition, registry grants, activation, and stage
state. AP08.4 owns external effects, idempotency, reconciliation, and uncertain
outcomes. The product page explains this division and does not present the minimal
example as an effectful production plugin.

AP08.2 is a plugin-authoring task. It does not own `.swarm/pipeline.json`, the project
compiler, pipeline submission, transport, the running Nova service, or an end-to-end
pipeline run. The checker creates one in-memory `pipeline-definition.v2` value only
to invoke the registered stage. This value is a local test harness, not a documented
project or pipeline configuration.

## Maintained Example

The canonical example is
[`docs/site/extend/examples/minimal-stage`](../site/extend/examples/minimal-stage/).
It contains one manifest, three JSON schemas, one stage module, and an isolated
package test. The stage registers `example.greeting.say` and requests no
capabilities. A successful call produces the fact `tutorial.greeting`. Input with
`fail: true` produces the terminal reason `tutorial.requested_failure`.

The example remains outside the shipped Nova plugin root. Documentation checks can
therefore execute it without adding tutorial behavior to a production role. The
reader journey makes the copy and role selection explicit. It also explains why a
source directory, a role selection, a built bundle, and an activated runtime are
four different proofs.

## Executable Journey

[`scripts/check-ap08-minimal-plugin.mjs`](../../scripts/check-ap08-minimal-plugin.mjs)
uses the real package schemas and runtime components. It performs these checks:

1. It verifies required guide sections, all seven example links, and the exact
   manifest shown in the page.
2. It resolves at least nine source links against their pinned Git revision and
   checks every line range.
3. It copies the package to a temporary installation root and runs its package test.
4. It proves that Nova rejects the owned package before the role selects it.
5. It passes a verification-only Nova role addition through the normal role checker.
6. It uses Foundation discovery, registry construction, grant resolution, and
   activation.
7. It uses a local Nova `PipelineRunner` harness, the stage executor, schema
   validation, and the lifecycle reducer for successful and intentionally failed
   plugin invocations.
8. It proves that invalid input stops before stage execution.
9. It removes the temporary package and requires
   `PIPELINE_STAGE_OWNER_MISSING` from a new activation attempt.
10. It confirms that the earlier success and failure event records remain readable.

The role checker now accepts optional `--additional-plugin` and `--role-addition`
arguments. These arguments change only the checker's in-memory catalogue and role
selection. Default role verification remains unchanged. This design tests the same
closure rules without changing the repository's production Nova role during a
documentation check.

The manual page also includes the physical copy, role-manifest edit, standard role
check, bundle build, bundle-manifest inspection, and exact reversal steps. The
automated check proves the role-selection rules. It does not claim that it wrote and
deployed a production role bundle.

## Persistence Boundary

An initial attempt used Nova's persistent file journal through `runPipelineV2`.
That path stopped before plugin execution because the local BusyBox `flock` command
does not support GNU `flock --timeout`. This host-tool difference is not a plugin
failure.

The maintained AP08.2 check therefore uses a controlled in-memory journal with the
production registry, grant, activation, runner, executor, and reducer. It proves
event production and retained records in one process. It does not prove persistent
file locking, process restart, snapshot recovery, image assembly, or live cluster
execution. The product page states this limit next to the command and in its expected
result table.

## Completion Decision

AP08.2 is complete for its declared documentation scope. A clean checkout contains
the maintained package and a guide that reaches package testing, explicit Nova role
selection, bundle inspection, runtime activation, observed success, intentional
failure, validation failure, removal, and remaining-state analysis. The durable
check exercises the local runtime path without modifying the shipped role.

This decision does not accept the complete pipeline-stage surface, an effectful
plugin, persistent recovery, live deployment, or the 51-package catalogue. AP08.3
is next and owns the shared data, authority, failure, and lifecycle contracts for all
five pipeline registration types.
